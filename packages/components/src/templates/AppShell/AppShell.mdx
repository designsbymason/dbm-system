<VisuallyHidden asChild><h2>Intro</h2></VisuallyHidden>

<ComponentHeader title="AppShell" tier="Template" />

**Which shell?** An app with a sidebar uses `AppShell`; one with no sidebar uses [`PageShell`](/docs/templates-application-shells-pageshell--docs).

The page frame of an application: a navigation column on one side, a header across the top, a main
area for the page's content, an optional aside at the other edge and an optional footer. It is
**layout and wiring only**. You put your own
[`Sidebar`](/docs/organisms-navigation-sidebar--docs) and
[`Navbar`](/docs/organisms-navigation-navbar--docs) in its slots and keep every prop they have; the
shell adds the grid they sit in, the page's one `<main>` landmark, the skip link's target, and the
shared state that lets a menu button in the header open the sidebar's panel on a phone.

By default the frame is exactly as tall as the window and only the main area scrolls, so the
sidebar and the header never move. Below the sidebar's `collapseBelow` width the sidebar leaves the
page for a menu button and a slide-in panel, and its column disappears so the main area takes the
whole width. The aside does the same below `asideCollapseBelow`: it becomes a drawer opened from a
toggle button, or disappears if you ask for that. The shell keeps a notch or a home indicator clear,
can run its header over the sidebar, and, given the router's page, moves focus to the new page and
announces it. It can collapse the sidebar to a rail by itself on tablet widths, take a banner above the
header, remember the reader's layout, let the reader resize the sidebar, keep a bar of actions at the
bottom, and show the header's shadow once the content has scrolled. On this page the live examples sit in a framed box 36rem tall, which is wider than a
phone; open a story from the sidebar on its own and narrow the window to see the phone layout.

### Import

```tsx
import { AppShell, Navbar, Sidebar, useAppShell } from "@dbm-system/components";
```

## Usage guidelines

<div className="dbm-do-dont-grid">
<Callout tone="success" title="Do">

- Put `AppShell.SkipLink` (if you use it) and `AppShell.Header` first in the markup. The shell places
  each slot in its own area, so the order does not change the layout, but it is the keyboard's tab
  order: a skip link and a header first make the skip link the first stop and the sidebar's links come
  after it.
- Use `Navbar.SkipLink` inside a `Navbar`, and `AppShell.SkipLink` when the header is not a `Navbar`.
  Both link to `#main`, which is `AppShell.Main`'s `id`.
- Name the aside with `aria-label` when the page has another complementary landmark ("Details", "On
  this page"); the name is also the drawer's title.
- Set the sidebar's own `side` to match `sidebarSide`, so its line and its phone panel are on the
  same edge. On a right-to-left page give the shell its `dir` and the page's `lang`: the shell provides `dir` to the `Sidebar` and
  the `Navbar` inside, so neither needs one of its own, and `lang` picks the fonts and how a screen reader speaks the text.
- Keep a wide table or a long code block inside `AppShell.Main` in a component that scrolls on its
  own (`Table`, `CodeBlock`); the main area scrolls vertically and never pushes the frame wider than
  the window.
- Pass `pageKey` (the router's pathname) and `pageTitle` so a screen-reader user and a keyboard user
  are told about a page change that no browser navigation announces.
- Leave `width` off a `Sidebar` inside a `resizable` `AppShell.Sidebar`: the shell sets the width, and a
  `width` of its own would win (a development warning says so).
- Use a `sticky` footer for a few actions that must stay in reach (Save and Cancel), not for a footer of
  links.

</Callout>
<Callout tone="danger" title="Don't">

- Don't use `AppShell` for a page with no navigation column or header of its own; a plain
  [`Container`](/docs/atoms-layout-container--docs) with `as="main"` is the page there.
- Don't put a second `<main>` inside it, and don't wrap a `Navbar` in `AppShell.Header as="header"`:
  a `Navbar` draws its own `<header>`, and the two would nest.
- Don't wrap the shell in an element with its own height: with `scroll="content"` it already fits
  the window, and a parent shorter than that clips it.
- Don't keep a tall banner `sticky` on a phone: it takes screen height permanently. A short notice, or
  one that scrolls away, is kinder.
- Don't put important content only in an aside that is `hidden` on a phone: use the default drawer so
  a phone can still reach it.
- Don't put an `AppShell` inside another `Sidebar.Provider` and expect the outer one to drive its
  sidebar. The shell renders its own provider, which replaces the outer one for everything inside it.
- Don't pass `collapsed`, `menuOpen` or their change handlers to the `Sidebar` itself. The shell's
  provider holds that state and the sidebar ignores the ones set on it, with a development warning.

</Callout>
</div>

## Best practices

- Printing prints the page, not the navigation: the sidebar, the aside and the skip link are left out, the main area is laid out
  in full and the banner, header and footer are ordinary rows. Put your own page breaks and a table's
  repeating header in the page's own CSS.
- A very large static table (thousands of cells) in the main area makes the sidebar's rail and resize animation drop frames: measured with
  3,000 cells the slowest frame was about 25ms, and with 10,000 it reached 50 to 85ms. Use [`DataTable`](/docs/organisms-data-display-datatable--docs),
  which draws only the rows in view, for a table that long.
- Choose `scroll="content"` for an application whose pages are long lists or tables, so the
  navigation is always in reach. Choose `scroll="page"` for a page that reads like a document: the
  page scrolls as a whole, and the shell keeps the header and the sidebar in view as it does.
- Choose `headerSpan="full"` when the header carries the product's brand and global actions and the
  sidebar belongs to the page below it; keep the default when the sidebar is the product's spine and
  the header belongs to the content.
- Put the collapse button (`Sidebar.Toggle`) in the sidebar's footer and the phone menu button
  (`Sidebar.MenuButton`) in the header: the shell's provider connects them to the same sidebar.
  `AppShell.AsideToggle` goes in the header the same way, and shows only below the aside's collapse
  width.
- Let the page set its own padding and maximum width inside `AppShell.Main`; the shell adds none, so
  a full-bleed table or a centred reading column are both possible.
- Give each `Sidebar.Nav` and each `Navbar.Links` its own name when there is more than one, so the
  navigation landmarks are told apart.
- Set the width of the sidebar on the `Sidebar` itself: `width` for the column on the page, and
  `panelWidth` for the drawer it becomes on a phone, if it should differ (`<Sidebar width="16rem"
  panelWidth="20rem">`). The aside's width is its own `width` prop, or the `app-shell.aside-width`
  token. Neither drawer is ever wider than the window less a sliver of the page that stays showing.
- Use `railBelow` when the sidebar's labels would crowd a tablet: below the step the shell collapses it
  to a rail and the reader can still open it. Pick a step wider than the sidebar's own `collapseBelow`,
  or the rail never shows.
- Use `persistKey` (or the controlled `collapsed` and `sidebarWidth` props, to store the layout in a user
  profile) so a reader's layout survives a reload.
- Put the page in `AppShell.Content` when it should be a readable column; leave it out for a full-bleed
  table or a dashboard that fills the area.
- Read `useAppShell()` for anything that must know the shell's state, such as a bar that sticks below
  the header, rather than measuring the header yourself.

## Accessibility

<Callout tone="info" title="Who provides which landmark">

The shell supplies `AppShell.Main` (the one `main`) and `AppShell.Footer` (the `contentinfo`) and
`AppShell.Aside` (a `complementary`, named by you). The banner `<header>` comes from the `Navbar` in
the header slot, or from `AppShell.Header as="header"` for a header built without one; each
`Sidebar.Nav` is a named `navigation`. All of them are real elements, not roles on divs. The shell's
own header slot is a plain `div` by default so that a `Navbar` is never wrapped in a second banner.

</Callout>

| Key | Behaviour |
|---|---|
| `Tab` | Moves through the skip link and the header first, then the sidebar, then the main area's content, then the aside, in markup order. |
| `Enter` on a skip link | Moves focus to `AppShell.Main`, past the header and the sidebar. |
| `Escape` in the aside's drawer | Closes it and returns focus to `AppShell.AsideToggle`. |

- `AppShell.Main` takes focus from the skip link (`tabindex="-1"`). While it scrolls
  (`scroll="content"` and more content than room) it is also a tab stop, so a keyboard user can scroll
  a page that has nothing focusable in it with the arrow and page keys; a page that fits, or one that
  scrolls as a whole, gets no extra stop. Whenever the keyboard has focused it, a focus ring is drawn
  just inside its edge. A scrolling aside follows the same rule.
- Below the `collapseBelow` width the sidebar's links are in a dialog opened from the menu button, and
  below `asideCollapseBelow` the aside's content is in one opened from the toggle, with the focus
  handling `Drawer` provides. The toggle is a button with `aria-haspopup="dialog"` and `aria-expanded`.
  The drawer's copy is not a second complementary landmark.
- When `pageKey` changes, focus moves to `AppShell.Main` and, with `pageTitle`, the new title is
  announced politely. Neither happens on the first render, so the page's own load is not announced
  twice, and nothing happens while `pageKey` is left out.
- While `busy` is set the main area has `aria-busy="true"` and a polite status region says "Loading"; when it
  clears the region empties, so nothing more is read out. The bar is decoration and hidden from assistive
  technology. An `error` state is announced at once (a polite status region); an `empty` one is not, because it is
  the page's expected content. A state's title is the page's `h1`.
- The shell keeps its layers in a fixed order, so a bar of your own never paints over it:

  | Layer | Above it | Parts |
  |---|---|---|
  | Content | – | The page's own sticky elements, such as `Affix` (the `sticky` step) |
  | Sidebar, aside, footer | Content | One step up |
  | Header | Sidebar, aside, footer | Two steps up |
  | Banner | Header | Three steps up |
  | Skip link | Everything in the shell | The `fixed` step |

  Menus, tooltips and dialogs sit on the steps above all of these.
- The resize handle is a `separator` (`aria-orientation="vertical"`) that takes focus and reports its
  width and its bounds (`aria-valuenow`, `aria-valuemin`, `aria-valuemax`). The arrow keys move it (Shift
  moves it four times as far, Home and End go to the least and the most), so a keyboard user can resize
  without a pointer. It is not drawn while the sidebar is a rail or in its phone panel.
- The scrolled-edge cue (a shadow under the header, a line over the footer) is not the only way to tell
  that a page scrolls, and forced colours, which drop shadows, get a line instead. Motion on it respects
  `prefers-reduced-motion`.
- The banner is not a landmark: put a role or an `aria-label` on it only if it is important enough to be
  navigated to, and an `Alert` inside it already speaks for itself.
- A notch or a home indicator never covers the shell: the frame leaves a device's safe-area inset clear
  on every side (zero on a page that does not draw under them), and the skip link is drawn below it.
- The shell adds no colour pairing of its own: the page background is the surface colour, and text
  inside uses the primary text colour (at least 4.5:1 on it in every theme).
- With `scroll="page"` the header, the sidebar and the aside stay in view as the page scrolls. The
  shell measures the header's height once it is on the page, so on the server and for the first paint
  the header is an ordinary first row and scrolls away; it sticks from then on.

```tsx
// With a router: the router's pathname is the page's key, its link is the item, and the sidebar closes its phone panel when an item is pressed
function Frame({ children }: { children: ReactNode }) {
  const { pathname } = useLocation(); // from your router
  return (
    <AppShell pageKey={pathname} pageTitle={titleFor(pathname)}>
      <AppShell.Sidebar>
        <Sidebar>
          <Sidebar.Content>
            <Sidebar.Nav aria-label="Main">
              <Sidebar.Item asChild current={pathname === "/billing"}>
                <RouterLink to="/billing">Billing</RouterLink>
              </Sidebar.Item>
            </Sidebar.Nav>
          </Sidebar.Content>
        </Sidebar>
      </AppShell.Sidebar>
      <AppShell.Main>{children}</AppShell.Main>
    </AppShell>
  );
}
```

On a page change the shell moves focus to the main area, scrolls it to the top and announces `pageTitle` politely. It does nothing on
the first render, so the page's own load is not announced twice. The phone panel closes by itself when an item is pressed, including a
router's link that stops the browser's own navigation (`closeMenuOnNavigate` on `Sidebar`, on by default); turn it off there if a link
should keep the panel open.
