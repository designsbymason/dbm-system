# Responsive and right-to-left

There is no responsive mode and no right-to-left mode. Every component works across the whole
breakpoint scale and in both text directions from the start. This page covers how to use that in your
own layouts, and the places where direction is still passed by hand.

## Breakpoints

The scale is mobile first: a value applies from its breakpoint **up**, and `base` is everything below
the first breakpoint.

<ReferenceTable
  columns={["Breakpoint", "Starts at", "Typical use"]}
  rows={[
    ["base", "0", "Phones"],
    ["sm", "640px", "Small tablets, large phones in landscape"],
    ["md", "768px", "Tablets"],
    ["lg", "1024px", "Small laptops"],
    ["xl", "1280px", "Standard desktop"],
    ["2xl", "1536px", "Large desktop"],
    ["3xl", "1920px", "Large external monitors"],
  ]}
/>

Type and spacing are fluid between breakpoints (`clamp()`-based tokens), so most text and gaps resize
smoothly without a breakpoint at all.

## Responsive props

A prop typed `Responsive<T>` takes either one value or a map keyed by breakpoint. A map only needs the
breakpoints where the value changes.

```tsx
import { Stack } from "@dbm-system/components";

{/* A column on a phone, a row from md up, with a bigger gap on desktop */}
<Stack direction={{ base: "column", md: "row" }} gap={{ base: 2, lg: 6 }}>
  <Sidebar />
  <Content />
</Stack>
```

The phone presentation props are the ones that change a component's whole shape. A `Menu` can be a floating
menu or a **sheet** across the bottom of the screen with larger rows, a `Combobox` or `DatePicker` can open
under its field or across the whole visible screen, and a `Dialog` or `CommandPalette` can fill the screen.
Pass a map to choose per breakpoint, for example `fullScreen={{ base: true, sm: false }}`. Check a
component's Properties table for the props typed `Responsive`.

## Right-to-left

Directional CSS in the components uses **logical properties** (`margin-inline-start`,
`inset-inline-end`, `padding-block`) instead of left and right, so a layout mirrors when the document
direction is `rtl`. Do the same in your own CSS.

```css
/* Mirrors automatically in right-to-left */
.panel { padding-inline: var(--dbm-space-4); border-inline-start: 1px solid var(--dbm-border-default); }
```

- **Mirroring is a per-component judgment.** Most things mirror (arrows, a sidebar's edge, an
  alignment). Some do not, because what they show is not directional: a badge's anchor position, a
  number, the segments of a date field, which are always drawn left to right.
- **Icons with a direction** do not mirror by themselves. Set the `Icon` atom's `mirrored` prop on an
  arrow or chevron whose meaning should follow reading order.
- **Text a component supplies** comes from one optional `labels` object, and any number it shows goes
  through an optional `formatNumber`. Pass translated strings and a locale-aware formatter there.
  Components do not bundle translations.

## Direction: `DirectionProvider` and the `dir` prop

Components that behave differently in right-to-left take an explicit `dir?: "ltr" | "rtl"`. It decides which
side things sit on and which arrow key moves forward. Wrap your app once in `DirectionProvider` and every one
of them, and every overlay that opens in a portal (`Dialog`, `Popover`, `Tooltip` and the rest), follows it.
A `dir` on a component itself still wins. Nothing is read from the page: reading it needs JavaScript and can
flash left-to-right on a server-rendered page, so the app says which way it reads.

<ReferenceTable
  columns={["Behaviour", "Components"]}
  rows={[
    ["Reads the nearest `DirectionProvider`, else left-to-right", "Every component that takes a `dir` (`Tabs`, `Slider`, `Menu`, `Select`, `Calendar`, `Sidebar`, `AppShell`, `DataTable` and the rest), and the overlays without one: `Dialog`, `Drawer`, `AlertDialog`, `ConfirmDialog`, `Popover`, `Tooltip`, `HoverCard`"],
    ["Native `dir` attribute: the provider's when there is one, else inherited from the page", "`Alert`, `Breadcrumb`, and the field of `ColorPicker`, `DatePicker` and `DateRangePicker`"],
  ]}
/>

```tsx
<DirectionProvider dir="rtl">
  <Tabs defaultValue="overview">{/* … */}</Tabs>
</DirectionProvider>
```

The provider carries a value; it draws no element and sets neither `dir` nor `lang` on the page. Set those on
the root element too (`<html lang="ar" dir="rtl">`), or use `AppShell`, which sets `dir` on its own frame.
Content you portal yourself with the `Portal` atom is outside the provider's reach: give it a `dir`, or read
the provider's with `useDirection()`.

Components that only draw layout and text, such as `Stack`, `Card` and `Text`, need no prop: they follow the
page's direction through CSS.

## Usage guidelines

<div className="dbm-do-dont-grid">
<Callout tone="success" title="Do">

- Design the phone layout first and add to it at each breakpoint.
- Reference the `breakpoint.*` tokens, or a component's responsive prop, for a change in layout.
- Check the real width with the viewport toolbar in Storybook, not only the narrowest and widest.
- Write your own CSS with logical properties (`inline`, `block`, `start`, `end`).
- Wrap a right-to-left app in `DirectionProvider`, set `dir` and `lang` on the page, and pass `mirrored` to a
  directional icon.
- Test a right-to-left page in a real browser, with long text and the keyboard.

</Callout>
<Callout tone="danger" title="Don't">

- Don't hardcode a pixel width in a media query.
- Don't hide a control at a narrow width without a way to reach what it did.
- Don't assume a hover. A phone has none, so anything that appears on hover needs a tap or focus path.
- Don't use `left`, `right`, `margin-left` or `padding-right` in new CSS.
- Don't rely on the page's `dir` alone to flip a component that takes a `dir`: wrap the app in `DirectionProvider`.
- Don't mirror an icon that is not directional, such as a clock or a check.

</Callout>
</div>
