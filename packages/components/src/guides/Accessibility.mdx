# Accessibility

Accessibility is not a variant or a mode in DBM. The system targets **WCAG 2.2 AA**. This page says what
the components guarantee, the known places where a measured value falls short of that target, how it is
checked, and what stays your responsibility when you compose components into a page. Each component's
review file records what was checked and what was not, and is the authority for that component.

## What every component guarantees

These come from the checklist a component passes before it is Finalized. They hold except where
**Known exceptions** below says otherwise.

- **Contrast.** Text is designed to meet **4.5:1**, and non-text elements that identify a control or its
  state (icons, borders, focus rings) to meet **3:1**, in all four themes. Each pairing is measured, not
  eyeballed, and the exceptions are listed below. Error and critical-alert text aims higher, for **AAA
  (7:1)**. A disabled control is exempt, as WCAG allows.
- **Keyboard.** Every interaction works from the keyboard, with the focus model the pattern calls
  for: a roving tab stop in toolbars, tabs and trees, a single tab stop with arrow keys in radio
  groups and menus, `Escape` to close, and focus returned to where it came from.
- **Focus you can see.** A focus ring appears for keyboard focus (`:focus-visible`) and not for a
  mouse press, and meets the non-text contrast floor.
- **Focus that stays put.** A modal dialog or drawer holds focus inside it and gives it back when it
  closes. A responsive change never removes the control that has keyboard focus, so a person does not
  lose their place when the layout changes under them.
- **Names, roles and states.** Interactive parts have an accessible name, and state (expanded,
  selected, invalid, busy) is exposed through ARIA that matches the element's real role. Relationships
  between parts, such as a field's label, hint and error, are wired by id for you. An icon-only button
  requires an `aria-label` in its types.
- **Names that match what you see.** A control's accessible name contains its visible text as whole
  words, in order (WCAG 2.5.3, Label in Name), so a person who says "Delete" to a voice-control tool
  reaches the button that shows "Delete".
- **Announcements.** Components whose content changes on its own, such as `Pagination`, `Toast` and
  `Stepper`, announce the change through a live region that is already on the page before its text
  changes, so a screen reader hears it once and not on first appearance.
- **Target size.** Every interactive target is at least **24 × 24 CSS pixels**, at every size step.
  Where a control must look smaller, only its hit area is extended.
- **Motion.** Looping animation (spinners, skeleton pulses) respects `prefers-reduced-motion`:
  a spinner slows down rather than freezing, and a placeholder pulse stops.
- **Forced colours.** Components are checked with `forced-colors: active` emulated in a real browser
  (the mode Windows high contrast turns on), so borders and indicators that rely on colour alone
  still show. A real Windows machine is listed as not verified in the reviews.
- **Responsive and right-to-left.** Components work across the whole breakpoint scale, with no
  control lost at a narrow width and directional CSS written with logical properties. See the
  [responsive and right-to-left guide](?path=/docs/guides-responsive-and-right-to-left--docs).

## Known exceptions

These are measured values that fall below the target, as recorded in the token spec. Some are accepted
positions, for example that a decorative border does not identify a control, which a strict reading of
WCAG 1.4.11 could dispute. They are listed so you can judge them for your own product.

If your own controls must meet 1.4.11 strictly, `border.neutral-strong` clears 3:1 (4.70:1 light, 6.08:1
dark) and is the border to use for a boundary that identifies a control.

Each Finalized component's review lists what was checked and, under "Not verified", what was not.
Typical gaps are a real screen reader, Safari and Firefox, a real phone, and Windows high contrast on a
real machine. A guarantee above is a checklist item a component passed, so for one component, read its
review.

<Callout tone="info" title="Automated checks are the floor">

Axe finds roughly the mechanical failures. It cannot tell whether a heading order makes sense,
whether a focus move is surprising, or whether a screen reader reads a page well. Treat a clean axe
run as the start of checking your own page, not the end.

</Callout>

## What stays your job

Components cannot know your page. When you compose them:

  plainFirstColumn
  columns={["Area", "What to do"]}

    ["Colour", "Never the only signal. If you mark state with colour, add text, an icon or a shape."],

    ["Real content", "Long names, 200% zoom and a translated string reach places a demo does not."],

## Usage guidelines

<div className="dbm-do-dont-grid">
<Callout tone="success" title="Do">

- Pass a visible label to every field through `FormField`, and wire errors with `FieldError`.
- Give every icon-only button an `aria-label`.
- Use the component's own `labels` prop to supply translated text for its built-in strings.
- Keep the visible text inside a control's accessible name if you override it.
- Test the finished page with the keyboard alone, then with a screen reader.
- Check a new colour pairing in all four themes before you ship it.

</Callout>
<Callout tone="danger" title="Don't">

- Don't remove or override a focus ring. Restyle it with tokens if you must.
- Don't rely on placeholder text as a label.
- Don't make a `div` clickable. Use `Button` or `Link` so the role, keyboard and focus come with it.
- Don't put `text.tertiary` text on `bg.canvas`: it falls below 4.5:1 in both modes.
- Don't remove a control that has focus when something changes, or move focus without a reason.
- Don't read a clean axe run as "accessible". It is the floor.

</Callout>
</div>
