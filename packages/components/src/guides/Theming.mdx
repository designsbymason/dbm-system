# Theming

DBM ships two brands, **Purple** and **Emerald**, each in a **light** and a **dark** mode: four themes
in all. A component is written once against token names such as `bg.brand` and never knows which
theme is active, so changing the brand or the mode never touches component code. Use the **Brand**
and **Mode** controls at the top of this page to switch the theme you are reading in.

## How it works

Components read **semantic tokens**, which are CSS custom properties named `--dbm-<family>-<name>`. Each
theme's stylesheet gives those properties their values, scoped to a `data-theme` attribute on the
document element, so switching the attribute switches every component at once.

The **brand** decides the brand slots (`bg.brand`, `text.brand`, `icon.brand`, `border.focus` and their
relatives). Status colours (success, warning, danger, info) are the same in both brands, so success is
always green. The **mode** decides the surfaces and the text on them. See the
[colour reference](?path=/docs/foundations-color--docs) for every token.

## Applying a theme

Wrap the app in `ThemeProvider`. It sets `data-theme` on the document element (for example
`data-theme="purple-light"`), which is what the token stylesheets are scoped to.

```tsx
import { ThemeProvider } from "@dbm-system/components";

export function App() {
  return (
    <ThemeProvider brand="emerald" mode="system">
      {/* the rest of the app */}
    </ThemeProvider>
  );
}
```

      defaultValue: "system",
    },

/>

- **The theme is document-wide**, not scoped to the provider's own element. A dialog, tooltip or
  toast that mounts on `document.body` therefore picks it up too. It also means a page shows **one
  theme at a time**: there is no way to theme one section differently.
- **Providers nest, but do not scope.** An inner provider takes over the document's theme while it is
  mounted and hands it back to the outer one when it unmounts.
- **Changing the brand or mode after the first render fades** the themed colours over
  `motion.duration.base`, and is skipped under `prefers-reduced-motion: reduce`. The first paint
  never fades in.
- **The choice is not remembered.** The provider does not store it. Keep a person's preference in your
  own state, and in storage if it should survive a reload.

To let a person switch, hold the choice in state and pass it down:

```tsx
function App() {
  const [mode, setMode] = useState<"light" | "dark" | "system">("system");
  return (
    <ThemeProvider brand="purple" mode={mode}>
      <Button onClick={() => setMode(mode === "dark" ? "light" : "dark")}>Toggle mode</Button>
    </ThemeProvider>
  );
}
```

## Reading the theme

`useTheme()` returns the brand, the `mode` as it was passed, and the `resolvedMode`: the concrete
`"light"` or `"dark"` that `"system"` currently means. It throws outside a `ThemeProvider`. Use it to
show the current choice or to pick an image, not to choose a colour.

```tsx
import { useTheme } from "@dbm-system/components";

function ModeLabel() {
  const { brand, resolvedMode } = useTheme();
  return <span>{brand} / {resolvedMode}</span>;
}
```

<Callout tone="info" title="System mode on a server-rendered page">

`mode="system"` always renders **light** on the first render, so the server's HTML and the browser's
first render agree, and corrects to the real preference just after mount and before the browser
paints. On a server-rendered page the very first paint can show light for a moment. Avoiding that
entirely needs a small blocking script ahead of hydration, which is outside what a component can do.
Pass an explicit `mode` if that flash matters.

</Callout>

## The stylesheets

The tokens are plain CSS custom properties in `@dbm-system/tokens`. A theme needs the shared files
and one file per theme in use:

This Storybook imports all of them. A consuming app loads the ones for the themes it offers. The token
package names the `Nunito` and `Lora` font families but ships no font files, so load them yourself. How
a consumer loads these files is not settled yet; this page will link to the Installation page when it
exists.

## Usage guidelines

<div className="dbm-do-dont-grid">
<Callout tone="success" title="Do">

- Reference a **semantic** token in your own CSS: `var(--dbm-bg-brand)`, `var(--dbm-text-primary)`.
- Let a component's own props choose its colour (`tone`, `variant`) rather than styling it from
  outside.
- Check a new colour pairing in **all four themes**, not only the one you are looking at.
- Keep the person's brand and mode choice in your own state or storage, and pass it to `ThemeProvider`.
- Pass an explicit `mode` on a server-rendered page if a first-paint flash of light would matter.

</Callout>
<Callout tone="danger" title="Don't">

- Don't reference a primitive such as `color.purple.600` directly. It does not change with the
  theme, so the page breaks in the other brand and in dark mode.
- Don't hardcode a hex value, even one that matches a token today.
- Don't branch on the theme in JavaScript to pick a colour. Pick a token and let the CSS resolve it.
- Don't expect to theme one section differently from the rest of the page. The theme is document-wide.
- Don't assume the provider remembers a choice across reloads.

</Callout>
</div>

## Adding another brand

The architecture allows a third brand, but none is built until a concrete need exists. It would take a
new primitive colour scale, one semantic token file per mode (the same keys as the existing ones), a
rebuild of the token CSS, a new value for the `brand` type, and a contrast check of every pairing in
both modes. No component changes.
