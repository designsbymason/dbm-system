<VisuallyHidden asChild><h2>Intro</h2></VisuallyHidden>

<ComponentHeader title="FileUpload" tier="Organism" />

A field for choosing files. A person drags files onto the drop area, presses its button, or pastes, and the files
appear in a list with their name, their size and, as you report it, how far along they are. It is a compound
component, meaning it is made of named sub-parts you can compose: with no children it draws `FileUpload.Dropzone`
(or `FileUpload.Trigger` for `layout="button"`), `FileUpload.Rejections` and `FileUpload.List`, and you can put
those parts in your own order.

**It sends nothing.** Choosing a file adds it to a list; sending it is yours. You start the request, and write each
entry's `status` and `progress` back into `value` as it goes, and the field shows them and asks for removal and
retry through callbacks. That keeps the field free of any assumption about your backend, and makes the progress it
shows always the truth you gave it.

Files are checked against `accept`, `maxSize`, `minSize`, `maxFiles` and your own `validate` rule whether they were
chosen, dropped or pasted. A refused file never enters the list; it is explained in words, beside the field, with its
name. The field also submits with its form: it carries a real file input, so `name`, `required` and a surrounding
`<form>` work, and it sits inside a `FormField`.

### Import

```tsx
import { FileUpload } from "@dbm-system/components";
```

## Properties

`ref` forwards to the outer group `<div>`, and `id` goes to the file input (see Accessibility). Also accepts any other
native `<div>` attribute beyond what's listed here (e.g. `onMouseEnter`, `title`) — passed straight through to the outer
group.

<PropertiesTable of={FileUploadStories} order={rootPropOrder} />

### Entries

`value`, `defaultValue` and `onValueChange` hold a list of entries. An entry is `{ id, file, status?, progress?,
error? }`: `id` is its stable identity; `file` is the `File`; `status` is `"idle"` (the default), `"uploading"`,
`"done"` or `"error"`; `progress` is 0 to 100 for an uploading file (leave it out for an indeterminate bar); and
`error` is the text shown for a failed one in place of "Upload failed".

### FileUpload.Dropzone properties

The drop area: a dashed box that takes files dropped on it, files pasted while it has focus, and a click, and holds the
button that is the keyboard's way in. Only dragged files count, never text or links. Also accepts any other native
`<div>` attribute beyond what's listed here (e.g. `onMouseEnter`, `title`) — passed straight through.

<PropertiesTable of={FileUploadDropzoneStories} order={dropzonePropOrder} />

### FileUpload.Trigger properties

The button that opens the file picker. Inside `FileUpload.Dropzone` it is the keyboard's way in; on its own it is the
whole field for `layout="button"`. It takes the `Button` atom's own props (`tone`, `isLoading`, …) beyond what's
listed here.

<PropertiesTable of={FileUploadTriggerStories} order={triggerPropOrder} />

### FileUpload.Rejections properties

The messages for files that were refused, drawn as errors and read out as they appear. They stay until the next files
are chosen or an entry is removed. Renders nothing when there are none. Also accepts any other native `<ul>`
attribute beyond what's listed here (e.g. `title`, `lang`) — passed straight through.

<PropertiesTable of={FileUploadRejectionsStories} order={rejectionsPropOrder} />

### FileUpload.Summary properties

One line above the list once a file has started: how many are sent of how many, and how many failed. Plain text, not a
live region (each file's own change is announced as it happens). Renders nothing while every file is still waiting.
Also accepts any other native `<p>` attribute beyond what's listed here (e.g. `title`, `lang`) — passed straight through.

<PropertiesTable of={FileUploadSummaryStories} order={rejectionsPropOrder} />

### FileUpload.List properties

The list of chosen files, one `FileUpload.Item` each (or whatever your function draws). Renders nothing while it is
empty. Also accepts any other native `<ul>` attribute beyond what's listed here (e.g. `title`, `lang`) — passed
straight through.

<PropertiesTable of={FileUploadListStories} order={listPropOrder} />

### FileUpload.Item properties

One chosen file: an icon for its kind, its name and size, where it has got to, and its remove button (and retry
button, for a failed entry when `onRetry` is set). Also accepts any other native `<li>` attribute beyond what's listed
here (e.g. `title`, `lang`) — passed straight through.

### All looks

The drop area is dashed, outlined, filled or ghost (no fill and no edge until files are dragged over it). Every look
draws a brand edge during a drag and the error edge when `hasError` is set, so a state is never lost to the look. The

the area is.

A dropped folder is refused with a message ("Photos is a folder; choose files instead") unless `allowFolders` is set;

## Usage guidelines

<div className="dbm-do-dont-grid">
<Callout tone="success" title="Do">

- Use `FileUpload` wherever a person hands the app files: attachments, a profile picture, an import. Use
  `layout="button"` in a toolbar, a comment box or a table row, where a large drop area would be too much.
- Say what is accepted. The hint under the button is written from `accept`, `maxSize` and `maxFiles` for you; write
  your own with `hint` when the rule is not a type or a size.
- Set `accept`, `maxSize` and `maxFiles` to what the server will take, so a person finds out before the request, not
  after it.
- Write each entry's `status` and `progress` as the file is sent, and its `error` when it fails, so the list tells the
  truth. Offer `onRetry` for failures a second try can fix.
- Use `showSummary` (on by default) to keep a count in view once files are being sent; turn it off when the page shows
  progress some other way, or draw `FileUpload.Summary` yourself where you want it.
- Turn on `allowFolders` for a field that imports a whole tree (a set of documents, a project). Leave it off for a field
  that wants named files, so a folder is turned away in words.
- Use `showPreviews` for photos, avatars and screenshots, where seeing the picture is how a person checks they chose the
  right file.
- Pass `onCancel` when a request can be stopped: an uploading file's button becomes "cancel" and asks you to abort it.
  Decide what the entry becomes afterwards (remove it, or set it back to `"idle"` or to `"error"`).
- Give the accepted types readable names with `acceptLabels` when the automatic ones don't say enough (a `.docx`
  becomes "Word documents"); they are used in the hint and in the message for a refused type.
- Put the field in a `FormField` inside a `Form` when it is part of a form: the label, the helper text, the error and
  `required` are then wired for you.
- Use `multiple={false}` for a field that holds one file (a profile picture): a new file replaces the old one instead
  of being refused.
- Give it a name: `aria-label`, or a `FormField` label. The group of controls is read out by that name.

</Callout>
<Callout tone="danger" title="Don't">

- Don't expect the field to upload. It never makes a request, and its progress is only what you write.
- Don't rely on the browser's own filter for `accept`: it does not see dropped or pasted files, which is why the field
  checks every file itself. Check again on the server, since none of this is a security boundary.
- Don't hide the button and leave only a drop area. Dragging is not possible for everyone; the button is the way in for
  a keyboard, a screen reader and a phone.
- Don't use the field to show files that cannot be changed and have nothing to add: `readOnly` is for that, and a plain
  list of links is often better.
- Don't put the label's text only in the drop area's prompt. The field needs its own name (`aria-label` or a
  `FormField` label).
- Don't turn on `allowFolders` and then expect a limit on how many folders were dropped: the files are counted, and one
  drop reads at most 5,000 of them.
- Don't use `showPreviews` for large lists of big images: each preview is decoded from the original file in the
  browser. Keep it to the images a person is choosing between.
- Don't set `allowDuplicates` just to silence the "already added" message: two copies of the same file are almost
  always a mistake, and the message says which one.
- Don't draw the field with children and leave out `FileUpload.Trigger`: a keyboard or screen-reader user then has no
  way to add a file, and the field warns in development.
- Don't combine `maxFiles` with `multiple={false}`: a single-file field holds one, and the field warns in development.
- Don't turn on `guardPage` in more than one place on a page, or use it as a general drop handler: it only stops the
  browser opening a stray file.

</Callout>
</div>

## Best practices

- Treat the list as yours. `value` is the single source of truth for what is shown, and the file input the form
  submits is rebuilt from it after every change, so what you see is what is sent.
- Start sending when files are added (`onFilesAdded`) or when a form is submitted; both work. For a form that sends
  files with the rest of its fields, leave status alone and let the form submit them.
- Keep `validate` quick and put the reason in words ("Remove the spaces from the name"): the message is shown with the
  file's name. A rule that returns a promise (reading the file's header, say) is waited for before anything is added.
- Show progress as a number when you can measure it and leave `progress` out when you cannot: the bar is then
  indeterminate and the text says "Uploading…".
- Sizes are written in bytes, in steps of 1024, with at most one decimal (`1.5 KB`). Pass `formatSize` for another
  convention, and `formatNumber` to write the digits in another script.
- On a phone there is no dragging, so the whole area is a tap target and the button is full size; long file names are
  cut with an ellipsis and the remove button stays in view.
- Use `size` to match the field to the form around it: `sm` in a dense form, `lg` for an area that is the point of the
  page.
- For a drop zone that is the whole page (a document workspace), turn on `guardPage` once so a file dropped just
  outside the area does not navigate away.

## Accessibility

<Callout tone="info" title="A named group, a real button and a real file input">

- The field is a `role="group"` named by `aria-label` or `aria-labelledby` (a `FormField` sets the latter). Inside it
  are ordinary controls: a button, a list, and per-file buttons. Nothing about the drop area is required to use the
  field.
- **Keyboard.** `Tab` reaches the button; `Enter` or `Space` opens the file picker. Each file has a remove button (and a
  retry button for a failed one), reached in the normal tab order. Pasting while the button has focus adds the clipboard's
  files.
- **The drop area is a convenience for a pointer.** Dragging, dropping and clicking the area are mouse and touch
  affordances; the same action is always available through the button, so the area itself takes no role and no key
  handler.
- **The name is the visible text.** The button is named "Choose files" (or what you write), which is also what it shows.
  Remove and retry buttons show only an icon and are named with the file ("Remove report.pdf").
- **`id` goes to the file input, not the button.** A label that points at a button replaces the button's own text as its
  name, which would hide "Choose files" from a speech-recognition user. A label that points at the file input opens the
  picker when it is clicked, and a form that focuses its first invalid control lands there and is handed on to the
  button.
- **Delete removes a file.** With focus on one of a row's buttons, `Delete` or `Backspace` does what the row's main
  button does: cancels an upload that can be cancelled, and otherwise removes the file. Nothing else on the page hears it.
- **Cancel is its own button.** For an uploading file with `onCancel`, the button is named "Cancel uploading
  report.pdf", not "Remove". It is the same button in the same place, so focus stays on it when the upload ends and the
  name goes back to "Remove".
- **Messages are read out.** Files that are refused appear as errors (`role="alert"`), each naming the file and the rule.
  Files added, removed, finished and failed are announced through a status region that is in the page before it has
  anything to say, so a change is announced and a first appearance is not.
- **Status is never colour alone.** Each file's state is written ("Uploading… 40%", "Uploaded", the error text) and
  carries an icon; the progress bar has a name and a value.
- **Targets.** Every button is at least 24 × 24 pixels at every size.
- **Focus.** After a file is removed, focus goes to the next file's remove button, or to the button when none is left,
  unless the person has already moved elsewhere.
- **Contrast.** The drop area's dashed edge is `border.neutral-strong`, 4.70:1 on the surface in light mode and 6.08:1 in
  dark, above the 3:1 floor for a boundary that identifies where to drop. In forced colours the dashed edge stays, a
  drag draws it solid and an error draws it double.
- **Right-to-left.** Layout uses logical properties: the icon leads on the right, the actions sit on the left, and file
  names are laid out by their own direction.

</Callout>

| Key | What it does |
|---|---|
| `Tab` / `Shift+Tab` | Moves between the button and each file's remove (and retry) buttons |
| `Enter` / `Space` | On the button, opens the file picker; on a file's button, removes or retries |
| `Delete` / `Backspace` | On one of a file's buttons, removes the file (or cancels it, while it uploads and `onCancel` is set) |
| `Ctrl/Cmd+V` | With the button focused, adds the files on the clipboard |

## Code examples

```tsx
import { useEffect, useRef, useState } from "react";
import type { FileUploadEntry } from "@dbm-system/components";

function Attachments() {
  const [files, setFiles] = useState<FileUploadEntry[]>([]);
  const requests = useRef(new Map<string, XMLHttpRequest>());
  const update = (id: string, patch: Partial<FileUploadEntry>) =>
    setFiles((current) => current.map((entry) => (entry.id === id ? { ...entry, ...patch } : entry)));

  // FileUpload sends nothing: you start the request and write what happens back into the list.
  const send = (entry: FileUploadEntry) => {
    update(entry.id, { status: "uploading", progress: 0, error: undefined });
    const request = new XMLHttpRequest();
    requests.current.set(entry.id, request);
    request.open("POST", "/api/attachments");
    request.upload.onprogress = (event) => update(entry.id, { progress: (event.loaded / event.total) * 100 });
    request.onload = () =>
      update(entry.id, request.status < 300 ? { status: "done", progress: 100 } : { status: "error", error: "The server refused it" });
    request.onerror = () => update(entry.id, { status: "error", error: "The connection was lost" });
    request.send(entry.file);
  };

  // A newly added file arrives as "idle"; sending it moves it on, so each is started once.
  useEffect(() => {
    files.filter((entry) => entry.status === "idle").forEach(send);
  }, [files]);

  return (
    <FileUpload
      aria-label="Attachments"
      accept="image/*,.pdf"
      maxSize={5 * 1024 * 1024}
      value={files}
      onValueChange={setFiles}
      onRetry={send}
      onCancel={(entry) => {
        requests.current.get(entry.id)?.abort();
        setFiles((current) => current.filter((item) => item.id !== entry.id));
      }}
    />
  );
}
```
