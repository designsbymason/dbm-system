<ComponentHeader title="Slider" tier="Molecule" />

A single-value slider built on Radix UI's Slider primitive, with a token-driven track, filled
range, and thumb. Accepts both controlled (`value`/`onValueChange`) and uncontrolled
(`defaultValue`) usage — as a plain number, not the array the underlying primitive uses internally
(that shape only matters once a slider has more than one thumb; for a range, use [`RangeSlider`](/docs/molecules-inputs-rangeslider--docs)). `onValueCommit` fires once, on
release, distinct from `onValueChange`'s continuous firing while dragging or stepping.

### Import

```tsx
import { Slider } from "@dbm-system/components";
```

### Right to left

`dir="rtl"` mirrors the slider for right-to-left languages: the minimum sits at the right, the filled range,
thumb and tick marks run from there, the arrow keys move the other way (`ArrowLeft` raises the value), and the
value and the min/max labels swap sides with them. It is passed through to the underlying Radix slider. It is not read from the page: with `dir` left out the slider
follows the nearest `DirectionProvider`, else left-to-right, so its parts always agree.

## Usage guidelines

<div className="dbm-do-dont-grid">
<Callout tone="success" title="Do">

- Use `Slider` to choose one value, and `RangeSlider` to choose a range between two — a price band, a
  date span — rather than two sliders that can cross each other.
- Reach for `onValueCommit` for anything expensive that should only run once the user settles on a
  value (a network request, an expensive filter) — `onValueChange` fires continuously while
  dragging and is the wrong hook for that.
- Pass `aria-label` (or `aria-labelledby`) — this component has no built-in visible-label slot of
  its own, so one of the two is required for the slider to be announced correctly.
- Set an explicit `height` via `style` whenever `orientation="vertical"` — a vertical slider has no
  intrinsic height, matching the underlying Radix primitive's own documented requirement. This
  still holds when `showMinMaxLabels` is also set: `style` always targets the same real element
  that ends up owning the explicit height, so nothing changes about where you set it.
- Use `showTicks`/`tickInterval` for a coarser set of marks than every single `step` — a small
  `step` on a wide range renders unreadably crowded ticks if `tickInterval` isn't set wider.

</Callout>
<Callout tone="danger" title="Don't">

- Don't drive `value` from a live control without a real `onValueChange` wired back — Radix always
  defers to the controlled value, which freezes the slider's own drag/keyboard handling.
- Don't reach for `onValueChange` as your only hook if the resulting action is expensive — pair it
  with `onValueCommit` instead, or you'll re-run that action on every pixel of drag movement.
- Don't assume the numeric value alone is enough context for assistive tech on a non-obvious scale
  (e.g. a 1–5 rating) — set `aria-valuetext` with a human-readable equivalent instead.
- Don't treat `showValueTooltip` as a substitute for `aria-valuetext` — the tooltip is a purely
  visual aid for sighted mouse/keyboard users; it doesn't change what's announced to assistive tech.

</Callout>
</div>

## Best practices

- Match `size` to the surrounding layout's density, same as `Input`'s own guidance.
- Keep `step` a "round" value relative to the value's own natural granularity — an oddly precise
  step is confusing to move through via the keyboard.
- Pair with `FieldHelperText` to state the valid range in plain language when `min`/`max` aren't
  self-evident from context (e.g. "Between 0 and 100").
- Turn on `showValue` when no other on-screen element already reflects the current value — it's a
  purely visual convenience for sighted users, since the value is already exposed to assistive tech
  via `aria-valuenow` regardless of whether it's shown.
- Reach for `showValueTooltip` instead of `showValue` when the value only matters *while*
  interacting (a color-mixer opacity slider, say) — it appears on hover/drag/focus and gets out of
  the way otherwise, rather than taking up permanent layout space.
- `showMinMaxLabels` and `FieldHelperText`'s own plain-language range statement aren't mutually
  exclusive — the labels anchor the two ends precisely; the helper text can still add context
  (units, what the value controls) the bare numbers don't carry.

## Accessibility

<Callout tone="info" title="Keyboard and ARIA state come from Radix's own slider primitive">

- Renders a `role="slider"` element (not a native `<input type="range">`) — `Tab` focuses it, and
  arrow keys (or Page Up/Down, Home/End) change the value, per the WAI-ARIA slider pattern.
- `aria-valuenow`/`aria-valuemin`/`aria-valuemax` reflect the real state directly, kept in sync with
  the visible thumb position automatically. `aria-valuetext`, when set, is announced instead of the
  raw number.
- `dir="rtl"` flips which arrow key moves which way (`ArrowLeft` raises the value) along with the layout, so the key that points toward the thumb's travel is always the one that moves it; Home and End still go to the minimum and maximum.
- `aria-invalid="true"` is set automatically while `hasError`, in addition to the visual danger
  ring and thumb outline — the two can't drift out of sync.
- A dev-mode console warning fires once if a `Slider` has no `aria-label` or `aria-labelledby` — a
  slider with no accessible name is invisible to screen reader users.
- A `disabled` slider is skipped by `Tab` entirely and ignores both pointer drag and keyboard
  input — not just visually dimmed while remaining reachable.
- `name` renders a hidden native input for real form submission when the slider sits inside an
  actual `<form>` (or `form` is set) — the same mechanism `Switch`'s own `name` documents, though
  Slider's hidden input carries no `type="range"` semantics of its own; it exists purely for
  form-data participation.
- The filled range (`bg.brand`) is checked against real WCAG contrast ratios. The unfilled track
  (`bg.track`) deliberately doesn't clear the 3:1 non-text floor — an accepted exception, since the
  thumb and filled range already carry the boundary/state information a user needs (see
  `03-token-system-spec.md`'s "Notable exceptions" and ADR-0016) — not an oversight.
- The thumb's pointer and touch target is at least 24 × 24px at every size (an invisible area around the smaller thumbs, so they are drawn at 12, 16 and 20px but grabbed like a 24px one), meeting WCAG 2.5.8.
- `showTicks`' tick marks, `showMinMaxLabels`' end labels, and `showValueTooltip`'s bubble are all
  purely visual — ticks are `aria-hidden`, and none of the three change what's announced to
  assistive tech, which already gets the real state via `aria-valuenow`/`aria-valuemin`/
  `aria-valuemax`/`aria-valuetext` regardless of what's visible on screen.
- With `formatNumber`, `aria-valuetext` becomes the formatted number (`٥٠`, `50%`), so what a sighted user reads
  and what a screen reader announces agree; `aria-valuenow` stays the plain number. An `aria-valuetext` you pass
  yourself takes precedence over the formatter in the value label, the tooltip and the announcement, and the min and
  max labels still use the formatter.
- `showValueTooltip` opens on hover, drag, or keyboard focus — covering both pointer and
  keyboard-only interaction, not just mouse hover.

</Callout>

## Code examples

```tsx
<Slider aria-label="Volume" defaultValue={50} />
<Slider aria-label="Brightness" value={value} onValueChange={setValue} min={0} max={10} />
<Slider aria-label="Price" onValueCommit={runExpensiveFilter} showValue />
<Slider aria-label="Opacity" orientation="vertical" style={{ height: "12rem" }} />
<Slider aria-label="Quality" defaultValue={2} min={1} max={3} aria-valuetext="Medium" />
<Slider aria-label="Volume" onFocus={() => trackFieldFocus("volume")} />
<Slider aria-label="Volume" showValueTooltip />
<Slider aria-label="Volume" showMinMaxLabels />
<Slider aria-label="Zoom" min={0} max={200} step={10} showTicks tickInterval={50} />
<Slider aria-label="Volume" showValue showMinMaxLabels formatNumber={new Intl.NumberFormat("ar-EG").format} />
<Slider aria-label="Opacity" step={5} showValue formatNumber={(value) => `${value}%`} />

{/* Composed inside a FormField for the label/helper-text wiring — see that
    component's own Docs page for the full pattern. */}
<FormField label="Volume" helperText="Between 0 and 100">
  {(fieldProps) => <Slider {...fieldProps} />}
</FormField>
```
