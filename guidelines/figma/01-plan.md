## 1. Goals

1. A Figma library that **mirrors the code**: the same tokens, the same themes, the same components, so a designer and an engineer describe one system.
2. **Tokens flow one way**, from `packages/tokens` into Figma by a script, so the two cannot drift (`../01-vision-and-goals.md` §3).
3. **Figma used as Figma is meant to be used**: variables with modes, styles, components with properties and slots, auto layout, constraints, no raw values.
4. A file that is itself **premium, professional and clean**: the design system's own look, built from its own library.
5. **No change to any published package.** Everything new is outside `packages/*`, in this folder, in `.local/` and in one private script.

Out of scope: templates, hooks, functions and non-visual utilities, Code Connect and right-to-left (deferred to a later phase), any change to `packages/*`.

## 4. Structure of the Figma file

**Page names and order:** the pages are in four groups, set apart by empty divider pages named `---`: the cover, Getting started, Foundations and Icons; Components with a category page under it, each named with a leading arrow (`↳ Inputs`); and the Spec frame with the Changelog after it. A page name starts with an emoji (or `↳` for a category) and then the plain name, and a script finds a page by the plain name, ignoring that prefix.

**Pages, in order:** Cover; Getting started (a Section of four frames: what the file is and where things are, how to use the modes with the same card shown in four themes and three viewports, how things are named in Figma and in code, and links to Storybook, the website, npm, GitHub and the agent file); Foundations (one page: an Overview frame, then a named Figma Section for each of Color, Typography, Spacing and Radius, Elevation, Motion and Breakpoints, stacked in that order, with that topic's frames side by side inside it and no frame taller than about 3,300 px: Color is six frames, Typography two, the rest one each); Icons (its own page); Spec frame (the master every component's spec frame is an instance of, with a filled example in light and dark); one page per category (Inputs, Data Display, Feedback, Layout, Media, Navigation, Overlay, Typography, Utility); Components (an overview of how components are structured, an index of every component drawn in Figma and a table of those that are not, each with its Storybook link; it replaces the separate Scope notes page, and is generated from the component catalog by `09-components-page.js`, so a component added or removed in code appears there or the script fails; which components are drawn is read from the file when the payload runs: a spec frame instance named `Spec: <Name>` on a category page marks one drawn, so no list is kept); Changelog (§7).

**The Components page index** links each name inside the file: to its spec frame once drawn, otherwise to its category page when that page exists (a planned component in a category with no page yet is plain text); a Storybook column links every row to its Docs page, and the Not drawn table links to Storybook only.

**The Spec frame master** is a component set named `.Spec frame` (the leading period keeps it out of a library publish) on its own page, with a `tier` variant (atom, molecule, organism), three text properties (Name, Description, Storybook label) and seven slots. Top to bottom the frame is the header, Variants, Properties, In code, not drawn and Tokens used (the last three as tables), then Anatomy, Built from and Accessibility side by side. The Properties slot lists the properties the component has in Figma (name, values, default, the code prop each maps to), then names the code props that are not modelled and links to the component's Props table in Storybook, which stays the full reference. The In code, not drawn section is a table of every value the code has and the file does not draw, each with the recipe for getting it ([ADR-0242](../adr/0242-a-component-set-draws-a-core-of-values-with-every-state-at-every-drawn-size-and-documents-the-rest-over-drawing-every-combination-of-every-value.md)). An instance sets the properties and puts its content into the slots; a dark twin is the same instance with its Semantic mode set to a dark theme.

**A category page** holds one Section per component, in build order (atoms, then molecules, then organisms), each filled with `bg/canvas` bound to the variable, like every Section in the file. A Section holds the component's **spec frame** above its component set and the set's "Matrix labels" frame, and the spec frame is an instance of a master component: a header (name, tier tag, one-line description, link to its Storybook page), the component set laid out as a variant matrix, an anatomy callout, the tokens it uses and its accessibility notes (§6). Props, usage and code stay in Storybook.

**Theme previews:** each spec frame appears in a light and a dark pair; brand switching is the page's explicit mode setting on the Semantic collection, so one page shows purple and, flipped, emerald.

**Layer and component names** follow the code: `Button`, `Button/Group`, `Card/Header`, properties named as the prop (`variant`, `size`, `tone`, `state`). A part of a compound component is its own nested component named `Parent/Part`.

## 5. Variables, styles and tokens

**Collections and modes**

| Collection | Modes | Holds |
|---|---|---|
| Primitives | one (`Value`) | 164 variables: colour scales, spacing, radius, border widths, opacity, icon sizes, breakpoint widths, font families and weights; the unitless line-height and letter-spacing ratios and the z-index scale are held with no scope, as reference values |
| Semantic | purple-light, purple-dark, emerald-light, emerald-dark | 123 `bg`, `text`, `border` and `icon` variables, each aliasing a primitive, with the same names as the theme files, except that `bg.overlay` is four variables, `bg/overlay-20`, `-40`, `-60` and `-80`, each the overlay colour's primitive with that opacity, made by hand because the plugin API cannot write a colour variable with an opacity ([ADR-0246](../adr/0246-skiplink-is-not-drawn-and-backdrop-is-provided-as-figma-styles-over-drawing-either-as-a-component.md)) |
| Component | one (`Value`) | 121 of the 35 component token files' 135 tokens, as pixel numbers; 14 are not representable (see below) |
| Viewport | mobile (375), tablet (768), desktop (1280) | The 11 font-size steps, the fluid ones evaluated at each width from their `clamp()`; the widths are the sizes a design is drawn at, not tokens |

**Opacity is held as a percentage.** Figma reads an opacity variable as a percentage, so `opacity/40` is the number 40, not 0.4 (a bound opacity of 0.4 draws at 0.4%, found in the Button pilot); the sync script writes it that way.

**Rules:** a variable is named by its token group, then the rest of the token's name, with a colour as `color/<hue>/<step>` and a component size step as its own segment (`color/purple/600`, `bg/brand-hover`, `space/4`, `avatar/size/lg`); its web code syntax is the CSS custom property (`var(--dbm-bg-brand-hover)`); a semantic variable aliases a primitive and never holds a raw value; scopes are set so a colour variable cannot be applied to a spacing field; every variable carries the token's `$description`. The script writes only what the tokens contain: adding a token in the repo and re-running it adds the variable.

**Styles** (written by the same script, `06-styles.js`): 54 text styles (the general roles Display, Heading, Body, Label and Overline at the top level, and the component-specific `Components/Control`, `Components/Field`, `Components/FieldLabel` (a form field's label, medium weight at the normal line height), `Components/Tag` (a tag's label, medium weight at the tight line height), `Components/Avatar` (an avatar's initials, semibold at the browser's own line height, five sizes), `Components/ProgressBar` (a progress bar's value label, semibold at the browser's own line height, one size), `Components/Textarea`, `Components/IconButton` and `Components/IconButtonPressed` (the caption under an icon button's icon, medium and bold, two sizes each); `Field` is regular weight at the tight line height, for the text inside a single-line field, and `Textarea` is the same sizes with an Auto line height, the browser's normal, which a multi-line field falls back to). A text style that exists for one component or one family of components lives under `Components/<Name>/<size>`, and a general role stays at the top level, so the Text styles panel keeps the two apart, 11 effect styles (the ten elevation styles and `Backdrop/blur`, a background blur), 4 paint styles (`Backdrop/20`, `40`, `60` and `80`, each bound to the Semantic variable `bg/overlay-N`, which carries the opacity, because a variable-bound paint does not show an opacity of its own in a style) and 3 grid styles.
- **Text styles** are named `Role/size` and bind their size to the Viewport variable and their family and weight to the Primitives variables, so a frame's Viewport mode resizes the type. Line height and letter spacing are the token ratios as percentages. The roles are a design decision, not a token: `Display` (Lora Medium, 3xl to 6xl, tight line height), `Heading` (Nunito Bold, sm to 2xl), `Body` (Nunito Regular, xs to lg), `Label` (Nunito SemiBold, xs to md) and `Overline` (Nunito SemiBold, upper case, wide letter spacing, xs and sm, for table headings and captions). There is no monospace style, because Figma has no `ui-monospace`.
- **Effect styles** are `Elevation/light/xs` to `xl` and `Elevation/dark/xs` to `xl`, the shadow tokens as drop shadows. Their colours are the tokens' literal rgba values, because a shadow colour is not a variable.
- **Grid styles** are a convention, not a token: `Grid/mobile` (4 columns, 16 px gutter and margin), `Grid/tablet` (8, 24 and 32) and `Grid/desktop` (12, 24 and 48).

Motion (durations and easing) is documented on the Motion section of the Foundations page, not made a variable ([ADR-0236](../adr/0236-the-figma-variables-are-four-collections-primitives-semantic-with-four-theme-modes-component-and-viewport-over-one-collection-or-a-collection-per-theme.md)).

**The sync script** is `scripts/figma-sync.mjs` (private, not published, no dependencies). It reads `packages/tokens/build/tokens.json` and writes one JavaScript body per collection into `.local/figma/payloads/`, each the code of one Figma MCP `use_figma` call, plus `90-verify.js`. A payload creates or updates by name, so a rerun changes only what differs. The MCP is called by the agent, not by the script, so a token change reaches Figma by running the script and sending its payloads in order (Primitives, Viewport, Component, Semantic).

**Order:** Figma lists a collection's variables in the order they were created and has no call to move one, so the script decides the order and the payloads create in it. Scales climb (50 to 950, xs to 3xl, space 0, px, 1, 2…), colours run neutral, gray, purple, emerald, red, amber, yellow, green, blue, and a semantic group (`bg`, `text`, `border`, `icon`) lists its general tokens first, then each tone (brand, neutral, info, success, warning, danger, highlight) with its base, hover, subtle, strong and `on-` variants, then the specialised ones (code, syntax). A collection that is already in Figma in another order is rebuilt in place by `95-reorder.js`, which copies each variable with its scopes, syntax, description and values, re-points the aliases at the copies, deletes the old ones and renames the copies; this is safe only before anything is bound to a variable, because the variables get new IDs. A variable added later, once components are bound, is created by hand with its aliases, scopes and web syntax and left where Figma puts it (the three `text/*-hover` variables landed beside their base tokens, and the order check stayed clean); `95-reorder.js` is not run then.

**Verification:** `90-verify.js` is read-only and returns, per collection, the counts, the modes, and every variable whose type, value in any mode (an alias is followed to its primitive), web code syntax or scope differs from the tokens; it also checks that the collection's order is the intended one, and it is clean for all 419 variables. Figma stores a number as a 32-bit float, so a number is compared to a millionth.

**Not in Figma as variables:** the 14 component tokens in `em`, `ch` or `%` (the `heading` trim offsets, the `link` icon sizing, the date and time picker segment widths, the table-of-contents and tags-input widths, and the command-palette tag width), which depend on the font or the parent and have no pixel value; shadows (Phase 2, effect styles); motion; the mono family is held as `ui-monospace`, which Figma has no font for.

## 6. Build rules for every component

Which components are drawn, which props become Figma properties and how big a matrix is are standing rules in [02-component-rules.md](./02-component-rules.md); what is drawn is the coverage rule, [ADR-0242](../adr/0242-a-component-set-draws-a-core-of-values-with-every-state-at-every-drawn-size-and-documents-the-rest-over-drawing-every-combination-of-every-value.md) (a core of each property's values, every state at every drawn size, the rest documented).

1. **Built from composition:** a molecule is made of atom instances, an organism of molecule and atom instances, never redrawn.
2. **Properties** (the rules are in [02-component-rules.md](./02-component-rules.md) §2): visual props (`variant`, `size`, `tone`) and states (default, hover, focus, pressed, disabled, loading, error) are variant properties, drawn to the coverage rule (a core of values, every state at every drawn size, the rest listed in the spec frame's "In code, not drawn" section); show and hide are booleans; content is text or instance-swap properties. Event handlers, refs, ARIA and controlled-state props are not modelled.
3. **Variable-bound everything:** fills, strokes, radius, padding, gap, type and effects are bound to variables or styles; there is no raw value on any layer.
4. **Auto layout everywhere**, with hug, fill and fixed set on purpose, minimum and maximum widths where the code has them, and constraints so a frame resizes correctly.
5. **Slots** for open content areas (Card body, Dialog content, Table cells, Tabs panels); the rest are nested components.
6. **Responsive:** the Viewport modes drive type and spacing; components that change shape (Navbar, Sidebar, Dialog into a sheet, Table) get a `platform` variant property.
7. **Accessibility annotations** on each spec frame: focus order, contrast of the text and edge pairings against the surface in each mode, and the target size.
8. **Dev Mode:** each finished component is marked ready for dev, with a description and a link to its Storybook page.
9. **The set is a labelled grid, and its default comes first.** A component set's own auto layout is turned off and its variants are placed on a grid: rows are the variant property, the tone and the size, columns are the state and the booleans drawn as variants (`rounded`), and a sibling frame named "Matrix labels" in the same Section carries the headings. Figma takes a set's default variant from its top-left cell, so the default value of each axis comes first in its row and column order (size runs md, xs, sm, lg, xl) and the cells are top-aligned in their row (centred, a taller variant sits above the default and takes the top-left place), and the property's defaults must equal the code's (`02-component-rules.md` §2 rule 2). The spec frame's Variants matrix has a header row naming its columns, and its Tokens used list has a Type row for the font variables the text styles bind.
10. **A property is named for what it shows when no code prop says so.** A Figma property takes the code prop's name (`02-component-rules.md` §2 rule 1). Where the look depends on something that is not one prop, it is named for what it shows and the spec frame's Properties table says which code props it maps to: `clearable` (the clear button, from `onClear` and a value), `filled` (a value is present, so the text colour changes, from `value` or `defaultValue`), `placeholder` and `count`; and Badge's `variant`, which takes the value `dot` beside `solid` and `subtle`, because the code's `dot` prop is a third presentation that ignores the solid-or-subtle choice and one axis leaves no invalid combination (placement props such as `position` and `overlap` are not modelled; the spec frame shows them as examples). A property that changes the colour or the shape is a variant property, and one that only shows or hides a layer is a boolean.
11. **A slot is a section a designer fills.** A component's open content areas (Card's media, header, body and footer) are slots built inside every variant before the variants are combined, with plain default content, so each becomes one property (cloning a variant loses its slots, so a new variant is built fresh and added to the set), named as the map names it, in lowercase. A slot's part in the code is named in the map (`kind: slot`), and a structure variant (Card's `layout`) is drawn at the default state only, while every state is drawn at every drawn size ([02-component-rules.md](./02-component-rules.md) §3).
12. **A transparent edge is no stroke and a padding.** A stroke with opacity 0 keeps its opacity on the component but loses it on an instance, where it draws as a faint line. A border the code makes transparent (Card's ghost) is drawn with no stroke and a padding of the border's width bound to `border-width/1`. This is not a transparent border on every variant: a component whose border is real only on some variants (Button's secondary) keeps the code's heights, with the offset drawn as the derived padding.
13. **Icons** (built, `07-icons-*.js`): the 58 Phosphor icons the component source uses (from `packages/icons`), on their own Icons page, as an instance-swappable component set with a `weight` property of bold (the library's default), regular and fill and a `tone` property of 17 values ([ADR-0238](../adr/0238-an-icon-set-has-a-tone-variant-over-a-contextual-colour-collection-an-overridden-fill-or-a-mask.md)), and a size bound to the `icon-size` variables; no other icons are drawn, and the page says how to add one. Its header frame credits Phosphor Icons (MIT licence) and links to the Phosphor website, https://phosphoricons.com, where the full set can be browsed.

## 8. Risks, gaps and open questions

- **Layout primitives** (Box, Stack, Grid, GridItem, Center, Container, Bleed, Affix, AspectRatio, Spacer) are CSS concepts that Figma expresses as auto layout, not components. **Decided 2026-11-22:** they are not drawn as components; they are listed on the Components page's table of what is not drawn, and the Layout page documents them as auto-layout patterns. Components are built only for Divider and the visual ones.
- **`Text`** is not drawn, **decided 2026-11-26** ([ADR-0248](../adr/0248-text-is-not-drawn-and-is-a-text-layer-with-a-text-style-and-a-colour-variable-over-drawing-it-as-a-component.md)): it is a text layer with one of the Body, Label, Heading or Display text styles and a `text/*` colour variable, so it joins the Components page's not-drawn table with a recipe, and `Heading` is decided when it is reached.
- **Components whose behaviour is the point** (Collapse, Backdrop, FocusTrap, SkipLink, BackToTop). **Decided 2026-11-22:** each is built only if it has a visual state worth drawing, decided when its category is reached; the rest stay on the Components page's not-drawn table. **Decided 2026-11-26** ([ADR-0246](../adr/0246-skiplink-is-not-drawn-and-backdrop-is-provided-as-figma-styles-over-drawing-either-as-a-component.md)): `SkipLink` is not drawn, and `Backdrop` is provided as Figma styles; `BackToTop` is not drawn either, **decided 2026-11-26** ([ADR-0247](../adr/0247-backtotop-is-not-drawn-and-is-a-rounded-iconbutton-with-an-up-arrow-over-drawing-it-as-a-component.md)): a visible one is a rounded `IconButton` with an up arrow, which that set draws.
- **Overlays** (Dialog, Drawer, Popover, Toast, Tour). **Decided 2026-11-22:** drawn as static frames in each open state.
- **Mode limits:** the four-mode Semantic collection uses the Professional plan's whole allowance; a third brand needs a higher plan or a second collection. Settled, no action.
- **Fonts:** Nunito and Lora are available in the file (confirmed in Phase 0). Settled, no action.
- **Drift:** components are drawn by hand, so a code change is not reflected until the file is updated. **Decided 2026-11-22:** `/figma-drift` is run for every release that changes a published package (`RELEASING.md`, item 7 of the sequence), and which components are drawn is read from the file, not kept in a list.
- **Publication:** whether the finished file is private, a view-only link or a Community file. **Decided 2026-11-22:** kept for Phase 8, because it needs the finished file and a Community copy is permanent. The plan is a Community file published from a private working file as snapshots, so no one can edit the original; library mode, the licence and what the listing says are decided then. What is known, recommended and unverified is in [07-community-and-code-connect.md](./07-community-and-code-connect.md).
- **Keeping a spec frame from going stale (proposed, not yet decided).** Only what a person must judge is written by hand: the description, the anatomy and the accessibility notes. The rest can be generated or checked: the "not modelled" names are the manifest's props minus the ones the frame maps; the tokens-used list can be read from the variables and styles the component actually binds; the "built from" text is read from its instances; and a per-release check compares each frame with the manifest and flags a property that no longer exists in code or a prop added since. The "Built from" block, a slot listing the components nested in this one, is in the master; it can be written from the frame's instances, and the Tokens used table is read from the variables and styles the component binds. Other candidates: a version stamp on each frame, set at each publish, and fixed accessibility lines (pattern, keyboard, target size, contrast per mode) so none is skipped.
- **Nothing in Figma updates itself when the code changes.** The components are drawn by hand, so a change to a component in code reaches Figma only when someone updates its frame. The tokens are one-way from the repository but not automatic either: they reach Figma when `scripts/figma-sync.mjs` is run and its payloads are sent.
