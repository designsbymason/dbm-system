# DBM System — Storybook & Documentation Standards

Companion to `05-component-api-conventions.md` (the API contract) and `06-engineering-standards.md` §9 (the review checklist). This doc covers a third dimension: how a component's *documentation and interactive showcase* meet the same "premium, comprehensive, agent-legible" bar the component code itself must meet.

---

## 1. Purpose

Every component ships with a hand-authored Docs page, a fully interactive Playground, interaction tests, copyable code under each story, and a place in a sidebar that matches the component inventory. This doc defines each of those, the shared Storybook infrastructure behind them, the per-component checklist (§5), and the status of every built component (§6). Storybook's defaults produce none of it: autodocs alone can't write prose sections, an unconfigured Controls panel renders inert placeholders for component-reference props, a `render` that ignores `args` makes every control a silent no-op, and a sidebar grows its own taxonomy unless it is held to the inventory's.

## 2. Storybook infrastructure

Registered in `.storybook/main.ts`'s `addons` array: `@storybook/addon-a11y` (the Accessibility panel), `@storybook/addon-docs` (Docs pages, with `remark-gfm` — `02-tech-stack-and-structure.md`) and `@storybook/addon-vitest` (every story and its `play` function as a real test in Chromium, `02` §3). The viewport toolbar and `play`-function testing (`expect`, `userEvent`, `within` from `storybook/test`) are part of Storybook 10's core, so they need no separate addon package. Every interactive component has at least one `play`-function story scripting its core interaction (click, keyboard navigation, focus), so behavior is verified in Storybook as well as in Vitest.

## 3. Sidebar taxonomy

`04-component-inventory.md`'s nine functional categories are the source of truth. A story's `title` is `{Tier}/{Category}/{Component}`, where `{Tier}` is `Atoms`, `Molecules` or `Organisms` (and `Templates` later) and `{Category}` is one of these shortened labels:

| Inventory category | Title segment |
|---|---|
| 1. Layout | `Layout` |
| 2. Typography | `Typography` |
| 3. Inputs & Forms | `Inputs` (includes `FieldLabel`/`FieldError`/`FieldHelperText`) |
| 4. Data Display | `Data Display` |
| 5. Navigation | `Navigation` |
| 6. Feedback | `Feedback` |
| 7. Overlay & Disclosure | `Overlay` |
| 8. Media | `Media` |
| 9. Utility | `Utility` |

There is no catch-all group: every component's category segment matches exactly one inventory category. A top-level **`Foundations`** group (§7) sorts before the tiers via the `groupPriority` array in `preview.tsx`'s `storySort`, since top-level group order isn't alphabetical by default.

## 4. The Docs page template

One hand-authored `ComponentName.mdx` file per component (via `@storybook/addon-docs`), set as the **first entry** in that component's Storybook group (before the Playground and every other story). Auto-generated docs (`tags: ["autodocs"]` alone) can't produce the prose sections below, so every component gets a real MDX file that embeds live `<Canvas>`/`<PlaygroundControls>` blocks from the Playground story, interleaved with hand-written content. Sections, in order:

1. **Intro** — title and tier badge via `<ComponentHeader>`, then the one-paragraph description, with **Import as a nested `### Import` subsection** right underneath (a single code block, not substantial enough for its own TOC tab). The section needs a heading for the TOC (§4.1) to produce an "Intro" entry, but a visible `## Intro` label reads as redundant under the big title, so keep a real `## Intro` in the DOM and hide it visually with `<VisuallyHidden asChild><h2>Intro</h2></VisuallyHidden>`, placed *before* `<ComponentHeader>` so the TOC entry scrolls to the very top, title included. The TOC library (tocbot) reads heading text from the DOM regardless of visibility.
2. **Interactive Playground** — the Playground story's live canvas, then **below it** a single-card, controls-only panel laid out in two columns of label+control pairs (`<PlaygroundControls>`, §4.1). **Exclude any prop whose control isn't editable** (`control: false`, explicit or inferred: `onClick` and other function props, `asChild`, `id`, `className`, `data-testid`) via `<PlaygroundControls exclude={[...]}>`. They still appear in the Properties table, but a row reading just "–" in a Playground is dead space. `exclude` is a plain `string[]` kept in sync by hand with whichever props end up `control: false`; some (bare function args like `onClick`) get it only through Storybook's own implicit inference, so there is no automatic way to detect them from the story's `argTypes`.
3. **Properties table** — prop name, **value options**, description, default, required/optional — via the custom `<PropertiesTable>` block (§4.1), not the stock `<ArgTypes>`, which has no "value options" column. Sourced from the component's TypeScript types and JSDoc (the same JSDoc that feeds the future manifest generator). **Every prop needs a real, non-empty description, including "obvious" native props** (`children`, `onClick`, `disabled`, `style`): docgen extracts several of them with an empty description rather than dropping the row, and the table shows blanks as an em dash. Fix it with an explicit `description` in the story file's `argTypes` (§4.1), not by hoping JSDoc alone is picked up.
   - **Row order must read sensibly** — content prop, then core visual props (`variant`/`size`), then behavioral/state props, then advanced/escape-hatch props (`asChild`, `className`, `id`, `data-testid`) last — passed explicitly via `<PropertiesTable>`'s `order` prop, since docgen's order is unpredictable.
   - **One sentence directly above `<PropertiesTable>` states that the component also accepts any other native `<element>` attribute beyond what's listed.** Every component that extends `ComponentPropsWithoutRef<'element'>` passes through dozens of native attributes the curated table never enumerates (`onFocus`, `onKeyDown`, `spellCheck`). Word it for the component's own native element ("`Badge` also accepts any other native `<span>` attribute beyond what's listed here (e.g. `onClick`, `title`) — passed straight through to the underlying element."); for a polymorphic component (`Avatar`, `Box`), phrase it around `as` instead of one fixed element.
4. **Variants / states gallery** — a static visual reference of every variant × size × state combination (distinct from the interactive Playground: an at-a-glance comparison). **Every story in this section gets its own `###` subheading** (the story's display name) directly above its `<Canvas>`; bare, unlabeled Canvas blocks give the reader no way to tell what they're looking at, and the TOC can't show them.
5. **Usage guidelines** — Do's and Don'ts, concrete not generic ("Do use `destructive` for irreversible actions", not "use variants appropriately").
6. **Best practices** — the judgment-level guidance a senior designer/engineer would give a newcomer.
7. **Accessibility** — keyboard interaction table, the ARIA attributes the component sets and why, screen reader behavior notes, any contrast pairings worth calling out.
8. **Code examples** — copyable snippets for the common real-world usage patterns, beyond what the props table conveys.
9. **Design tokens used** — which semantic tokens this component consumes, doubling as a visible confirmation of "no hardcoded values". A unit test keeps it matched to the stylesheet (`06` §9).
10. **Related components** — cross-links (e.g. `Input` ↔ `Textarea`, `FieldLabel`, `FormField`).

**Editorial bar:** the Docs page is a reference a complete newcomer to DBM, human or agent, should be able to read and fully understand, not just a props reference for people who already know the system. **Define any technical/jargon term the first time it's used** ("polymorphic" appeared in `Box.mdx`'s opening sentence with no definition). When a concept is foundational to the whole system rather than one component (the polymorphic-`as` pattern, used by `Box`, `Stack`, `Text`, `Heading`, `Center` and others), define it thoroughly once in the most foundational component (`Box` for polymorphism) and have every other component cross-link to it through Related Components instead of re-explaining it.

**Never reference an internal `guidelines/*.md` path, or internal decision-history and process narrative, in visible page content** (component Docs pages and Foundations pages alike). Those documents are internal working notes, not something a consumer of the published package or hosted Storybook should see cited. The same restriction covers dates (`since the 2026-08-20 token consolidation`), review-process framing (`a real gap found and fixed during review`), and provenance phrasing (`chosen at explicit direction`, `merged from the retired X`). Keep whatever is genuinely useful to a reader in evergreen, present-tense terms (what a token or behavior does, why a design tradeoff exists, how something is enforced) and drop only the *when/how/why-we-internally-decided-this* framing: `"the dropdown content's own elevation — a fixed light/dark pair, not a reactive token (see 03-token-system-spec.md)"` becomes `"the dropdown content's own elevation"`. If the history is worth preserving at all, it belongs in that component's `guidelines/component-reviews/ComponentName.md`. Source-code comments (`.storybook/**/*.ts(x)`, `.css`) citing a guideline for a future maintainer are fine, since they aren't rendered to a Storybook visitor.

### 4.1 Visual presentation layer

Beyond content and structure, the Docs page has a dedicated visual-polish layer — a custom Storybook theme, global CSS, and a small set of reusable MDX-only components — so every Docs page reads as a premium, cohesive reference rather than Storybook's default autodocs output. None of it ships in the published package; it lives under `packages/components/.storybook/` and is wired in through `preview.tsx`'s `docs` parameter.

**Shared infrastructure (applies to every component automatically):**
- **`.storybook/theme.ts`** — two `create()`-based Storybook themes (light/dark) mirroring the same semantic step selections as the design system's own `--dbm-*` tokens, applied reactively: `.storybook/manager.ts` listens for the Mode toolbar global via the addons channel and re-calls `addons.setConfig({ theme })` on change, and `.storybook/DbmDocsContainer.tsx` (wired via `parameters.docs.container`) does the same for the Docs addon's wrapper and typography. Manager chrome and the Docs wrapper track the same Brand/Mode toggle that themes previewed components.
- **`.storybook/docs.css`** — global typography/table/Canvas styling scoped to Storybook's real, DOM-confirmed class names (`.sbdocs-content`, `.sbdocs-preview`, `.docblock-argstable*`). Don't guess class names: verify them in the rendered DOM first, since Storybook styles most elements through hashed CSS-in-JS classes with no stable selector.
- **`parameters.docs.toc: { headingSelector: "h2" }`** (in `preview.tsx`) — the built-in sticky table of contents for every Docs page. It is restricted to `h2` (the library default is `h2, h3`) so the TOC shows only the template's fixed section list, identical across every component, rather than each component's own `h3` variant subheadings. "Import" is an `h3` and deliberately has no TOC entry. Verify by comparing two components' rendered TOCs side by side.
- **`minHeight` in the shared `withTheme` decorator is conditional on `context.viewMode === "docs"`** (undefined there, `100vh` in standalone story view); without it, every Canvas embedded in a Docs page gets a huge empty space below the component.
- **`.sbdocs-content h2`'s top `margin-block` needs `!important`:** Storybook's own MDX stylesheet has a `:first-of-type` rule (`margin-top: 0`) that is more specific than `.sbdocs-content h2`, so it silently wins margin-top for whichever `##` section is first in the DOM. It is harmless on component pages and Foundations pages, where the first `h2` is the visually hidden "Intro" (§4 item 1, §7.2).

**Per-component MDX building blocks (import from `.storybook/blocks`, use in every `ComponentName.mdx`):**
- **`<ComponentHeader title="X" tier="Atom|Molecule|Organism|Template" />`** — replaces the plain `<Title />`. Renders the component name plus a tier badge (DBM's own `Badge` atom) so a reader knows where the component sits in the atomic hierarchy. The badge colour is set per tier (a `toneForTier` map in `ComponentHeader.tsx`): Atom `info`, Molecule `warning`, Organism `success`, Template `brand` — categorical labels, not status signals, with the badge text always the primary cue so colour is never the only way the tier is conveyed. The title+badge row is `flexWrap: "wrap"` so a long component name wraps the badge beneath it instead of pushing it off-screen at narrow widths.
- **`<Callout tone="success|danger|info" title="...">...markdown children...</Callout>`** — a styled callout box (icon + tinted background) for the Do/Don't pair under Usage guidelines (`success`/`danger`, laid out as a two-column grid; see `Box`/`Button` for the grid wrapper) and for the Accessibility section (`info`, wrapping the whole body, with a specific descriptive title rather than the word "Accessibility").
- **`<TokenRow token="bg.brand" usage="..." />`** — one row per token in "Design tokens used". Color tokens (`bg.*`/`text.*`/`border.*`/`icon.*`) render a live swatch resolved from the actual CSS custom property, so it reflects the current theme; non-color tokens (`space.*`, `radius.*`, `font-*`, `motion.*`, `opacity.*`) render with no swatch. Give each color token its own row; a range of non-color tokens (`space.1`–`space.6` for a per-size scale) may stay in one row.
- **`<RelatedCard name="..." description="..." href="...">...live mini-preview...</RelatedCard>`** — a small card with a live rendering of the related component (a real component, not a screenshot) plus its name and description, in a `repeat(3, 1fr)` grid (see `Box`/`Button` for the wrapper). Keep the preview small and representative: a few coloured squares for a layout primitive, one real instance for an interactive atom. The card's own `href` is a raw anchor and uses the full `/?path=/docs/...` or `/?path=/story/...` form (contrast the Markdown-link rule in the Pitfalls below). Rules for the preview slot:
  - It must never render its own top-level `<a>` or `<button>` unwrapped by something else. The card's navigation link wraps only the name and description, not the preview, because nesting a real `<a>` (a `Link`) inside the card's `<a>` is invalid HTML and throws a hydration warning, and a nested `<button>` (`IconButton`, `CloseButton`, a removable `Tag`) is equally invalid. Don't re-wrap the whole card in one clickable element.
  - It must be `inert` (`RelatedCard.tsx` sets the attribute), because a preview can render something with a real destination (`<Link href="/docs">`) that a plain click would follow, bypassing the card's own link. `inert` blocks both pointer clicks and keyboard Tab-then-Enter activation; verify with a real simulated mouse click, since `element.click()` bypasses `inert` entirely.
  - Its height is fixed, not floored: `height: space.20` (80px, `overflow: hidden`). A `minHeight` let a taller preview (a `size="sm"` `Button`, about 68px) push the name and description to a different Y position from an adjacent card; 80px is the first scale step that fits the tallest real preview with room to spare, and one sitewide constant keeps every card consistent across pages and rows.
  - A preview with no width of its own (`ProgressBar`, `Slider`, `Divider`) is wrapped in a sized box (`<div style={{ width: "var(--dbm-space-24)" }}>`), or it draws at zero width and the card shows no graphic: a `label` is only the accessible name, not visible text to give it width. Look at each card on the live page.
  - Plain-text children go on the same line as their tag (`<Button variant="secondary" size="sm">Hover me</Button>`); see the MDX pitfall below.
- **`<PropertiesTable of={ComponentStories} order={[...]} />`** — replaces `<ArgTypes of={ComponentStories} />`. A fully custom table (`.storybook/blocks/PropertiesTable.tsx`), because the stock `<ArgTypes>` has no supported way to add a column (`ArgTypesProps` accepts only `of`/`include`/`exclude`/`sort`). It resolves the argTypes data through the exported `useOf(of, ["meta"])` hook and renders its own `<table>`. Columns: Name, **Value options** (the literal set a prop accepts — enum members as `<code>` pills, `true`/`false` for booleans, an em dash for freeform or function props — computed from `argType.options` and `argType.type.name`), Description, Default. The `order` prop forces display order (§4 item 3). The alternating row background is the primitive `--dbm-color-purple-200`, not a gray: `bg.brand-subtle` reads as plain gray when spread across a stripe, and there is no semantic step between it and `bg.brand-hover`. This is a documented exception to "semantic tokens only" because it is presentational Storybook chrome, not shipped component code.
- **`<FieldsTable rows={[...]} />`** (`.storybook/blocks/FieldsTable.tsx`) — the fields of a plain object a component takes (a `DataTable` column), in the same table as `<PropertiesTable>`: same four columns, same stripes, same name, option and default cells, through the same helpers. `<PropertiesTable>` reads a component's argTypes and an object's fields aren't a component's props, so it takes the rows directly (`name`, `required`, `options`, `description` with `` `code` `` spans, `defaultValue`). Use it instead of a Markdown table, which gets the generic prose-table look.
- **`<PlaygroundControls of={PlaygroundStory} exclude={[...]} order={[...]} />`** (`.storybook/blocks/PlaygroundControls.tsx`) — the Playground's controls panel. It takes the same `of`/`exclude`/`order` API as `<PropertiesTable>`, resolves the target story's live args (`usePlaygroundArgs`, backed by the Docs addon's `DocsContext`) and renders each row itself with this design system's own form atoms (`FieldLabel` plus a dispatched `Switch`/`Select`/`Input` per `argType.control.type`), real controlled two-way-bound inputs, not a re-skin of Storybook's Controls widgets (whose ArgsTable boxes every row as two separate table cells that no CSS could wrap in one border). Layout is `.dbm-playground-controls-grid` in `docs.css`: a two-column CSS grid (`repeat(2, minmax(0, 1fr))`) collapsing to one column under `40rem` (a literal match to `breakpoint.sm`, since `@media` can't reference custom properties); it is not a table, so there is no row striping.
  - **"Reset to defaults"** is a `Button` (`variant="tertiary"`, `size="xs"`) wired to `resetArgs()`, left-aligned *below* the card, mirroring where the Canvas block's native "Show code"/"Copy code" controls sit. Its icon is composed into `children` with no explicit `tone`: `Button` colours a `leadingIcon` through a variant-locked `tone`, while an `Icon` with no `tone` inherits `currentColor` from the button, so it tracks the hover colour automatically.
  - **It renders nothing at all** (no card, no reset button) when no live-editable prop is left after `exclude` and `control: false` filtering, which `usePlaygroundArgs`'s empty `rows` array detects.
  - **A `mapping`-backed select needs a reverse look-up.** `usePlaygroundArgs` holds the *resolved* post-`mapping` value (a real component reference for `icon`), so the select computes its displayed key by finding the `argType.mapping` entry whose value matches, falling back to `String(value)`. Without it the embedded dropdown shows its unselected placeholder while the Canvas is correct.
  - **Widgets echo changes optimistically.** Displayed values driven directly off `usePlaygroundArgs` lag about a second (the update round-trips through Storybook's event channel), so a control looks like it does nothing. `ControlField` keeps its own local `draft` (plus a `rawText` buffer for `number`, so a bare `-` isn't clobbered while typing a negative value) that updates synchronously and re-syncs from the external value when *that* changes. The re-sync happens during render, not in an effect (`react-hooks/set-state-in-effect` flags the effect version).
  - **`placeholder`** on an argType is passed to the underlying `Input`'s native `placeholder` on the `number` and `text` branches: cosmetic guidance only, never an arg. Use it for a prop with no safe default whose real value would collide (`GridItem`'s `colStart`/`rowStart`: `"auto"`).
  - **`if`** on an argType (`truthy`/`exists`/`eq`/`neq`/`arg`) hides a control that does nothing in the current state until it does, decided from the value the person just set rather than the arg returning through the channel. Use it for a prop the component ignores unless another is set, and have the story's `render` stop passing the ignored prop (so it doesn't log a development warning).
  - **`control.labels`** (`Record<string, string>`, keyed by `String(option)`) gives an option a visible label. Without it an option whose stringified value is empty (`Accordion`'s `defaultValue: ""`, meaning "nothing open") renders a selectable row with invisible text, in the Playground's select *and* in `PropertiesTable`'s Value options pill. The label is also the option's underlying `Select.Option` `value`, which avoids relying on how `Select` handles a literal `value=""` (its internal "nothing selected" sentinel); `onChange` reverse-looks-up to the real value.
  - **The boolean `Switch`** gets `aria-labelledby` pointing at its row's `FieldLabel` (given a stable `id`), because `Switch`'s own dev-mode check only inspects its own props and warned "no accessible name" on every Docs page even though the native `<label for>` association resolved correctly.
  - **The reset button's styling lives in a real class** (`.dbm-playground-reset-button` in `docs.css`), not an inline `style`, because an inline style can never lose to a `:hover` rule; and an `!important` rest-state rule needs an `!important` hover rule too, since `!important` declarations form their own priority tier above normal ones, whatever the selector's specificity. Check with `document.querySelectorAll(':hover')`, not by reading the cascade.

**Playground layout:** wrap the Canvas and controls as two siblings — `<div className="dbm-playground-canvas"><Canvas .../></div>` then `<PlaygroundControls of={PlaygroundStory} exclude={[...]} order={[...]} />` (no wrapping div; the block renders its own card) — directly in the MDX flow, with the blank lines MDX needs around nested JSX so it parses `<Canvas>`/`<PlaygroundControls>` as components rather than literal text (see `Box`/`Button`/`Avatar`). The controls panel renders **below** the Canvas, not beside it: a side-by-side split was reverted because a two-column control grid needs the full content width.

**Verification requirement:** after writing or changing any `ComponentName.mdx`, visually verify it in a running Storybook instance (via the browser preview tools, not just `tsc`/lint): the TOC appears, every Callout renders with the correct tone and icon, every RelatedCard's live preview renders (not a broken import), the Properties and token tables are styled, and **every internal link's actual rendered `href` (not just its visible text) is correct and its click-through lands on the intended page**. `tsc --noEmit` passing only proves the MDX compiles, not that the page renders or navigates correctly.

**Pitfalls.** Each is pitfall → rule → how to check. All were found by a real defect, usually one only a live browser showed.

*MDX and Markdown*
- **A backslash-escaped quote inside a JSX attribute breaks the page** (`usage="status=\"online\" dot color"` — `storybook dev` fails to start: "Unexpected character `\`"). MDX's JSX parser doesn't support it. Use single quotes for the inner text (`usage="status='online' dot color"`). *Check:* Storybook starts and the page renders.
- **Own-line, indented text inside a JSX tag is wrapped in a stray `<p>`.** `<Link href="…" external>` with `External link` on its own indented line renders `<a><p>External link</p><svg/></a>`: MDX treats it as block-level markdown, and the `<p>` pushes anything rendered after the text (the external-link icon) onto a new line, even though the component's own CSS is innocent. It also adds the browser's default `1em` margins inside an inline-flex, `nowrap` element (a `size="sm"` `Button` measured 68px instead of 41px). *Rule:* keep short children on the same line as the opening and closing tag whenever they are meant to flow inline with a sibling the component renders; multi-line formatting is fine for props. Block content (a `<p>` inside a `<Callout>`) already expects paragraph wrapping. *Check:* sweep `RelatedCard` blocks for a bare-text line between JSX tag lines, and inspect the rendered DOM.
- **A Markdown table renders as raw pipes and dashes** without GFM, which core CommonMark lacks. `remark-gfm` is registered in `.storybook/main.ts` (`02-tech-stack-and-structure.md`), so a real Markdown table works in any Docs page. *Check:* it renders as a `<table>` in light and dark.
- **A Markdown internal link written as `[text](/?path=/docs/…)` gets a doubled, broken `href`** (`./?path=/?path=/docs/…`). `@storybook/addon-docs` renders MDX links through Storybook's own `Link`, whose logic is `href.startsWith('/') ? './?path=' + href : href`, so it expects the bare form. *Rule:* **write Markdown-syntax internal links without the prefix** — `[text](/docs/story-id)` or `[text](/story/story-id)`. `RelatedCard`'s `href` is a literal JSX prop that bypasses `Link` and keeps the full `/?path=…` form, so the two conventions are deliberately different. *Check:* read the rendered `href` and click through.

*The shared Docs document*
- **Every `<Canvas>` on a Docs page shares one underlying `document`.** Only one `#storybook-preview-iframe` exists on a Docs page, however many Canvases the MDX embeds. A demo that targets `document.body` or uses `position: fixed` (a common way to show "this rendered somewhere else") escapes to the corner of, or the end of, the *entire page* and stays pinned through every section. *Rule:* for an embedded interactive story, give the demo a locally scoped target (a ref-callback `<div>` passed as `container`; see `Portal.stories.tsx`'s Playground). For a story whose point is the true unscoped default, take its Canvas out of the Docs page's embed list ("sidebar-only", as for `FocusTrap`'s `MergedOntoChild`) and replace it with a `Callout` linking to the standalone story. This is a Docs-page architecture effect, not a `Portal` bug.
- **A modal overlay embedded in a Docs page covers the whole page.** Its scrim is `position: fixed`, and it locks scroll, hides the rest of the page from assistive technology and traps focus, so one `Canvas` showing an open `Dialog` takes over the Docs page for as long as it is open. *Rule:* draw the demo inside a box that is a containing block for fixed descendants (`transform: translateZ(0)`, `overflow: hidden`) and pass that box as the dialog's `container` (`DialogStage` in `Dialog`'s story kit), and keep every embedded story closed until the reader opens it (no `defaultOpen`). A story whose point is the page-wide behaviour (the scroll lock itself) is a hidden `!dev` check, not an embedded one.
- **A story that depends on real `window` scroll breaks once embedded:** it measures or sets `window.scrollY`/`scrollTo` as part of its own persistent render, so it stretches the *whole page* to its content height and resets the whole page's scroll. *Rule:* any embedded story demonstrating scroll-driven behavior scopes its scroll to a confined container (`scrollContainerRef` or equivalent; `BackToTop`'s `BoundedScrollDemo`). A `play` function scripting a real end-to-end `window`-scroll test is fine on a story kept out of the Docs embed list.
- **A component whose purpose is a document-wide side effect breaks the Docs page's theming.** `ThemeProvider` sets `document.documentElement.dataset.theme`, the mechanism `preview.tsx`'s `withTheme` uses for the Brand/Mode toolbar. Embedded, it overwrites the `--dbm-*` custom properties (what Callouts, code blocks and Canvases use) without updating the second, independent chrome layer sourced from the toolbar's globals through `getStorybookTheme` (the wrapper background and Storybook's default heading colour), giving a split-theme page of washed-out, low-contrast text that cannot occur in a real app. *Rule:* don't embed such a Playground; link to the standalone story with a `Callout`, and call the exception out in the page's intro. With zero embedded Canvases `withTheme` stops running for the page, so render `<ThemeSync />` once, right after `<Meta/>` (§7.1).
- **Two stories that open a popover on mount (`defaultOpen`) on the same Docs page race each other's mount-time auto-focus,** and Storybook's patched `focus()` then calls React's `act()` mid-commit, so the second story's block renders `Error: Should not already be working` instead of a canvas (and has no "Show code"). It is fine standalone and in the browser test run. *Rule:* a demo popover that opens on mount passes `onOpenAutoFocus={(event) => event.preventDefault()}`, which a static demo wants anyway.
- **`docs.css`'s `.sbdocs-content h1/h2/h3` rules override a component's own real `h1`–`h6` output.** They style the MDX page's prose headings, but `.sbdocs-content h2` matches *any* `h2` under the content, at (0,1,1) specificity, which beats a single-class rule in a component's CSS Module. `Heading` was the first component whose output is real headings, and its `size`, `weight` and border looked wrong. The three rules are scoped with `:not(.sbdocs-preview h2)` and the like (addon-docs' stable Canvas wrapper); `:not()` takes the specificity of its argument, so genuine prose headings still win. *Rule:* a new bare-element selector added to `.sbdocs-content` needs the same `:not(.sbdocs-preview …)` treatment. *Check:* a component that renders real headings, its computed `font-size`/`border` against its own class.

*Properties table and Controls*
- **The Default column shows nothing unless the story's `argTypes` says so.** `PropertiesTable` reads `argType.table.defaultValue.summary` and nothing else, and docgen inference fails in three shapes (`06` §9 lists them: a root Playground meta with no `component:` field, a compound sub-part's `component: Parent.Sub`, and a default applied by runtime logic or native-HTML behavior). Check every row against the type file's own `@default` tags, never by guessing from a component's shape (components sharing a shape turned out to differ). *Fix:* an explicit `table: { defaultValue: { summary: "..." } }` matching the JSDoc `@default`. A prop with no default shows "—" like every other, and `undefined` is never written into it.
- **A long cell widens the whole table** (`RangeSlider` was 877px against `Slider`'s 705px, wider than the page). *Rules:* (1) a prop whose default is an object, several values or a function shows "—" and states the default in the description, since a Default cell is one unbreakable `<code>` pill (docgen prints a function's whole source otherwise: `table: { defaultValue: { summary: "" } }`); (2) a prop name longer than the Name column's width (`NAME_COLUMN_CHARACTERS`, 17) wraps at its camelCase joins through a `<wbr>` before each capital and the `dbm-proptable-name-wraps` class, offered to that name alone (allowing every name to wrap shrank the column and wrapped `defaultValue`); (3) inline code in a description never wraps, so a code pill of a whole object or array sets the column's minimum width, so write such an example as prose with short pills. *Check:* measure against a well-behaved table (`SearchInput`'s is 644px: Name 170, Value options 190, Description 158, Default 124).
- **The Name column wraps long `<code>` prop names** (`aria-labelledby`) when `table-layout: auto` squeezes it. `white-space: nowrap` on the `td` alone fails because `.sbdocs-content code`'s base rule sets `white-space: normal` on the `<code>` itself; put `white-space: nowrap` (and `overflow-wrap: normal`) in `.dbm-proptable code`'s own `!important` block.
- **A Playground-only choice ("off", "Default", a custom icon to try) is not a value the prop takes,** so it goes on the Playground *story's* `argTypes`, never the meta-level ones. The "Value options" column is built from the meta-level `options`, so an `"off"` there is listed as a real value an agent could pass. Give the meta-level argType only the real values (`options: [3, 4, 5, "container"]`) and add the extra choices, and any `mapping` that turns them into "leave it out", to the Playground's `argTypes`, which merges over it for that story only. `Breadcrumb`'s `maxItems` and `Alert`'s `icon`/`role` are the examples.
- **The native per-story Controls panel's row order is not `PropertiesTable`'s `order`.** `parameters.controls.sort` accepts only `'none' | 'alpha' | 'requiredFirst'`, so row order comes from docgen's extraction of the `*Props` declaration: a prop declared directly (with JSDoc) on the component's interface renders at that position, while one only inherited through `extends ComponentPropsWithoutRef<…>` is extracted in a separate pass whose position nothing controls (`Button`'s `disabled`/`onClick`). *Fix:* redeclare the prop on the component's own interface where the order wants it (reordering `meta.argTypes` has no effect). *Checks:* restart the dev server, since Vite HMR and "Reload story" don't invalidate docgen's cache for a changed type file; and re-check the redeclared prop's rendered control, since redeclaring a function-typed prop can flip its row from no control to an inert "Set object" placeholder, which then needs an explicit `control: false`.
- **A story's own `render` that ignores `args`, and a non-primitive resolved arg, break the "Show code" panel.** See §4.2.

### 4.2 The code under "Show code"

Every `<Canvas>` on a Docs page has a "Show code" button, and what it shows is meant to be something a developer can **copy and paste**. Left to Storybook's defaults it usually isn't. A story with its own `render` shows the *story object's source text* (`{ name: "All variants", argTypes: noControls, render: () => … }`), including demo-only helpers (`DemoCard`, `DemoTable`, `gridStyle`, `allTones.map(…)`), TypeScript casts and every comment inside the render. A Playground shows either a `<DemoSections />` placeholder or, for a story with no render, a bare `{}`. None of that exists in the published package.

**Two failure modes.** A story with its own `render` and no `args` shows the story object's source permanently. A story that spreads `args` (`<Grid {...args}>`) shows that source for a second or so and then Storybook **swaps in a snippet generated from the rendered tree**, so what a reader actually sees is the generated one, and **a check must be a settled read (wait about 3 seconds after opening "Show code")**. The generated snippet spells out every default and empty placeholder (`hasError={false}`, `name=""`, twenty props on a `Slider`); fills every handler with a no-op (`onValueChange={() => {}}`); keeps the story's demo wrapper `div`; **freezes controlled state** (`value={50} onValueChange={() => {}}` and a hardcoded "Live: 50"); **drops a render-prop child entirely** (`FormField`'s snippet had no control in it); prints a helper's name as a placeholder (`<DemoOptions />`); and hides a one-prop variant of the Playground among all the other props.

**The rule:** every visible story on a Docs page points `parameters.docs.source` at hand-written code, never at its own source and never at the generated snippet ([ADR-0020](adr/0020-show-code-uses-hand-written-snippets-over-storybook-generated-source.md) has the decision and the alternatives). It applies to every component and is part of the §5 checklist; converting a Finalized component's stories is docs-only, so it does not reopen the component (`06` §9), but it still needs the maintainer's go-ahead.

- **Gallery stories** put their snippets in `ComponentName.snippets.ts` next to the stories (`export const componentSnippets = { variants: "…", … }`, plain strings) and set `parameters: { docs: { source: { code: componentSnippets.variants } } }`; Storybook uses `code` verbatim when set. A snippet is the **smallest real usage of what its story shows**: one representative element with a comment naming the other values (`{/* variant: "outlined" (default) | "elevated" | … */}`), not the whole demo grid. It uses only exports of the package (plus plain HTML elements), no imports (the Import section covers those), and none of the story's layout scaffolding (wrapper `div`s, `maxWidth` styles, test ids, `preventDefault`).
- **The Playground** builds its snippet from the live controls with `parameters.docs.source: { type: "dynamic", transform: (_code, context) => componentPlaygroundSnippet(context.args) }`: only the props that differ from their defaults, around a small real example, updating as the controls change. The builder lives in the same `.snippets.ts`. A Storybook-only control (`Card`'s `media`) is rendered into the example as real markup and never appears as a prop. **Playgrounds also serve the "args-only" stories** (`Popover`'s "With the arrow hidden", "Modal"), which would otherwise show just `{ name, args: {…} }` with no code: give them the same `transform`, which builds the snippet from that story's merged args.
- **Comments inside a story's `render` are accurate, and name no internal document,** since they used to be part of what "Show code" displayed (a `Table` story's comment cited `04-component-inventory.md` there, breaking the §4 rule and going stale once `Card` existed).
- **Enforced by `src/storySnippets.test.ts`,** which picks up every `*.snippets.ts` and fails a snippet that isn't valid TSX, uses a component or sub-part the package doesn't export, or contains a demo helper, a `.map(` loop, story-object scaffolding or a reference to an internal document; it also exercises each Playground builder across a spread of control values. It does **not** check prop names or values, so when a snippet is written or changed, typecheck it against the real components once: generate a throwaway `.tsx` that wraps each snippet in a fragment and imports the components from `./index`, run `tsc --noEmit`, then delete it (include a planted bad prop to prove the check bites).
- **Where a story's demo and its snippet would otherwise diverge, change the demo.** A story that composes a component with something since built uses the real thing (`Table`'s Ghost story uses `Card` instead of a styled `div`; `Radio`'s "Inside a RadioGroup" uses `RadioGroup` instead of a hand-wired Radix primitive that printed `<React.ForwardRef>` in the snippet).
- **Snippets can't hold state, so say so.** A controlled example (`Accordion`'s "Controlled", `Popover`'s interactive form) needs `useState`; write it as a comment above the JSX (`{/* const [value, setValue] = useState("shipping"); */}`), since a snippet is JSX only. Name where icons come from in a comment (`{/* GearIcon comes from @dbm-system/icons */}`), since snippets carry no imports. **When typechecking, import the icons from `@dbm-system/icons` in the throwaway file; don't declare them** — a declared name that doesn't exist compiles fine (`ButtonGroup`'s snippet used `BoldIcon`, `ItalicIcon` and `UnderlineIcon`, which don't exist; the package has `TextBIcon`, `TextItalicIcon`, `TextUnderlineIcon`). Declare only state and handlers. A repo-wide check: list every `…Icon` name used as an `icon`/`leadingIcon`/`trailingIcon` prop or import in a `*.snippets.ts` or `.mdx` and confirm the icons package exports it, and that no snippet uses a component that isn't built yet.
- **A component whose hidden real-browser checks outgrow its stories file puts them in `Name.checks.stories.tsx`:** its own group (`…/Name/Checks`) with `!dev` on the whole group, following [ADR-0013](adr/0013-compound-sub-part-properties-documented-via-hidden-docs-only-stories-file.md)'s way of keeping a second file out of the sidebar. What the two files share (demo code, the block they draw, the setup an app does at start) lives in a module that is not a stories file (`NameStoryKit.tsx`), and anything the checks need at load (registering a language) lives there too, since the runner loads each stories file on its own.
- **A placeholder a snippet leaves undefined says what it stands for.** `code={source}` is fine provided a comment in the snippet defines it (`{/* source: the code to show, as a string */}`) and the Docs page states the convention once; otherwise it reads as broken.
- **An icon prop can't appear in the generated snippet at all.** Storybook serializes an icon component as `{ $$typeof: Symbol(react.forward_ref), render: () => {} }` (this also happens to any non-primitive resolved arg in a `{...args}` render, such as `Icon`'s `icon`). Write the icon by name (`leadingIcon={TagIcon}`) with the comment above. A Playground *builder* can write it: the control hands it the icon component, which it compares against the icons it knows and writes back as a name. A genuinely interactive Playground whose default arg is non-primitive keeps this as an inherent limit of Storybook's source generation.
- **A control with a `mapping` hands a snippet `transform` the option key, not the mapped value.** For `{ Star: StarIcon }` or `{ Hidden: false }`, `context.args` holds `"Star"` or `"Hidden"`. A builder that only recognised the mapped value silently dropped the prop (`FieldError`'s "Without icon" snippet came out identical to the Playground's). Every icon-control builder accepts both the component and the option key, and a unit test per builder covers the key form.
- **A function prop shows its real body.** The generated snippet prints every function as `() => {}`, hiding the one thing a formatter story demonstrates (`ProgressBar`'s "With custom value label"). Write the real function. Where the function is the reader's own (a click handler, `onRemove`), name it (`onClick={handleClick}`) rather than inventing a body, and declare those names in the throwaway typecheck file.
- **A thing that only mounts after an interaction vanishes from the generated code.** `Backdrop`'s "Click to dismiss" renders the `Backdrop` only after a click, so the generated snippet showed the button and scaffolding and **no `Backdrop`**. Write the conditional in the snippet (`{isOpen && <Backdrop onClick={() => setIsOpen(false)} />}`) with the state named in a comment, and check for any overlay or toggled component that the component itself appears in every panel.
- **A builder that writes the reader's free text quotes it safely.** A control's text can hold a `"` or an `&` (which a JSX string attribute would misread) or a `<`/`{` (which JSX text would read as markup); builders write such an attribute value as `{"…"}` and escape such children via `src/snippetHelpers.ts` (`quote`, `escapeJsxText`, `truncateValue`). The guard test checks the result still parses.
- **A value the component derives from another prop is written only where it differs from the derived one.** `Heading`'s `size` follows its `level` when left out, and the Playground syncs the `size` control to the level, so the generated code printed `size="4xl"` on every heading; the builder compares against the component's own `defaultSizeForLevel`. `Link`'s `external` is auto-detected from its `href`, so the builder writes `external` only for a path that doesn't look external, and `external={false}` only for a URL that does.
- **A `.map(` over the reader's own state is fine** (a `Tag` per filter in state); a `.map(` over a stories-file constant (`allTones.map(…)`) is the scaffolding the guard test rejects. **A Playground-only control the story strips before rendering** (`ProgressBar`'s `indeterminate`, which leaves `value` out) is handled by the builder the same way: it isn't a real prop, so it never appears in the snippet.

## 5. Per-component checklist

Applied to every component, in this order. The code-level review checklist is `06-engineering-standards.md` §9; this one is the Storybook half, and where an item repeats §9's wording this one points there.

**Component correctness**
- [ ] Re-verify the full definition of done (`05-component-api-conventions.md` §8) — don't assume it still holds
- [ ] Feature-completeness pass against comparable components for the same role — name any concrete gap before adding anything, in this system's own terms without naming the library it came from (`06-engineering-standards.md` §8–§9)
- [ ] Required/recommended props present and sensibly defaulted
- [ ] Zero hardcoded values — grep-verify every CSS value traces to a token
- [ ] JSDoc complete on the component and every prop

**Storybook**
- [ ] `title` follows the taxonomy in §3
- [ ] Docs page per the §4 template, first in the group, using the shared blocks from §4.1 (`ComponentHeader`, `Callout`, `TokenRow`, `RelatedCard`, `PropertiesTable`) rather than plain `<Title />`/`<ArgTypes>`/markdown — verified visually in a running Storybook instance, not just typechecked
- [ ] `PropertiesTable`'s `order` prop lists every prop in a sequence that reads sensibly (content prop → core visual props → behavioral/state props → advanced/escape-hatch props last); docgen's default order usually isn't. Every `Canvas` in the Variants section has its own `###` subheading directly above it, matching the story's display name
- [ ] Playground story, second in the group — every prop wired through `args`/`argTypes`, nothing hardcoded via a bare `render`
- [ ] **"Show code" is pasteable on every story (§4.2)** — each visible story sets `parameters.docs.source.code` to a hand-written snippet from the component's `*.snippets.ts` (the Playground builds its own from the live controls), and the snippets were typechecked against the real components. Verified by opening every "Show code" on the live Docs page, not by reading the file
- [ ] Every controllable prop has an explicit value in the Playground's top-level `args`, matching its real component default. An arg left `undefined` renders as an inert "Set boolean"/"Set string"/"Set object" placeholder instead of a live control (on `Button`, `isLoading`/`loadingText`/`fullWidth` showed as placeholders until given explicit defaults)
- [ ] Every enum-like prop gets an explicit `select`/`radio` control; non-controllable props (icon references, refs, and any inherited native prop docgen can't cleanly infer — `Button`'s native `type` fell back to a broken "Set object" control) get `control: false` explicitly. Check the whole rendered Properties table for stray placeholders, not just the props you typed
- [ ] **Every story's Controls panel drives its canvas, checked live** by toggling a control and watching the canvas, not only in the Playground (`06` §9, "Storybook documentation", has the two failure modes and the multi-instance exception). Two conventions apply:
  - When a story's own fixed `render` ignores `args` entirely (a single-purpose Variant story, not a Playground) — an arrow `render: () => (...)` or a `render: function Name() {...}` with no parameter — give that story its own `argTypes: { propName: { control: false }, … }` for every prop its render doesn't consume, instead of leaving live-looking toggles that do nothing (`Portal`'s `Default`/`CustomContainer`/`DisabledPortal`/`AsChild`). A story-level entry needs only `control: false`; it merges over the meta-level entry per key, so the existing `description` and `table.defaultValue` still render in `PropertiesTable`, which reads component-level docgen, not a story's `args`.
  - Audit a component's fixed-render stories against its *full* set of live meta props, not a spot check: partial gaps are easy to miss (`Divider`'s 13 stories dashed seven props each but all missed `aria-label`; `Tooltip`'s two fully bespoke stories missed seven of nine).
  - Each story's shown `args` also match what's rendered, including the starting value.
- [ ] **No live control is dead in any visible story, an uncontrolled `defaultValue` control included.** An uncontrolled component keeps the `defaultValue` it first mounted with, so its control is dead unless the story remounts when it changes (a meta-level decorator `<Fragment key={String(context.args.defaultValue)}><Story /></Fragment>`). A prop the component ignores in some state (a read-only rating's `precision`) needs `control: false` in that story, or `if` where the Playground can reach the state. Check by driving every control: in the running preview, for each story and control, emit `updateStoryArgs` with a different value through `__STORYBOOK_ADDONS_CHANNEL__`, read current args from `__STORYBOOK_PREVIEW__.storyStoreValue.args` (not `story.args`, which is empty), compare `#storybook-root`'s markup, restore the original value (an `undefined` deletes the key) and wait for the markup to settle between controls. A behaviour-only control (`clearable`) leaves the markup unchanged and is covered by its tests instead.
- [ ] Every explicitly redeclared native prop (`className`, `style`, `id`, `data-testid`, the relevant `aria-*` props — `05` §3) appears in the rendered Properties table with its description, not only in the source. Storybook's default docgen (`react-docgen`, not the TS-checker-based `react-docgen-typescript`) silently dropped `aria-label`, `aria-labelledby`, `className`, `id` and `data-testid` from `Button`'s table although each had its own JSDoc'd declaration, while a sibling (`type`) showed fine. JSDoc on the type alone is not evidence of a working table entry. When docgen drops one, add an explicit `argTypes` entry with its own `description` (and `control: false` for props like `id`/`data-testid`/`className`).
- [ ] Every row in the rendered Properties table has a non-empty Description — a different failure from the previous item (the row exists, but docgen extracted no JSDoc text). Plain native props (`children`, `disabled`, `onClick`, `style`) commonly come through empty. Fix with an explicit `description` in the story's `argTypes`.
- [ ] Every row carrying a real JSDoc `@default` shows it in the Default column — a third failure (row and description fine, Default silently empty). Check each row against the type file's own `@default` tags (§4.1 Pitfalls, `06` §9).
- [ ] Docs page has the visually hidden `<VisuallyHidden asChild><h2>Intro</h2></VisuallyHidden>` before `<ComponentHeader>` (§4 item 1), `### Import` nested under it (not its own `##`), and every other template section's `##` heading text matches §4's list verbatim — the TOC is generated from these headings, so a reworded title silently breaks "the same tabs on every page". `<PlaygroundControls exclude={[...]}>` lists every prop with a non-editable control; check the rendered Playground for stray "–" rows, which mean something was missed.
- [ ] A demo box with `resize` (which needs an `overflow` other than `visible`) has padding at least as wide as a focus ring's reach (6px: a 4px offset and a 2px line), or it clips the ring of a control at its edge, leaving only the sides that fit (`Breadcrumb`: two vertical bars instead of a ring)
- [ ] At least one `play`-function interaction story for interactive components
- [ ] **A story that is *shown* (sidebar or Docs page) must not end in a different state from the one it starts in.** Storybook runs a story's `play` function every time it is opened, so a play that clicks, types or resizes makes the demo visibly animate and settle somewhere unexpected (a pagination that starts on page 42 and ends on page 1). Keep the visible story play-free (or, if its play only measures, leave it) and put any state-changing interaction in a hidden twin: `export const XInteraction: Story = { ...X, name: "… — interaction test", tags: ["!dev"], play: … }`. Hidden from the sidebar and Docs, it still runs as a test. **Write `!dev` on the story itself:** Storybook's indexer reads `tags` only from a literal property, so a tag arriving through a spread (`...hidden`) is ignored and the story stays visible; `src/storyTags.test.ts` fails any story named "… — interaction test" without a literal tag. Where a demo is really about an interaction, give the person a way to do it themselves (a `resize: horizontal` box) instead of scripting it. A hidden story is also the place for a **pure test with no visible counterpart** — right-to-left order, a container that must re-measure as its content changes, a real-browser layout measurement — provided it renders what it needs itself (`Pagination`'s `RightToLeftInteraction`, `FitContainerDigitsInteraction`, `LabelsInteraction`).
- [ ] Behaviour that changes at a breakpoint (a padding step-down, a layout that stacks) is *asserted*, not only checked by hand. A jsdom test can't evaluate a media query, so give it a story pinned to a phone width with `globals: { viewport: { value: "mobile1", isRotated: false } }` and a `play` that first asserts `window.innerWidth` is below the breakpoint (so it fails loudly if the viewport didn't apply) and then asserts the computed values, measured against what the requirement names (a "full-width" action against the container's content box, not its own wrapper, which can shrink to fit and pass trivially). The vitest addon applies that global (its default test viewport is 1200px wide), and the Storybook UI resizes the canvas when the story is opened on its own; on a Docs page the story sits in the wide page like any other, so say so above it. Confirm the assertion bites by breaking the CSS once and watching it fail (`EmptyState`'s "On a phone" story).
- [ ] Remaining showcase stories (`AllVariants`, etc.) audited — kept where they add value as static references, converted to args-driven where feasible, removed if redundant with the Playground/Docs gallery
- [ ] Visual correctness spot-check across all four themes (both brands × light/dark)
- [ ] Dead/redundant stories cleaned up, consistent naming

## 7. Foundations pages

A second top-level Storybook sidebar group, **`Foundations`**, sorted to appear *before* `Atoms` (the `groupPriority` array in `preview.tsx`'s `storySort`: top-level group order isn't alphabetical by default, so it has to be forced). Ten standalone reference pages, with no components and no stories, cover every token category shipped in `packages/tokens`: one page per token category, with Color and Typography given the most detail as the highest-leverage categories.

**Page list, in reading order** (`packages/components/src/foundations/*.mdx`, each a standalone `<Meta title="Foundations/X" />` page with no `of=` prop, since there is no component or story behind it): Overview, Color, Typography, Spacing, Radius, Shadows, Motion, IconSizes, Miscellaneous (border width, opacity and z-index, grouped because each alone would be a near-empty page), Breakpoints. The explicit `foundationsOrder` array in `storySort` keeps this sequence, since alphabetical would scatter `Overview` into the middle.

**Data source — read live, never retyped by hand:** every value on every Foundations page comes from `@dbm-system/tokens`'s built JS export (`import { primitives } from "@dbm-system/tokens"`) rather than being copied from the JSON source or hardcoded in the MDX, so the pages can't drift from the real token values. Semantic (per-theme) tokens use the same `var(--dbm-{token})` CSS-custom-property mechanism `TokenRow` uses in component docs (§4.1), so they are live-reactive to the Brand/Mode toolbar like every other themed swatch.

**Keeping `Color.mdx` complete and in order.** "Read live" covers each token's *value*, not *which tokens appear at all*. `Color.mdx`'s `<SemanticSwatchGrid tokens={[{ token: "bg.brand", usage: "..." }, ...]} />` arrays are hand-maintained, because each entry pairs a token name with a `usage` description a script can't author. `SemanticSwatchGrid` resolves any token name it is given, but a new semantic token doesn't appear on the page until someone adds its entry. So:
- **When adding a semantic token, also add it to `Color.mdx`'s matching category array** (`bg.*`/`text.*`/`border.*`/`icon.*`), immediately after its most related token and in the semantic JSON files' own key order (`packages/tokens/src/semantic/*.json`). Reorder the JSON source first and match `Color.mdx` to it, not the other way around.
- **Group by family, not by when a token was added:** base, base-hover, subtle, subtle-hover, then the next family (`border.danger` immediately followed by `border.danger-subtle`, then `border.warning`/`border.warning-subtle`, and so on), not all the bases together followed by all the `-subtle`s, and not new tokens clustered at the end.
- **Presence is enforced, order is manual.** The Foundations token-coverage check (§10) fails when a semantic token is missing from `Color.mdx` or `Color.mdx` references one that no longer exists. Nothing checks order; re-read the surrounding entries in both files before adding a token.
- Every other Foundations page (Radius, Spacing, Shadows, Motion, IconSizes) renders its scale by iterating `primitives.*` at render time (`RadiusScale`, `SpacingScale` and the like in `.storybook/blocks/foundations/`), so a new primitive step appears there without any check.

**Shared blocks** (`.storybook/blocks/foundations/*.tsx`, separate from the component-docs blocks in `.storybook/blocks/` directly, imported via `.storybook/blocks/foundations`): `ColorScaleGrid`/`ColorSwatch` (primitive color scales), `SemanticSwatchGrid` (theme-reactive semantic color tokens), `SpacingScale` (bar-chart visualization), `RadiusScale` (rounded-box visualization), `ShadowScale` (elevation cards on a light/dark-matched background), `MotionScale` (replayable animated demo, isolating the duration axis and the easing axis separately rather than a combinatorial grid), `TypeSpecimen` (the font-size scale at real rendered size), `IconSizeScale` (the real `Icon` atom at each size step), `TokenReferenceTable` (a generic Name/Value/Usage table, reusing `.dbm-proptable` styling for the small non-visual scales).

### 7.1 `<ThemeSync />`

**Every Foundations page must render `<ThemeSync />`** (from `.storybook/blocks/foundations`) once, anywhere in the file. Without it, every semantic-token swatch, every `RelatedCard` border, and anything referencing `var(--dbm-bg-*)`/`text-*`/`border-*`/`icon-*` on that page silently resolves to nothing.

**Why:** `preview.tsx`'s `withTheme` decorator sets `document.documentElement.dataset.theme` from the Brand/Mode toolbar globals, which is what makes the theme-scoped semantic CSS (`:root[data-theme="..."] { ... }`) resolve at all, and it runs only when Storybook renders an actual **story**. Every component's `ComponentName.mdx` embeds at least one `<Canvas>`, so the decorator fires as a side effect and the attribute is set for the whole page (a shared `document.documentElement` mutation, not scoped to the Canvas). A Foundations page has no `<Canvas>`/`<Story>`, so the decorator never runs and `data-theme` is never set (`getComputedStyle(document.documentElement).getPropertyValue('--dbm-border-default')` is an empty string). The same applies to any Docs page with zero embedded Canvases (§4.1, `ThemeProvider`).

**How `ThemeSync.tsx` works, and the two rules behind it:**
1. **Listen for `UPDATE_GLOBALS`, not `GLOBALS_UPDATED`.** `GLOBALS_UPDATED` is the natural choice but only round-trips once the preview has an active story to apply the change to, which a story-less page never has. `UPDATE_GLOBALS` (the command the manager sends on every toolbar interaction, from `storybook/internal/core-events`) fires regardless, but carries only the *changed* keys (`{ mode: "dark" }`), so merge it onto a running snapshot rather than treating it as the full set.
2. **Bootstrap that snapshot from `document.documentElement.dataset.theme` on mount, not a hardcoded default.** A globals change re-renders the whole Docs container, which remounts `ThemeSync` and resets its React state straight back to the default, clobbering the change just applied. The attribute survives the remount even though the component's state doesn't.

### 7.2 `<VisuallyHidden asChild><h2>Intro</h2></VisuallyHidden>`

**Every Foundations page renders this heading too**, immediately after `<ThemeSync />` and before the page's real `# Title`, mirroring the component-docs pattern in §4 item 1. It gives the TOC (§4.1) an "Intro" entry that scrolls to the very top of the page, and, by the same mechanism as §4.1's `.sbdocs-content h2` note, spares the page's first visible section (for example "Primitive scales" on the Color page) the `:first-of-type` margin collision. Import: `import { VisuallyHidden } from "../atoms/VisuallyHidden";` (relative to `src/foundations/`).

## 8. Token usage in Storybook-only code

Everything under `.storybook/` and every `*.stories.tsx` and Foundations `*.mdx` file is Storybook tooling, not shipped component code, but per `CLAUDE.md`'s token-first rule it still references `var(--dbm-*)` tokens wherever a token exists, rather than hardcoding. Three standing exceptions, not oversights:
- **`.storybook/theme.ts`** — Storybook's `theming/create()` API takes a literal JS object read by the manager UI, which runs outside our CSS entirely; every hex/px value there is traced to its source token in an inline comment instead.
- **CSS media-query breakpoints** (`docs.css`) — `var()` cannot appear inside an `@media` condition; these stay literal, cross-referenced to the matching `breakpoint.*` token in a comment.
- **Story-file demo-wrapper container sizing** (`width`/`maxWidth`/`height` on a story's outer wrapper `<div>`, e.g. `maxWidth: "24rem"` around an `Input` demo) — the `space.*` scale tops out at `space.32` (8rem) and is calibrated for gaps, padding and margins, not arbitrary layout container widths; forcing these onto the nearest token would visibly cramp story layouts. They stay literal, a deliberate scope boundary.

## 9. Manager-chrome customizations are version-fragile — re-verify after any Storybook upgrade

`.storybook/manager.ts`'s sidebar and mobile-drawer customizations (brand logo layout, Settings-gear repositioning, the mobile popover, Close-button position, theme-sync via the addons channel) rely on Storybook internals that are not a stable public contract, not the official theming API:
- `SET_GLOBALS`/`UPDATE_GLOBALS` imported from `storybook/internal/core-events` — the `/internal/` path is explicitly unstable.
- CSS overrides keyed to `aria-label` and DOM structure found by inspecting rendered output (`.sidebar-header`, `button[aria-label="Settings"]`, `a[aria-label="About Storybook"]`, etc.), not documented Storybook API.
- The mobile popover's capture-phase click interception, which depends on how Storybook currently wires its own click handling.

**After merging any Storybook version bump (a manual dependency-refresh pass, or a security fix), manually re-verify in the browser, on both desktop and mobile viewports, in both light and dark:** the brand logo layout, the Settings gear popover (desktop) and its mobile-popover equivalent, the mobile drawer's Close-button position, and Brand/Mode theme-sync across the sidebar, toolbar, panel and Foundations pages. A clean `pnpm install` and build is not sufficient evidence these still work: they can silently stop matching without any error.

## 10. CI & build reliability

Standing checks around the Storybook build. None of them changes what ships in `@dbm-system/components`; they harden the tooling. How the CI jobs are organized is in `02-tech-stack-and-structure.md`'s CI row.

- **`pnpm audit`** (`ci.yml`) runs on every push (`02` §3.1 covers the remediation pattern and the accepted advisories).
- **`pnpm build-storybook`** (`ci.yml`) builds the static production site (`storybook-static/`). The Playwright visual-regression suite (`test:visual`) targets the `storybook dev` server, not the static build, so without this step a broken static build could ship undetected; public Storybook hosting is a Phase 9 goal.
- **Bundle-size tripwire** (`packages/components/scripts/check-storybook-bundle-size.mjs`, run right after the build) — no dependency; checks the total `storybook-static/` size and the largest single Vite-bundled chunk under `assets/` against a budget. It excludes `sb-manager/`/`sb-addons/` (Storybook- and addon-owned bundles, not ours to fix) from the per-chunk check. The separate per-component check of the published package (`check-component-bundle-size.mjs`) is in `06-engineering-standards.md` §4.
- **`.storybook/**` is type-checked:** `.storybook/tsconfig.json` plus a `typecheck:storybook` script chained onto `lint` (`packages/components/tsconfig.json` includes only `src`). One narrow, explained exception: `preview.tsx`'s `storySort` function can't carry real type annotations, because Storybook statically extracts its source and `eval`s it as plain JS before any TypeScript transpilation, and inline types fail `build-storybook` outright (`SyntaxError: Unexpected token ':'`). It uses a commented `@ts-expect-error` instead.
- **`storybook-static/**` is in the shared ESLint ignore list** (`packages/eslint-config/base.js`): a local `build-storybook` followed by `pnpm lint` otherwise feeds about 21,000 bogus errors from minified output into ESLint.
- **Storybook telemetry is disabled** (`core.disableTelemetry: true` in `main.ts`), matching the project's free/OSS-only, no-phone-home posture (`CLAUDE.md`).
- **Foundations token-coverage check** (`packages/components/scripts/check-foundations-token-coverage.mjs`, run right after `pnpm build`) reads every semantic token (`bg.*`/`text.*`/`border.*`/`icon.*`) from the built `@dbm-system/tokens` package (unioned across all four brand/mode theme exports) and diffs it against every `token: "..."` in `Color.mdx`, failing with the exact missing or stale list. Only Color needs it (§7).
