# DBM System — Component API & Coding Conventions

This is the contract every component follows, regardless of which build phase or Claude Code session creates it. Consistency here is what keeps a 100+-component system feeling like one system instead of 100+ one-off decisions.

---

## 1. File structure (one folder per component)

```
packages/components/src/{tier}/{ComponentName}/
├── ComponentName.tsx          # implementation
├── ComponentName.module.css   # scoped styles, tokens only
├── ComponentName.types.ts     # exported prop types/interfaces
├── ComponentName.stories.tsx  # Storybook stories, one per variant/state
├── ComponentName.snippets.ts  # hand-written code for each story's "Show code" button (ADR-0020)
├── ComponentName.mdx          # the Docs page (07-storybook-and-documentation-standards.md §4)
├── ComponentName.test.tsx     # unit + interaction tests
└── index.ts                   # barrel: re-exports component + types
```

Optional files, each present only when it applies:

- `ComponentName.checks.stories.tsx` — hidden real-browser checks, when they outgrow the stories file (`07-storybook-and-documentation-standards.md` §4).
- `ComponentName.docs.test.ts` — a guard that the Docs page's "Design tokens used" table matches the stylesheet (`06-engineering-standards.md` §9).
- `ComponentName.ssr.test.tsx` — a server render and hydration check, for a component that creates a DOM node or a portal of its own (`06-engineering-standards.md` §9).
- Helper modules split out of a large component, named for what they hold (`useDatePickerValue.ts`, `DatePickerPanel.tsx`, `dateRangeValue.ts`, `Combobox.match.ts`), each with its own test where it has logic of its own (`06-engineering-standards.md` §1).
- `ComponentPart.stories.tsx` — for each sub-part of a compound component, a hidden docs-only file that documents the sub-part's props on the parent's Docs page ([ADR-0013](adr/0013-compound-sub-part-properties-documented-via-hidden-docs-only-stories-file.md)).
- `*Context.ts` — a context shared by a component and its sub-parts, or read by atoms (§3, "A molecule that configures the atoms inside it").
- `*Store.ts` — state held outside React for a component with an app-wide, imperative surface (`Toast`'s queue), read with `useSyncExternalStore`; one per provider, no module-level state (§3).

**A component with no visual output of its own has no `ComponentName.module.css`** — one that renders no styled element of its own, or that draws entirely through other DBM components it composes. Today: `Box` (passes `className`/`style` through to whatever `as` renders), `ClientOnly` (renders `children`/`fallback` with no wrapper), `FocusTrap` and `Portal` (behavior-only wrappers of Radix primitives), `SearchInput` (styled entirely by the `Input`, `Icon` and `Spinner` atoms it composes), `ConfirmDialog` (drawn entirely by the `AlertDialog` it wraps, with `Input`, `FormField` and `Spinner`), and `RangeSlider` (drawn with `Slider`'s stylesheet, which it imports, since the two must look identical). Don't add an empty stylesheet to satisfy this list; if such a component later gains a style of its own, it gets a module then. `ThemeProvider` similarly has no `*.snippets.ts`, since its Docs page has no story demos (`07-storybook-and-documentation-standards.md` §4.2).

**A component may import another component's CSS module when the two must look identical and change together** (`RangeSlider` draws with `Slider`'s, `AlertDialog` with `Dialog`'s, `DateRangePicker`'s panel with `DatePicker`'s). The later component imports the earlier one's, never the reverse; the shared module's class names become a contract between them (a rename needs the usual go-ahead for a Finalized component and a check that the importer still looks the same); each component's Docs-token test reads both stylesheets, and `check-component-bundle-size` counts the imported code in the importer. Extract to `internal/` when a third component needs the same rules: the overlay sections (header, body, footer, the corner close button and the `divided` lines) were, when `Drawer` was built, and `Dialog`, `AlertDialog` and `Drawer` draw them from `internal/overlay/` while each keeps its own panel ([ADR-0060](adr/0060-the-overlay-sections-are-extracted-to-internal-overlay-with-the-panel-staying-each-components-own.md)). The floating option list of `Combobox` and `MultiSelect` (the panel, rows, matching, windowing and layout hooks, and the in-field buttons) is in `internal/optionList/`, extracted at the second consumer because the third (`CommandPalette`) is certain and what is shared is code, not only a stylesheet ([ADR-0123](adr/0123-the-floating-option-list-is-shared-by-combobox-and-multiselect-through-internal-and-multiselect-draws-tagsinputs-box-and-chip-over-copying-them-or-adding-a-multiple-prop-to-combobox.md)); `MultiSelect` draws its box and chips with `TagsInput`'s stylesheet and chip, the first case above.

`{tier}` is `atoms`, `molecules`, or `organisms` per `04-component-inventory.md`. Compound components (see §4) get one folder containing all their parts, not one folder per sub-part.

## 2. Naming conventions

- **Component names:** PascalCase, matching the name in `04-component-inventory.md` exactly (`DataTable`, not `DataGrid` or `Table2`).
- **Props:** camelCase. Booleans read naturally without an `is`/`has` prefix when mirroring a native HTML attribute (`disabled`, `required`, `checked` — matches what an agent or developer already knows from HTML). Custom booleans not mirroring HTML use a clear prefix (`isLoading`, `hasError`).
- **Event handler props:** `onXxx` pattern. Use `onChange` only when wrapping a native form element 1:1; use `onValueChange` for custom/controlled values (e.g., `Select`, `Slider`, `DatePicker`) to avoid ambiguity with the native DOM event.
- **Size prop:** always `size`, always the same scale across every component that has one: `xs | sm | md | lg | xl`, mapped to the spacing/icon-size tokens — never invent a component-specific size scale. **Established exception:** components whose `size` drives typography or icon dimensions directly (`Text`, `Heading`, `Icon`) use the *full* underlying token scale instead — the font-size scale has 11 steps (`xs` through `6xl`, including `base`) and icon-size has 7 (`xs` through `3xl`), and forcing those into the generic 5-step scale would lose real steps the token layer already defines. This still satisfies "never invent a component-specific size scale": each maps onto one canonical, pre-existing token category, just a wider one.
- **Visual style prop:** always `variant` for stylistic variants (`primary | secondary | tertiary | ghost | destructive`). Never use `type` for this (reserve `type` for native HTML semantics, e.g. `<Input type="email">`).
- **Variant names come from one shared vocabulary — a bordered variant is `outlined`, never `outline`.** Reuse the name an existing component already uses for a treatment rather than coining a synonym. For a border that name is **`outlined`**: `outline` is the CSS property (a focus ring is one), so it is not a variant value. `bordered` is a different treatment — a bordered *group* — and stays on `Accordion` and `Table`. Before naming a new variant, list the existing ones (`grep -rn "Variant =" packages/components/src`) and reuse a name if one fits; a component may still add a name only it needs (`Tabs`' `underline`).
- **In a group-style molecule, `variant` is the look of the controls inside it, and the container's own look has another name (`surface`).** `ButtonGroup`'s `variant` is its buttons' style, `ToggleGroup`'s is its items' look and `Pagination`'s is its controls' treatment, so `Toolbar`'s `variant` is its items' and the bar's own `ghost`/`outlined`/`filled` is `surface` (the shared names, under a different prop). A component whose own look is what `variant` names (`Card`, `EmptyState`) is a container, not a group of controls, and keeps it. An agent that has read one group component writes `<Toolbar variant="secondary">` by analogy, which is why the name has to be the same across them.
- **Status/meaning prop:** always `tone` for feedback-type coloring (`info | success | warning | danger | neutral`; some components also offer the non-status `brand` and `highlight`, the system's identity colour and its general highlight and accent colour), kept separate from `variant` — a `variant="ghost"` `Alert` with `tone="danger"` should be a valid, meaningful combination.

## 3. Standard prop patterns every component follows

- **Always `forwardRef`.** Every component forwards its ref to the underlying DOM element — required for Radix composition and for consumers who need direct DOM access. **Narrow, explained exception:** a component with no single root DOM node of its own takes no `ref` prop at all, rather than forwarding to an arbitrary or wrong element — e.g. `Tooltip` (the trigger is an arbitrary child, the content renders in a portal) and `ClientOnly` (renders `children`/`fallback` directly, no wrapper). Each exception justifies itself in its own component-level JSDoc, matching Radix's own precedent (`Tooltip.Root` takes no ref either). **Conditional variant:** a component that can render a *variable* number of root-level elements depending on runtime content (`Highlight`'s `query` auto-matching renders zero, one or many `<mark>`s) still declares `forwardRef` and attaches the ref only when exactly one such element exists, not unconditionally undefined and not to an arbitrary one of several. Document the exact condition in the prop's own JSDoc.
- **Always extend native props where applicable.** `interface ButtonProps extends React.ComponentPropsWithoutRef<'button'> { variant?: ...; size?: ...; }` — don't redeclare `onClick` or other event handlers that HTML already provides. The one exception is the next bullet.
- **Always accept `className`, `style`, `id`, and `data-testid`, and redeclare all four in the component's own `*Props` interface with JSDoc** (one narrow exception: a part whose `id` the parent generates and points an `aria-*` attribute at takes no `id`, as `Dialog.Title` and `Dialog.Description` don't, since a replaced id would leave the reference dangling). `className`/`style` are the standard escape hatch (internal styles use CSS Modules, but consumers can extend); `id` is needed whenever another element's `aria-labelledby`/`aria-describedby`/`htmlFor` must point at this component, or a test/router needs a stable anchor; `data-testid` is a plain, behavior-free pass-through for automated testing. They all compile without the redeclaration (`className`/`style`/`id` come from `ComponentPropsWithoutRef`, and TypeScript exempts any `data-*`/`aria-*` attribute from prop checking), so the reason to redeclare is documentation: **Storybook's default docgen (`react-docgen`, not the TS-checker-based `react-docgen-typescript`) does not reliably surface inherited-only native props in the Properties table**, and they went missing until each had its own local JSDoc'd declaration (`07-storybook-and-documentation-standards.md` §5 has the Storybook-side fix when JSDoc alone isn't enough).
- **Always spread `{...props}` *before* a component's own computed `role`/`aria-*`/similar attributes in the JSX, never after.** Later-declared JSX attributes override earlier ones, so a computed attribute placed before the spread lets a same-named consumer prop silently win (a consumer-passed `aria-hidden` overriding a loading indicator's own computed one; a `role`/`aria-orientation` computed fresh at each responsive breakpoint being replaced by a stale consumer value). This holds whether or not the prop falls under the `data-*`/`aria-*` typecheck exemption — `Omit`-ing a name from the props type doesn't stop a consumer passing it. **It applies to attributes a wrapped Radix primitive computes itself too:** Radix sets `data-orientation` on `Tabs`' root and `aria-orientation` on its list *before* spreading the props it is given, so compute them again in the JSX, after `{...props}`, from the value actually in effect. Check this on every component review (read the JSX, confirm `{...props}` comes first), and add a regression test proving the same-named prop can't win.
- **Redeclare component-relevant `aria-*` props explicitly**, for the same documentation-visibility reason — not every possible ARIA attribute, just the ones that matter for that component's role: `aria-label`/`aria-labelledby` on most interactive atoms (an icon-only control effectively requires one), `aria-pressed` on toggle-style controls, `aria-expanded`/`aria-controls` on disclosure triggers, `aria-haspopup` on menu/dialog triggers, `aria-describedby` on form controls commonly paired with helper/error text. Every component already passes *any* `aria-*` attribute through at runtime via native prop inheritance; this is about making the relevant ones discoverable.
- **Controlled/uncontrolled pattern:** any component holding internal state (`Switch`, `Tabs`, `Accordion`, `Select`) accepts both `value`/`onValueChange` (controlled) and `defaultValue` (uncontrolled), mirroring Radix. **Narrow exception:** a component with no internal trigger of its own (visibility entirely driven by whatever composes it, as with `Backdrop`) takes a plain `open?: boolean` instead of the full trio, since `defaultOpen`/`onOpenChange` would be dead API surface. See `guidelines/adr/0010` for the reasoning and the Radix `Presence`-driven exit-animation pattern this pairs with.
- **Minimize required props.** Every prop should have a sensible default wherever possible — fewer required props means fewer ways for an agent (or a person) to call a component incorrectly. A component should render something reasonable with zero props where that's plausible.
- **`asChild` support** on components where composability matters (`Button`, `Link`, trigger-style components) — follows the Radix Slot pattern, letting a consumer render the component's behavior onto a different element (e.g., `<Button asChild><Link href="/x">Go</Link></Button>`).
- **`as` vs `asChild` — pick based on where the visual content comes from.** `asChild`/Radix `Slot` fits a component whose rendered content genuinely *is* `children` (`Button`'s label, `Link`'s text). The plain polymorphic `as` prop (`Stack`/`Container`/`GridItem`, also `Avatar`) fits a component that generates substantial visual content of its own from props rather than from `children` — `Slot` can't keep that content rendering alongside a slotted child. See `guidelines/adr/0007`.
- **`disabled` on an `as`-polymorphic interactive component:** apply the native `disabled` attribute only when `as` resolves to an element that supports it (in practice `as === "button"`); on an arbitrary element type it does nothing (an `<a disabled>` is ignored by the browser). For every other `as` value, apply `aria-disabled` plus a click-handler guard that blocks the event, as `Button`'s `asChild`-disabled handling does. The guard stays focusable rather than leaving the tab order, matching WAI-ARIA APG guidance for `aria-disabled` (native `disabled` removes focusability).
- **`disabled` on a component whose interactive root is never a native interactive element (no `as`/`asChild` at all, e.g. `Tag`):** the same `aria-disabled` + blocked-handler + stays-focusable pattern applies unconditionally, with no native-element branch to special-case. Gate `disabled` on the component's own "is this interactive at all" condition (`Tag`'s `isInteractive`, true when any of its click or toggle props is set); a component with no interactive affordance has nothing to disable, and warns once in development if `disabled` is passed anyway (`06-engineering-standards.md` §9, "invalid prop combinations fail loud").
- **`disabled`'s click-guard must be `onClickCapture`, not `onClick`, on any component supporting `asChild`.** Radix `Slot` composes bubble-phase `onClick` handlers with the slotted child's *own* `onClick` running first and the component's guard second, so a bubble-phase guard blocks only the component's own action, not a side effect the child's handler already ran (a router's navigation declared directly on the slotted element). `onClickCapture` runs before any bubble-phase handler regardless of `Slot`'s composition order. `Button` and `IconButton` use it (a caller's own `onClickCapture` still runs when the click isn't blocked); tests assert the slotted child's handler is not called when disabled, loading or in a disabled group.
- **Text a component supplies itself is a `labels` object; numbers it displays go through an optional `formatNumber`** ([ADR-0021](adr/0021-labels-object-and-optional-formatnumber-over-an-implicit-intl-default.md)). One optional `labels?: Partial<…Labels>` prop holds every accessible name, summary and field label the component writes, with English defaults; a label that needs numbers is a function of the *plain* numbers. A component that shows numbers also takes `formatNumber?: (n: number) => string`, defaulting to `String`, used for the digits on screen *and* by the default label functions, so a control's visible text is always inside its accessible name (WCAG 2.5.3). A consumer's own label functions get plain numbers and write them with the same function; callbacks (`onValueChange`) and native `<input type="number">` fields keep plain numbers. Never default to `Intl` or the browser's locale: it changes existing output and makes server and client text differ (a hydration mismatch). Where a control's visible words and its accessible name are separate labels (`previousText` beside `previous`), warn in development if the name stops containing the words.
- **Text that joins two formatted numbers isolates each one** (`RangeSlider`): a script with right-to-left digits (Arabic-Indic) pulls the separator between two of them into its own right-to-left run, so a left-to-right page draws "20 – 80" as "80 – 20". Wrap each number in a bidirectional isolate (U+2068 … U+2069) and test it in a real browser, since jsdom lays out no text.
- **A component that lets one function replace the whole text** (`ProgressBar`/`ProgressCircle`'s `formatValueLabel`, `Indicators`' `formatLabel`/`getLabel`) does the same job at whole-label granularity and keeps that shape.
- **A control's accessible name holds its visible text as whole words, in order** ([ADR-0112](adr/0112-an-interactive-controls-accessible-name-holds-its-visible-text-as-whole-words-in-order-over-a-name-that-only-means-the-same.md)): a button shown as "Jan" is not named "January" alone ("Jan, January"), and one showing "JD" is named "Jane Doe, JD". WCAG 2.5.3 (Label in Name, Level A); the real-browser tests run axe's `label-content-name-mismatch` on every story.
- **A molecule that configures the atoms inside it does so through an optional context defined beside those atoms and read by them — not `cloneElement`, and never an import from the molecule (an atom may not import from one)** ([ADR-0025](adr/0025-buttongroup-shares-settings-through-a-context-read-by-button-and-iconbutton.md), `ButtonGroup`). The context is `null` outside the molecule, so the atom is unchanged there; the atom's own prop always wins over the molecule's default, with `disabled` the one setting that is OR-ed. Reading it means a prop can no longer be a destructuring default (the atom can't tell an explicit value from an absent one), which also blanks docgen's Default column for it: state each default in the stories' `argTypes` (`07` §4.1). `EmptyState`'s internal size context is the same idea for a molecule's own sub-parts, and `Toolbar` reuses `ButtonGroup`'s context rather than adding a second one ([ADR-0032](adr/0032-toolbar-puts-radix-toolbar-roving-focus-behind-wrapper-parts-and-reuses-buttongroups-context.md)); its items join the arrow-key order through wrapper parts, not automatically. **A context crosses a portal, so an overlay that draws consumer content in one wraps it in `ButtonGroupReset`** (from `atoms/Button/buttonGroupContext`), or a button in a dialog or popover opened from inside a group takes the group's settings ([ADR-0102](adr/0102-overlays-put-their-content-out-of-reach-of-a-button-groups-settings-over-letting-them-cross-the-portal.md)).
- **A part you control from outside is asked by a gesture inside the component, not changed by it** ([ADR-0039](adr/0039-a-handle-only-asks-a-controlled-pane-to-collapse.md), `Splitter.Pane`'s `collapsed`). When a prop makes a value controlled, an interaction in the component that would change that value calls its `onXxxChange` with the value it wants and leaves the value alone until the prop changes. Changing it and also re-applying the prop afterwards looks the same until the usual `onXxxChange={setX}` wiring, where the stale prop and the new state undo each other in the same commit and React ends with "Maximum update depth exceeded" — which only a real browser run showed, since every unit test that pressed the key passed. Don't report a change the prop itself made, and test the pair wired to state, not each half alone.
- **A Radix-wrapping component with a direction exposes `dir?: "ltr" | "rtl"`, passed to the primitive and defaulted, not read from the page** (`Tabs`, `Accordion`, `RadioGroup`, `Slider`, `RangeSlider`, `Toast.Provider`). A component built on native radios (`RatingInput`) exposes it the same way, and handles Left and Right itself in `rtl`, since browsers disagree on whether a native radio group's arrows follow the direction it is drawn in. Whether the result mirrors is ADR-0009's per-component call. A library-wide answer for inheriting the page's direction (a `DirectionProvider`) is undecided and would cover every Radix component together (`01-vision-and-goals.md` §12).
- **`autoFocus` only works on a native form control.** React focuses a `button`, `input`, `select` or `textarea` on mount and nothing else, so forwarding `autoFocus` onto a `role="slider"`, `role="tab"` or other `span`/`div`-based control does nothing. Focus it from a ref in an effect (`useEffect(() => { if (autoFocus) ref.current?.focus(); }, [autoFocus])`) and test that the element really has focus after mount.
- **A field a person types into takes text inserted all at once, not only keys.** A phone's keyboard, an autofill and a paste deliver a whole string in one `input` event with no usable key events, so a component that reads `keydown` alone, or takes only the last character of an insertion, silently mangles it (typing "041" through the browser's own text insertion gave "01" in `TimePicker`). Handle `keydown` for what only a key can say (arrows, `Backspace`), and feed the inserted text (`InputEvent.data`) through the same code one character at a time, threading the state through the whole string. Test it with `Input.insertText` in a real browser as well as a dispatched `input` event in jsdom.
- **A field made of several focusable parts reports focus and blur once, as one field** ([ADR-0030](adr/0030-timepicker-holds-its-report-with-commiton-and-validates-through-a-hidden-time-input.md)). `onFocus`/`onBlur` fire on arriving at and leaving the whole thing, judged by DOM containment plus an `inside` flag (a portaled popover is part of the field though React bubbles its events), not once per part. A field that reports a value as it is edited offers `commitOn` to hold the report until the person is done, and validates through a real (visually hidden, not `display: none`, not `type="hidden"`) control so a surrounding `<form>` can refuse it.
- **A group or other container role doesn't take `aria-invalid` or `aria-required`; the focusable parts do.** `role="group"` supports neither, so a field made of several inputs puts both on each of them (`jsx-a11y/role-supports-aria-props` catches it); the group keeps its name (`aria-label`/`aria-labelledby`), `aria-describedby` and `aria-disabled`.
- **When a component wraps its element in a frame only in some modes, `className` and `style` go on the outermost box in every mode; `ref`, `id`, `data-testid` and the `aria-*` props stay on the element that carries the role** (`Toolbar`'s default `overflow="scroll"` puts the bar in a frame; `Tabs` forwards to its list for the same reason). Otherwise a consumer's margin or width lands *inside* the frame in one mode and on the component in another. State the split on the props' JSDoc and the Docs page, and test both modes for where each prop landed.
- **`scrollContainerRef` for any component that watches or acts on scroll position:** a `RefObject<HTMLElement | null>`, `undefined` by default (falling back to `window`/the page's own scroll). It is on `Affix`, `BackToTop`, `Alert`'s `sticky` (passed through to the `Affix` it composes) and `TableOfContents`, with the same name and shape. Any future scroll-aware component (an infinite-scroll list, a scrollspy nav) reuses this exact name and shape. It changes only what is *measured or scrolled*, never a `position: fixed`/`sticky` element's own rendered position, which stays relative to the viewport (or the nearest transform/filter/contain ancestor); `BackToTop`'s Docs page says so, so it isn't assumed to behave like a container-relative position.

- **A component with an app-wide, imperative surface is a provider, a hook and a declarative twin, with its state in a per-provider store** ([ADR-0070](adr/0070-toast-is-raised-from-code-through-a-provider-and-a-hook-with-a-declarative-toast-beside-it-over-a-module-level-function-or-component-only-use.md), `Toast`). The provider holds the state and draws the region; a hook returns functions whose identity never changes; the same parts can be drawn from your own state; and a `create…()` factory serves code with no component, handed to one provider. Nothing is held at module level, so two providers or two server renders never share state, and nothing touches `window` while rendering.
- **A component code needs to open, close or drive from outside takes a `controllerRef` and offers the same object from a hook inside it** ([ADR-0076](adr/0076-form-rules-may-return-promises-and-the-form-is-reached-from-outside-by-a-controller-and-two-hooks-over-synchronous-rules-or-an-imperative-ref.md), `Form`; [ADR-0120](adr/0120-contextmenu-is-opened-from-code-by-sending-radixs-trigger-a-contextmenu-event-through-a-controller-and-an-openonkeys-prop-over-rebuilding-the-trigger.md), `ContextMenu`). The object's identity never changes and its methods read the latest state; a method says whether it had anything to do (a boolean) rather than throwing; outside the component the hook returns an inert object and warns in development.
- **A floating panel with a touch-screen form takes `presentation`, a mobile-first map, and the sheet is the same component drawn differently** ([ADR-0121](adr/0121-menus-sheet-is-the-same-radix-menu-pinned-to-the-bottom-edge-by-the-stylesheet-with-a-back-row-for-a-submenu-over-a-drawer-with-items-of-its-own.md), `Menu`, `ContextMenu`). It is resolved in JavaScript like `Popover`'s `side` since it chooses what is drawn, defaults to the floating form so nothing changes until an app asks, and keeps one set of parts, keys and focus handling; text the sheet adds is a `labels` entry.
- **A component generic over the shape of its data is a `forwardRef` function cast to a generic call signature, with its parts attached** ([ADR-0085](adr/0085-datatable-takes-columns-and-data-and-holds-the-interaction-state-with-toolbar-selection-and-pagination-parts-over-composed-table-rows-or-a-headless-hook.md), `DataTable<TRow>`). `forwardRef` can't carry a type parameter, so the export is `forwardRef(Inner) as unknown as (<TRow>(props: Props<TRow> & RefAttributes<El>) => ReactElement | null) & { Part: … }`, with each part assigned on it. Data is `columns` and `data` props rather than composed rows when the component must know what a row and a column are (to sort, choose and page them); what it draws for a cell is a function of the row, and anything with state of its own is a component that function renders.
- **A part that sits around a component's main element is a direct child placed by its kind** (`DataTable.Toolbar` above the table, `DataTable.Pagination` below). The parent reads `Children` for those types and draws the rest above; parts reach the parent's state through a context, and a `use…()` hook exposes the same state to a caller's own parts. A part wrapped in a fragment or another component isn't placed, which the Docs page says.
- **A long table or list keeps row heights in tokens, one per `size` step, and a control a row can hold is no taller than the row** ([ADR-0086](adr/0086-datatable-draws-fixed-height-rows-from-tokens-a-window-at-a-time-only-when-unpaged-over-measured-rows-or-windowing-inside-pages.md)). Each token is just taller than the tallest atom of its step in a row (`IconButton`), so a real-browser check measures every size against its token.

- **A listener on a node that other components are portaled into must be a native one** (`Toast`'s list). A portal's events bubble through the React tree, to the component that rendered it, and never through the props of the DOM node it was drawn into: `onPointerEnter` and `onFocus` on the list never heard a toast. Attach `addEventListener` to the node from an effect (held as state if it only exists after the first render), and read `relatedTarget` against it for enter and leave.

## 4. Compound components

Complex components use the compound-component pattern (matching the Radix primitives underneath, for consistency): `Select.Root`, `Select.Trigger`, `Select.Content`, `Select.Item` rather than one component with 30 flags. Applies to: `Select`, `Tabs`, `Accordion`, `Table`, `Menu`, `Dialog`, `DataTable` (with `DataTable.Toolbar`, `DataTable.Pagination` as composable sub-parts), `Form`. See [ADR-0013](adr/0013-compound-sub-part-properties-documented-via-hidden-docs-only-stories-file.md) for how a sub-part's own props get documented on the parent's Docs page — a hidden, docs-only stories file per sub-part, not a second sidebar entry.

## 5. Icon props

Any component with an icon slot accepts a **component reference**, not a string name:
```tsx
import { Wallet } from '@phosphor-icons/react';
<Button leadingIcon={Wallet}>Pay</Button>
```
Not a string enum (`icon="wallet"`) — this keeps tree-shaking intact (unused icons never ship) and gives full type-checking on valid icon references.

**The prop name depends on how many icon slots the component has.** A component with exactly **one** slot (`IconButton`, `ListItem`) keeps the plain `icon` name, since there is no position to disambiguate. A component with **two** slots, one before the label and one after (`Button`, `Tag`), uses the symmetric `leadingIcon`/`trailingIcon` pair, because an unprefixed `icon` beside `trailingIcon` reads as the "main" or only icon rather than specifically the leading one. A component that gains a second slot later switches to the pair.

**Default icon weight is `bold`**, set once on the shared `Icon` atom (`weight = "bold"`), so every icon renders bold unless a component says otherwise. Only `IconButton` varies it, to communicate state: `fill` for a pressed or active toggle, reinforcing it beyond colour alone.

## 6. CSS conventions

- CSS Modules only, class names in camelCase.
- **Every value traces to a token.** `var(--dbm-color-bg-brand)`, `var(--dbm-space-4)` — never a raw hex, px, or arbitrary value in component CSS. If a needed value has no token, add the token first (per `CLAUDE.md` principles), don't inline it "just this once."
- CSS custom property prefix is `--dbm-*` throughout, matching the token spec.
- **An icon's color comes from `icon.*`, never `text.*`, even when the two tokens share a value today.** The two families aren't guaranteed to stay in lockstep if either is retuned. Any component coloring an icon via `currentColor` (a fallback glyph, an icon-only button, an icon paired with a status label) reaches for the matching `icon.*` token for that context (`icon.default`/`icon.danger`/`icon.on-brand`/…), not a `text.*` token because the color matches. `Icon` inherits `currentColor` unless its `tone` is set, so an icon with no `tone` takes whatever color its parent sets. **One exception: an icon that is part of a run of text follows the run's colour,** so it reads as part of it and tracks its hover, visited, active and disabled states. `Link`'s external-link icon, `TableOfContents`' entry and group-toggle icons and `FieldError`'s icon are the instances; leave them without a `tone`. (`FieldError` also keeps `text.disabled` when disabled, where `icon.disabled` is a different value.)
- **Icons used inside an input field use neutral colors — `icon.default` at rest for a control and for text, `icon.secondary` for a purely decorative icon — unless otherwise noted, and are the field's own size step** ([ADR-0103](adr/0103-a-fields-icons-are-its-own-size-step-and-a-bare-icon-in-a-slot-is-sized-by-the-field-and-coloured-by-a-no-specificity-rule-over-a-context-read-by-icon.md)). This covers every icon inside a form control's own box: a plain leading/trailing icon (`Input`'s `prefix`), a purely decorative affordance (`Select`'s chevron, `SearchInput`'s magnifier, a bare `Icon` in a slot, `EditableText`'s pencil: `icon.secondary`), and an icon-only in-field button (`Input`'s `.clear`, `PasswordInput`'s `.toggle`, `NumberInput`'s stepper carets, `Select`'s and `Textarea`'s `.clear`). They read as neutral, informational controls belonging to the row, not brand-tinted affordances. An in-field button gets `bg.neutral-subtle` as a hover-only background (none at rest); a decorative, non-interactive icon gets no hover background.
- **Radix `Portal` content needs its own `font-family` — don't assume it inherits.** Anything rendered through a Radix `Portal` mounts at `document.body`, outside the component's own tree, and nothing upstream of `document.body` in a consuming app is guaranteed to set `font-family: var(--dbm-font-family-primary)`. A component whose trigger sets it but whose portaled panel doesn't falls back to the browser default font in any app that doesn't set one globally. Every portaled top-level class (`Select`'s `.content`, `Tooltip`'s, `Popover`'s, `HoverCard`'s, `Dialog`'s, and any future `Menu`) declares its own `font-family`. The `Portal` atom renders no styles, so content a consumer puts in a bare `<Portal>` sets its own (its Docs page says so); `Backdrop` portals a scrim with no text and needs none.
- **Focus-ring `border-radius`.** Every interactive element's `:focus-visible` outline needs an explicit `border-radius` on the element the outline is drawn on: modern browsers round `outline` to follow it, but only if it is set, so an interactive element with none gets a sharp-cornered ring however rounded its content looks. Use `var(--dbm-radius-full)` when the element itself is fully round (a circular avatar, a round icon button); use `var(--dbm-radius-sm)` for everything else, **regardless of that component's own corner radius**, a deliberately standardized, smaller ring radius so every square-ish focus ring reads consistently. Where the outline lives on an element with no background or border of its own (`Avatar`'s unclipped wrapper), the radius is cosmetic for the outline only. Where the element is itself the visible control (`Button`), the rule does tighten its corners slightly while `:focus-visible` is active (8px → 4px), an accepted trade-off against adding a wrapper box solely for the ring. `Button`'s `rounded` prop is the fully-round case: `.rounded:focus-visible` sets `radius-full`, declared after `.root:focus-visible` (same specificity, so source order decides), the arrangement `IconButton` and `CloseButton` use too; `rounded` is the one name for this across the three.
- **A text field draws its focus ring on its own edge, not offset from it.** A field is a box with a border, and an outline floating 4px off it reads as a second, detached frame around the first, and an outside ring is cut off by a scrolling frame at its edge (the next rule). `Input`, `Textarea`, `Select`'s trigger, `TagsInput`, `MultiSelect`, `TimePicker`, `DatePicker` (and so `DateRangePicker`) and `PinInput`'s active cell (and so `NumberInput`, `PasswordInput` and `SearchInput`, which draw with `Input`) set the border to `border.focus` and draw the 2px outline with a negative offset equal to its own width (`outline-offset: calc(-1 * var(--dbm-border-width-2))`): the ring covers the border and the pixel beside it, so the box keeps its outer size and place and nothing is drawn outside it. **They do not override the corner radius while focused:** the outline follows the box's own corners, so the 8px-to-4px change the rule above accepts for `Button` does not happen here. An invalid field keeps the ring in `border.danger` (`.error:focus-within { outline-color: … }`), since the ring now covers the red border it would otherwise hide. The outline stays an `outline`, not a `box-shadow`, because forced colours keeps outlines. Controls that sit inside a field (a clear button, a show/hide toggle, a stepper) and every non-field control keep the offset ring above. A real-browser check (`foundations/FieldFocusRing.checks.stories.tsx`) asserts it for every field in this list.
- **Inside a box that scrolls, the focus ring is drawn inside the control.** A box with `overflow` other than `visible` clips whatever is drawn outside its edge, and an outline with a positive `outline-offset` is drawn outside, so the ring on a control at the edge of a scrolling strip loses its top and bottom. Use a negative offset equal to the ring's width (`outline-offset: calc(-1 * var(--dbm-border-width-2))`), keeping `radius-sm`; anything else the control draws (an indicator bar, a shadow) stays inside its own box for the same reason. Where the ring would sit on a brand fill, `border.focus` is unreadable (1.3–1.6:1 on `bg.brand`), so draw it in a colour that contrasts with the fill (`icon.on-brand` does, 6.08–8.51:1). Two recorded exceptions are not patterns to copy: `Tabs`' `solid` variant draws its selected tab's ring as `bg.brand-hover` (1.24–1.48:1 against that fill, below the 3:1 floor, by direction), and `ButtonGroup`'s attached `primary` and `destructive` groups have a ring side over the next button's solid fill at 1.1–1.6:1 (the other three sides are on the surface at 4.2–6.5:1). The remedy is the inside ring in `icon.on-brand` / `icon.on-danger`. Anything not inside a scrolling box keeps the outside ring.
- **A focusable box that sits right against another control leaves its ring room with a margin, not padding.** The standard ring is drawn outside the box (a 4px offset and a 2px line, 6px in all). If `Tabs.Content` took its space from the list as padding inside itself, its ring would start inside the tab list, where positioned tabs paint over its top edge and cut it off. Space between a focusable box and its neighbour is `margin`, at least as wide as the ring (`Tabs`' smallest gap, `space.3`, is 12px). A browser story measures the gap against the ring rather than trusting the CSS.
- **Text drawn with CSS `content` is exposed to assistive technology unless it says otherwise.** Generated content is in the browser's accessibility tree: `CodeBlock`'s line numbers were read out as `StaticText "1"`. For decoration, give it empty alternative text after a slash, with the plain declaration first as a fallback: `content: attr(data-line); content: attr(data-line) / "";`. Check it in the accessibility tree, not by reading the CSS. (`Slider`'s width-reserving sizer is `visibility: hidden`, so it isn't exposed.)
- **A transparent border is drawn in forced colours.** Windows high contrast forces every border colour and draws `transparent` as a solid line, so a `border: 4px solid transparent` reserved to avoid a layout shift shows on every element that has it. Set the colour to a system colour keyword (`Canvas` to hide it, `Highlight` to show it) inside `@media (forced-colors: active)`; system colours are the one thing forced colours keeps. Emulate it in a real-browser test (the Chrome DevTools Protocol's `Emulation.setEmulatedMedia`); jsdom can't.
- **An SVG's `fill` and `stroke` are not recoloured in forced colours.** Forced colours recolours a box's background and border but, in Chromium, leaves a drawn shape's `fill` and `stroke` as written, so an arrow or icon meant to meet a border (or sit on a background) stops matching it. Inside `@media (forced-colors: active)` set them to system colours (`Canvas`, `CanvasText`, `ButtonText`, `Highlight`…), the same ones the surface gets, and measure it in a real browser with emulated `forced-colors`. Applies to any component that draws SVG decoration next to a border (`OverlayArrow` is the one shared piece today).
- **A thin line drawn as a background colour disappears in forced colours.** Forced colours replaces every background colour with the page's, so a 1px divider made from `background-color` computes to white on white (`Toolbar`'s separator measured `rgb(255,255,255)` on a white page). Give it a system colour (`CanvasText`) inside `@media (forced-colors: active)`, or draw it as a border. The same goes for anything told apart from the page by fill or shadow alone (a filled or stuck bar gets a one-pixel outline instead) and for gradient fades (drop them).
- **A native `<fieldset>`'s `<legend>` is floated, and what follows it `clear`s it.** The browser draws a fieldset's first in-flow legend straddling the top border, outside the padding; a floated legend (`float: inline-start; inline-size: 100%`) is an ordinary block inside it. Two traps follow: a flex or other formatting-context box beside a full-width float shrinks into the room left (none), ending up zero wide at the far edge, so give it `clear: both`; and a cleared box's top margin is absorbed by the clearance, so space it with `padding-block-start`. Also reset the fieldset's default `min-inline-size`, border, padding and margin. Measure it in a real browser: a unit test sees none of this.
- **A list with its markers removed (`list-style: none`) states its roles outright.** Safari with VoiceOver stops treating such a `<ul>` as a list, and its items as list items, so "list, 7 items" is never announced. Put `role="list"` on the `<ul>` and `role="listitem"` on each `<li>` (`List`/`ListItem`, `Pagination`). The `jsx-a11y/no-redundant-roles` lint rule is right on paper and wrong for Safari: either compute the value (as `List` does) or, for a fixed structure, disable it with a stated reason. jsdom can't reproduce the Safari behaviour, so a test asserts the attributes rather than the announcement.

- **An element's pull toward another place is `translate` and `scale`, not `transform`, when an animation also moves it** (`Toast`'s fan). The individual properties compose with the `transform` an entrance, a swipe and an exit write, so neither replaces the other and neither has to know about it.

## 7. Documentation requirement (definition of "typed")

Every exported component gets a component-level JSDoc block with a usage example; every prop gets an inline JSDoc description. This is what the manifest generator (`packages/manifest`) reads to build the agent-facing component index — undocumented props are invisible to that tooling, not just "less polished."

## 8. Definition of done (per component)

A component isn't complete until all of these are true (the full review checklist a component passes before it is Finalized is `06-engineering-standards.md` §9):
- [ ] Implementation follows the file structure, naming, and prop patterns above
- [ ] Full TypeScript types, no `any`
- [ ] JSDoc on the component and every prop
- [ ] Storybook story covering every variant/size/state combination, including error and disabled states
- [ ] Docs page (`ComponentName.mdx`) per `07-storybook-and-documentation-standards.md` §4, and every visible story's "Show code" set to a hand-written snippet from `ComponentName.snippets.ts` (§4.2, [ADR-0020](adr/0020-show-code-uses-hand-written-snippets-over-storybook-generated-source.md))
- [ ] Unit test (React Testing Library) covering rendering and interaction
- [ ] Accessibility test passes (jest-axe/vitest-axe) with zero violations, and every interactive control's accessible name holds the text it shows (WCAG 2.5.3, [ADR-0112](adr/0112-an-interactive-controls-accessible-name-holds-its-visible-text-as-whole-words-in-order-over-a-name-that-only-means-the-same.md))
- [ ] Keyboard navigation verified (tab order, focus visible, escape/enter/arrow behavior where applicable)
- [ ] Any new color pairing introduced is contrast-checked (methodology in `03-token-system-spec.md`), not assumed
- [ ] Exported from the package's public `index.ts`
- [ ] No hardcoded values — everything traces to a token

## 9. Commit & release convention

Conventional Commits format (`feat(button): add loading state`) — this is what lets Changesets generate accurate changelogs. Changesets is configured (`.changeset/config.json`) but not yet wired into a release pipeline, and pull requests are disabled on the repo, so no per-change changeset is written today. Building the release flow is Phase 8 (`01-vision-and-goals.md` §13); once it lands, every change that affects the public API includes a changeset describing the change from the consumer's point of view.

## 10. `CloseButton` vs. a local, component-specific remove control

`CloseButton` is a fixed, brand-styled dismiss control, reserved for modal-style overlay surfaces (Dialog, Drawer, lightbox) — not a context-adaptive one. Any component whose own tone/color varies per instance (`Tag`, `Alert`, `Toast`) implements its own local, self-contained remove control instead. Default to the local implementation unless `CloseButton` is explicitly requested. See `guidelines/adr/0008` for the reasoning, the conflict that produced this rule, and alternatives considered.
