# ContextMenu — review findings

Fourteenth organism and the first 🟡 v1.5 one, built 2026-10-24 on `Menu`'s item parts with the `06-engineering-standards.md` §9 checklist applied as it was written. **Finalized 2026-10-24**, at the maintainer's declaration after a final review whose six findings were all fixed (below), with the items under "Open" accepted as open: none changes the component.

## Decisions
- Wraps Radix ContextMenu pinned at `2.3.7` (the only release on `Menu`'s `react-menu@2.1.24`), holds its own open state, is modal by default and uses Radix's 700ms long press for touch; documented as a shortcut and never the only way to an action: [ADR-0118](../adr/0118-contextmenu-wraps-radix-contextmenu-pinned-at-2-3-7-on-the-menu-release-train-holds-its-own-open-state-and-is-modal-with-a-long-press-over-the-newest-release-or-a-hand-rolled-trigger.md).
- Opened from code by sending Radix's trigger a `contextmenu` event, through a controller (`controllerRef`, `useContextMenuController()`) with `openAt`, `openFrom` and `close`, and the trigger's `openOnKeys` for platforms with no context-menu key: [ADR-0120](../adr/0120-contextmenu-is-opened-from-code-by-sending-radixs-trigger-a-contextmenu-event-through-a-controller-and-an-openonkeys-prop-over-rebuilding-the-trigger.md).
- A `presentation` of `"sheet"` (or a width map) draws it as a bottom sheet for touch, shared with `Menu`: [ADR-0121](../adr/0121-menus-sheet-is-the-same-radix-menu-pinned-to-the-bottom-edge-by-the-stylesheet-with-a-back-row-for-a-submenu-over-a-drawer-with-items-of-its-own.md).
- A `DataTable` row opens one with `rowContextMenu` ([ADR-0122](../adr/0122-datatable-opens-a-rows-context-menu-through-a-render-prop-that-chooses-the-row-first-and-is-told-the-selection-over-a-menu-per-consumer-or-a-menu-that-ignores-the-selection.md)).
- Its items, labels, groups and submenus are `Menu`'s own parts, drawn with Radix ContextMenu's parts through a context, and with `Menu`'s stylesheet: [ADR-0119](../adr/0119-menus-item-parts-draw-with-the-radix-parts-a-context-supplies-so-contextmenu-shares-them-over-copying-them-or-extracting-them-early.md).
- **No new token and no new dependency beyond the pinned Radix package.** The stylesheet holds one rule for the area (a block) and one for its focus ring; everything else is `Menu`'s.
- Shipped as `ContextMenu`; "Right-click menu" is a search term.
- **The area is a `<span>` by default,** with `asChild` for a row, a card or a canvas, and `tabIndex` redeclared and documented, since the context-menu key and Shift+F10 open the menu only on a focused element.

## What was found while building it
- **Radix's dropdown parts do not work under a context menu's root** ("`MenuItem` must be used within `Menu`"): each root provides the scope its own parts read. Sharing `Menu`'s parts needed the kit context of ADR-0119, which `Menu` provides nothing for. A first reading of Radix's source suggested the parts were interchangeable; running them showed they are not.
- **`Menu`'s panel read `--radix-dropdown-menu-content-*` custom properties,** which only DropdownMenu sets. Under a context menu the caps and transform origin found nothing, so it now reads the popper's own (`--radix-popper-*`), which both set. `Menu`'s panel measurements in its real-browser checks are unchanged.
- **Radix ContextMenu returns focus only to a trigger it can focus,** and the trigger is a plain `span`. The area records what had focus as the menu opens and the panel returns it there; a dialog an item opens could not find it (`findInvoker` follows a menu's `aria-labelledby`, and this panel has no trigger button to be named after), so a panel registers its opener in a `WeakMap` (`internal/overlay/menuInvokers`), read by the same function. A unit test of the confirmation flow failed before the registration and passes after.
- **The panel mounts a render after the root opens** (Radix's portal waits for its first commit), so the registration is a ref callback, not an effect.
- **A menu opened with `open` or `defaultOpen` before any press has no position** and is drawn at the page's top-left corner, with a Radix development warning. `open` is documented as for following and closing it, and the hidden docs-only stories don't open it.
- **The test browser's synthetic key events do not trigger the browser's own context-menu action,** so Shift+F10 could not be exercised for real; the unit tests send the `contextmenu` event the key sends.
- **Two nested areas open only the innermost's menu** for a press inside it, and the outer's for a press outside the inner one (unit tests; Radix stops the outer one).
- **A `div` with `tabIndex` inside `asChild` is flagged by accessibility lint** (a focusable element with no role): the examples put `tabIndex` on the trigger, and the Docs page says to give a plain box a role and a name.
- **Closing with a real mouse leaves no focus ring on the row,** and the check holds that. It also passes without the `focus({ focusVisible: false })` call this component copies from `Menu`, in Chromium, so the call is defensive here rather than demonstrated; it was kept for parity.

## Added after the first pass (2026-10-24)
- **Opening from code and from extra keys.** A synthetic `contextmenu` event with the point's coordinates opens Radix's menu at that point (a unit test and two real-browser checks: a point, flipped inside the viewport in the corner, and `Alt+ArrowDown` from a focused button inside the area, the panel under the button and Escape returning focus to it). `jsdom` refuses `view: window` on a `MouseEvent`, so the event is built without it.
- **The sheet.** A real-browser run showed the stylesheet's override of Radix's position wrapper holds with a real mouse and a real touch: the panel's rectangle is the viewport's width at its bottom edge, rows are at least 48px, a press on the scrim closes it, and a submenu covers the menu under a Back row. **Back first closed the whole menu** (an item's default on select), found by that check and fixed with `preventDefault`; the unit test of it does not fail without the fix in jsdom, so the real-browser check is the one that holds it.
- **The `DataTable` row menu** is one `ContextMenu` per row, opened by a press on the row, with the items drawn only while it is open and through its exit.

## Final review pass (2026-10-24)
A full §9 read-through before Finalization, with its six findings fixed:
- **Three visible stories had dead controls** (`OnRows`, `OpensADialog`, `FromAButtonAndAKey` passed only some of the Playground's args): every story that draws its own area now takes all of them through `rootPropsOf` and `contentPropsOf` in `ContextMenuStoryKit.tsx`. Checked live by changing `presentation` and `size` through the Storybook channel and reading the open panel in each.
- **The Content's `aria-label` and `aria-labelledby` inherited `Menu`'s JSDoc** ("named after its trigger"), false for a context menu; redeclared with accurate text.
- **The server-render list lacked the new surface:** variants for a sheet, a responsive presentation (resolved after hydration), a custom back label, a controller and `openOnKeys`; and an axe test of an open sheet with a submenu showing.
- **The area's own focus ring had no real-browser check:** one now presses a real Tab (a synthetic one doesn't change what the browser counts as keyboard use) and a real click, and asserts the 2px ring and its corners for the first and none for the second; it fails when the rule is removed.
- **The Docs token rows described only the panel** where the area's ring uses the same tokens: four usage texts extended.
- **The sheet's rectangle checks were intermittently wrong in a full run** (read mid-slide: 114px off the bottom edge): `getAnimations()` is empty until the browser has started the animation, so `settled` can return early on a busy machine. The sheet checks in `ContextMenu` and `Menu` now wait for the rectangle to stop moving (`stillRect`); three full Storybook runs in a row passed after it.
- **The controller was documented only by an example:** a subsection now says what each method does and returns, that the event it sends bubbles to the page, and what `open` reads.

## Checks run
- 125 unit tests in `ContextMenu.test.tsx`, `ContextMenu.ssr.test.tsx` and the Docs-token test (and the Playground snippet builder's, in `storySnippets.test.ts`), with the controller, `openOnKeys`, `matchesKeyCombo` and the sheet added to what follows: a right-click, a long press and its early release, the keyboard's `contextmenu` on a focusable area, Escape and focus return, a press outside, a disabled area leaving the browser's menu, the browser's menu prevented, controlled and uncontrolled state, `onOpenChangeComplete`, arrow keys, Home/End, typeahead, choosing by click, Enter and Space, `preventDefault`, descriptions and trailing content, a promise from `onSelect`, `disabledReason`, checkbox and radio items, groups, link items, submenus (and right-to-left), refs and props on the area and the panel, the attribute-precedence probe, the row size, a `Dialog` hosting it (including Escape and focus return after a confirmation), a row holding both a `ContextMenu` and a `Menu`, `StrictMode`, axe, and server render and hydration of seven variants.
- 14 real-browser checks (Chromium), the last four being `openAt`, `openOnKeys`, the sheet at the bottom edge with its Back row and scrim, and a sheet opened by a long press on a phone-width viewport, beside: the panel placed at a real right-click; flipping and staying inside the viewport in the far corner; chosen with a real mouse from inside a `Dialog` with the dialog left open (the item is the top element at its point); a 28-item list capped to the viewport, scrolling, with the last item fully in view after End; every size's items at least 24px tall and inside the panel; focus back on the row without a ring after a real click; a real touch held for 900ms opening it and a short one not; a right-to-left submenu opening to the left with its caret mirrored; forced colours drawing the highlighted item's outline; and a row's `Menu` button and right-click each opening only their own menu.
- Whole package: `pnpm lint` (eslint and both typechecks), the 179 unit files (9725 tests), the 281 Storybook files (2100 tests), the build, `pnpm audit` (none), the per-component bundle-size check (ContextMenu 6.86KB of JS and 2.34KB of CSS gzipped, inside the 10KB default) and `check-guidelines`. `Menu`'s own unit tests and real-browser checks pass after the shared-parts and sheet changes.
- The Docs page was opened in a running Storybook: every Properties table has a description and no stray rows, and the right-click was tried by hand on the rows story, in the default theme and in Emerald dark.
- The "Show code" snippets were typechecked against the real components (a planted bad prop failed it).

## Open
- **Not verified:** a real keyboard (Shift+F10 and the context-menu key), a real touch device and the long press on one, a screen reader's announcement of the menu opened from an area, Safari and Firefox (their handling of the `contextmenu` event on a focused element and of `focus({ focusVisible: false })`), Windows high contrast on a real machine, and the four themes by eye (Purple light and Emerald dark were looked at; the rest follow `Menu`'s measured pairings, which this component adds none to).
- **Known gaps, named and not built:** swipe to dismiss and a drag handle on the sheet; a configurable long-press time (Radix fixes it at 700ms); and a platform-aware shortcut hint.
- **The Docs page's Properties tables for the shared parts are written beside `Menu`'s** (copies of its docs-only stories, with the names changed), and have to be kept in step with them.
