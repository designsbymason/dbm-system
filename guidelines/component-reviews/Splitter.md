# Splitter — build findings

**Layout:** Splitter — built 2026-10-04, item 30 in the molecule build order (`04-component-inventory.md`). **Finalized 2026-10-04** by the user, after the final review and the `toggle` addition recorded at the end of this file. Decision: [ADR-0037](../adr/0037-splitter-is-hand-rolled-on-the-window-splitter-pattern-with-automatic-handles-and-a-percentage-layout.md).

**What it is:** a compound component, `Splitter` + `Splitter.Pane`, that divides its container among panes with draggable, keyboard-operable handles. Orientation (a breakpoint map too), a `line` or `grip` variant, `keyboardStep`, `disabled`, `dir`, `labels`/`formatNumber` (ADR-0021); a layout held by you (`layout`/`onLayoutChange`) or by it (`defaultLayout`), `onLayoutCommit` for saving; per pane `defaultSize`, `minSize`/`maxSize` (percentages or pixels), `collapsible` with `collapsedSize` (nothing, or a strip), `collapsed`/`defaultCollapsed`/`onCollapsedChange`, and render-function `children` that receive `{ collapsed, size }`.

**Decisions put to the user before building:** sizes as percentages with pixel or percentage limits (chosen over percentages only, or mixed fixed and flexible panes); collapsible panes (chosen); no built-in storage (chosen). The rest is in the ADR.

**Composition checkpoints (06 §9):** compound sub-part completeness — `Splitter.Pane` has its own `forwardRef`, JSDoc, pass-through props and a hidden docs-only stories file for its Properties table (ADR-0013); atom reuse — none applies (the handle is its own control), `Icon`/`Divider`/`ScrollArea` appear only in stories and Related cards; consumed-atom defects — none; Radix audit — no Radix primitive underneath, none needed; cross-part ARIA wiring — each handle's `aria-controls` names the two panes' ids (a pane's own `id` or a generated one), tested and axe-clean; composed tab order — every handle is one tab stop in order (checked in Chromium across nested splitters and with a disabled one); nested provider — a splitter inside a pane has its own context and moves only its own panes (checked in Chromium).

**Findings made by looking and measuring, fixed:**
- **A collapsed strip had no way to show a different thing.** A 48px rail wrapped its label into a column of single words. A pane's `children` may now be a function of `{ collapsed, size }`, so a rail shows an icon.
- **Two of my own tests were wrong, not the component:** a measurement taken while the panes were still easing to their size (waiting for the size to settle fixed it), and a `waitFor` whose callback added and removed an element on every poll, which re-triggered itself and hung the run. Colours are now resolved once, outside the polling.
- **Mutation testing** (19 deliberate breakages of the component's logic): 15 caught at once; four survived. One is equivalent (in controlled mode the local state is never read) and one is equivalent (an effect dependency already implied by another); the other two exposed gaps, a disabled double click and an `undefined` label overriding the default, both now tested and caught. A unit test for a resize re-reading a pixel limit was added as well (the browser story already covered it); its mutant stays equivalent.

**Accepted:** at rest the `line` variant is a hairline divider (`border.default`, 1.4:1, the treatment `Divider` has), not a control drawn to 3:1; `variant="grip"` is (the mark is `bg.neutral`, 4.7:1 light and 8.2:1 dark), and the handle's 24px target is not visual. Hover and drag draw the line in the brand colour, and keyboard focus in the focus colour, thicker. Forced colours draws the line and grip in system colours (a background colour would be dropped).

**Tokens:** none added; the handle uses `border.*`, `bg.neutral*`, `space.*`, `radius.full`, `opacity.40` and the motion tokens (every one listed on the Docs page and held to the stylesheet by `Splitter.docs.test.ts`).

**Responsive:** the orientation takes a breakpoint map (checked on a phone-width story in Chromium: stacked, the handle follows); pane sizes are percentages, so a layout keeps its proportions as the container changes (measured), and a pixel limit is re-read as a percentage when it does (measured).

**Tests (as first built; see the feature round below for the current counts, 41 and 89 and 15 hidden checks):** 29 for the pure model (every operation, snapping both ways, limits, infeasible moves, normalisation), 64 for the component (structure, ARIA, defaults, controlled layout, keyboard in both orientations and directions, dragging with the container's size mocked, lengths, collapsing every way, labels, props and warnings, StrictMode, server render, jest-axe), a Docs-page token guard, and 10 hidden real-browser checks (a real drag in both layouts, keyboard in pixels, the 24px target by `elementFromPoint`, collapse out of the tab order and a strip that stays, pixel limits and resize, proportions on resize, right-to-left, focus and forced colours, nested splitters, a phone). A real mouse drag in the browser pane moved a boundary 50% to 79% for 200px of a roughly 690px container.

**Self-verification (real runs):** `tsc` and `eslint` clean; unit project 5,616/5,616; Chromium project 1,078/1,078; `pnpm -r build` clean; component bundle sizes within budget (`Splitter` 3.61KB JS / 0.83KB CSS gzipped); the snippets typechecked against the real components (a planted bad prop and a `"12rem"` limit are both rejected); the Docs page opened in a running Storybook (all template sections, both Properties tables, every "Show code" panel read against its demo, no console errors); Variants in light, Collapsible in Emerald dark.

## Feature-completeness round (2026-10-04, at the user's request)

A gap review of the first build named eight; four were built the same day, the rest recorded here as not built:
1. **`rem` limits** (`minSize="15rem"`): measured against the root font size when the container is measured (on mount and whenever it changes size), so a limit about the text inside keeps up with the text size a person has chosen. An em, or a `rem` before the container is measured, is not a limit. ADR-0037 amended.
2. **Panes coming and going**: a pane's identity is its `id`, else its `key`; the others keep their sizes, a new pane takes its default or the unclaimed share, and a collapsed pane stays collapsed and reopens at the size it had. [ADR-0038](../adr/0038-splitter-panes-have-an-identity-fixed-panes-are-rescaled-and-locked-panes-have-plain-dividers.md).
3. **`resizable={false}` and `fixed`** (the user chose both): a locked pane's handles are plain dividers (no tab stop, value, target or hover, and not counted in handle names); a fixed pane keeps its length through a container resize while the others share out the rest. Same ADR.
4. **Pane `label`**: the handle after a pane is named "Resize Sidebar" (`labels.handle` gets it as a third argument); it is not put on the pane, since an `aria-label` on a role-less `div` is invalid.

**Not built (listed in the gap review, left for later or left out):** a larger touch target under `(pointer: coarse)`; reset-to-default on double click for panes that can't collapse; a saving hook beside `usePersistentDismiss`; the size before collapse surviving a reload; pixel sizes from `onLayoutChange`; per-frame batching of a drag; a "maximise one pane" action; pushing a neighbour past its limit (left out on purpose).

**Found by testing, fixed:**
- **A collapsed pane reopened itself when another pane was removed.** The adapted layout clamped its 0 up to its minimum. Collapsed panes are pinned in the adaptation, as they already were on a container resize; found by a unit test, now also a model test.
- **Mutation testing of the new logic** (16 breakages: rem as px, identity by index or id ignored, restore by index, locked beside either side, handle numbering, label not passed, fixed ignored, ratio inverted, collapsed not held, rescale not clamped or pinned): 15 killed at once. The survivor was a test that never made its pane start collapsed; fixed and killed.
- **Two browser tests measured mid-transition**, as before (the panes ease to their new sizes); both now wait for the value to arrive. A fixed-pane test with the ratio inverted fails as it should.

**Verification (real runs):** `tsc` and `eslint` clean; unit project 5,656/5,656 (the model has 41 tests, the component 89); Chromium project 1,086/1,086 with five new hidden checks (rem limits in the browser's own rem, a fixed pane's width through two container resizes, a locked pane and its divider, panes removed with the others keeping their proportions, handles named after panes); build clean; `Splitter` 4.25KB JS / 0.85KB CSS gzipped, within budget; the new snippets typechecked (a planted `fixed="yes"` and `"12em"` limit are rejected); the Docs page opened live (the Pane table's three new rows with defaults, every new "Show code" panel read) and the locked-panes story looked at.

## Reset on double click (2026-10-04, at the user's request)

A double click on a handle only collapsed a collapsible pane; with none beside it, it did nothing. It now **sets the two panes beside the handle back to the proportions they started in**, keeping the space they share, so every other pane stays where it is (resetting the whole layout from one handle would undo work done at the others, and nested splitters would reset each other). **Enter does the same**, as the keyboard's equivalent of a pointer-only gesture (WCAG 2.1.1) and as it already toggles collapse. A handle beside a collapsible pane still collapses or opens it; a locked pane's plain divider does nothing; a reset that changes nothing reports nothing.

**What "started in" means.** The layout the panes had when the splitter mounted, or when panes were last added or removed, taken for all panes at once. A first version recorded each pane's size when it first appeared; a test caught that this mixed two moments (a pane arriving later was compared with its neighbours' earlier sizes), so a reset went to proportions nobody had seen. Panes' own `defaultSize` and a `defaultLayout` both feed the starting layout, as before.

**Verification (real runs):** the model gained `resetPair` with 5 tests (46 in all); the component has 100 tests, 11 of them new (after the keyboard, after a drag, Enter, a pane's own default, only the pair, silence when already there, reporting, collapsible still winning, a late arrival, a locked divider, the limits); seven deliberate breakages of the new paths were all caught; a new hidden browser story drags a handle, double clicks it, checks the pane that isn't beside it stayed put, then repeats with Enter on the second handle (it fails when the reset is removed); `tsc`, `eslint` and the build are clean; unit 5,672/5,672 and Chromium 1,087/1,087; `Splitter` is 4.36KB JS / 0.85KB CSS gzipped. In the browser pane a real mouse drag moved a handle from 20% to 42% (the next pane from 55% to 33%) and a real double click put it back to exactly 20% and 55%.

## Final review before Finalization (2026-10-04)

A full `06-engineering-standards.md` §9 pass over the finished component, hunting for defects by writing the *desired* behaviour as a test first and confirming it failed before fixing it. Six findings, all fixed:

1. **Alt, Ctrl and Cmd with an arrow key were swallowed.** The handle `preventDefault`ed every handled key, so Alt+Left (Back) did nothing while a handle had focus. A key with a modifier now belongs to the browser, as in `Pagination`, `TimePicker` and `ToggleGroup`.
2. **A pane whose content overflowed it couldn't be scrolled from the keyboard.** A pane clips and scrolls, so a pane with long content and nothing focusable in it was unreachable. A pane is now a tab stop *while it overflows* (and a named region when it has a `label`), the pattern `ScrollArea` and `Table` already use, with a focus ring drawn inside it (the pane clips its own outside). A pane that fits isn't a tab stop, and nor is one collapsed to a strip (its content is clipped, not scrollable).
3. **Focus was lost when the pane that held it collapsed to nothing** (Escape in a sidebar that closes itself, say): the pane becomes `visibility: hidden` and focus drops to the top of the page. Focus now moves to the handle beside the pane, from where Enter opens it again.
4. **Content vanished the instant a pane started to close**, then the pane eased shut empty. Hiding is now delayed by the closing animation, and showing is immediate.
5. **A real infinite loop on a controlled pane** (the finding that mattered most): with `collapsed` set and `onCollapsedChange={setCollapsed}`, Enter on the handle made the pane and the state undo each other until React stopped with "Maximum update depth exceeded". Found only in a real browser, by the story written for finding 3. A handle on a controlled pane now only asks; see [ADR-0039](../adr/0039-a-handle-only-asks-a-controlled-pane-to-collapse.md) and the new bullet in `05` §3. A pane controlled as collapsed also starts shut instead of animating shut on mount.
6. **A test double was hiding the effect of finding 2:** every pane now creates a `ResizeObserver` (for its scrollability), and the tests' stub kept only the last one's callback, so a "resize" notified a pane instead of the splitter. The stub now notifies them all, as a browser does.

**Mutation testing of the new code** (seven breakages around controlled panes: re-enforcing on every flag change, a handle changing a controlled pane directly, the asked-memory not cleared on a key press or by a toggle, controlled panes reported twice, no dedupe in a drag, a controlled-collapsed pane not starting shut): six killed; the seventh (re-enforcing on every flag change) is equivalent once a handle only asks, since the flag can no longer drift from the prop. A gap it exposed, the asked-memory not clearing on a key press, now has a test (Home pressed twice on a pane whose parent says no asks twice).

**Checked and found fine:** `{...props}` before every computed attribute on the container and on the pane; every native prop is passed through and the pane's own (`label`, `fixed`, `resizable`, limits and collapse props) are not put on the DOM; server render; StrictMode; unmounting mid-drag; nested splitters; right-to-left; forced colours; a phone width; all four themes (looked at Purple light, Purple dark, Emerald light and Emerald dark); the 24px target; contrast of the grip (`bg.neutral` on `bg.surface` and `bg.neutral-subtle`, the two backgrounds a pane is shown on here: 4.70 and 4.51:1 light, 8.21 and 5.86:1 dark; a pane on any other fill needs its own check) and of the hover and focus lines.

**Accepted and documented, unchanged:** the `line` variant at rest is a hairline divider (1.1 to 1.4:1), not a control drawn to 3:1; the grip variant is. `useLayoutEffect` is used as in several other molecules (no server warning on React 19; React 18.2 would warn on the server).

**Verification (real runs):** `tsc` and `eslint` clean; unit 5,686/5,686 (the model 46, the component 114); Chromium 1,091/1,091 with 20 hidden browser checks (four new: a scrollable pane, a collapsed strip that isn't one, focus leaving with a pane, content visible while closing); no "Maximum update depth" in the run; `pnpm -r build` clean; `Splitter` 4.70KB JS / 0.90KB CSS gzipped, within budget. Looked at live: the focus ring on a scrollable pane in Purple dark (Tab lands on it, announced as the "Long pane" region, a 2px ring inside), and Variants in Emerald light.

## `toggle` for a pane's own content (2026-10-04, at the user's request)

**The gap.** In the Collapsible story an icon sat on the collapsed rail and clicking it did nothing: a pane's render-function `children` received `{ collapsed, size }` and no way to act, so a rail button needed controlled `collapsed` state just to open its own pane. A story-only fix would have hidden the problem by making the story controlled.

**What was built.** The children also receive `toggle()`, which does what Enter on a neighbouring handle does: collapse the pane, or open it at the size it had. Same rules as a handle: it does nothing in a disabled splitter or for a pane that can't collapse; on a pane controlled with `collapsed` it only asks, through `onCollapsedChange` ([ADR-0039](../adr/0039-a-handle-only-asks-a-controlled-pane-to-collapse.md)); it reports a finished change through `onLayoutCommit`. A locked pane (`resizable={false}`) can still toggle, since `resizable` only bars the handles.

**Two things the work made explicit, now in the docs.** A rail button only makes sense on a *strip*: a pane collapsed to nothing hides its content, button included, so there would be nothing to press. And the button must stay the same element in both states (change its icon and label, not what is rendered): a different element for each state unmounts the one that was pressed, and keyboard focus drops to the top of the page. The story and the snippet do this and the browser check asserts the button still has focus after it collapses and after it opens.

**Verification (real runs):** 8 new unit tests (collapse and reopen at the size it had, reporting, a controlled pane only being asked, a parent holding the state, disabled, a pane that can't collapse, a locked pane, a lone pane outside a splitter); six deliberate breakages of the new function all caught; a new hidden browser check (a real click collapses to 48px and the button, now "Expand sidebar", still has focus; Enter opens it and "Collapse sidebar" has focus); an older check that raced the closing animation (it asserted a hidden pane's button was gone the instant the width reached zero) now waits for the hidden state, stable over three consecutive runs; `tsc`, `eslint`, build clean; unit 5,694/5,694 (the component 122), Chromium 1,092/1,092, no update loops; `Splitter` 4.76KB JS / 0.90KB CSS gzipped; the snippet typechecked. In the browser pane a real click on the rail button opened the pane to 180px (its minimum, the earlier 25% being below it) with the button still focused.
