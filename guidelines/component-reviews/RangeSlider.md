# RangeSlider

**Tier:** molecule · **Category:** Inputs & Forms · **Status:** built 2026-09-25; **Finalized 2026-09-25**, declared by the user after the final review pass recorded below.

## What was built

A single component (not compound) wrapping `@radix-ui/react-slider`, already a dependency: a slider with two thumbs, item 17 in the itemized molecule build order (`04-component-inventory.md`). It is drawn exactly like `Slider` — same track, thumb, sizes, tick marks and label layouts — with the stretch between the thumbs filled. No new dependency, no new token, no new CSS: it reads `Slider`'s stylesheet.

Props mirror `Slider`'s, with the value a pair: `value` / `defaultValue` / `onValueChange` / `onValueCommit` are `[minimum, maximum]` tuples, lower first (`RangeSliderValue`); `defaultValue` defaults to the whole track. New: `minStepsBetweenThumbs` (Radix's own, default `0`) and `labels` (`minimum`, `maximum`, `range`; ADR-0021). Same as `Slider`: `size`, `hasError`, `min`/`max`/`step`, `orientation`, `inverted`, `showValue` (the range as "20 – 80"), `showValueTooltip` (one per thumb), `showMinMaxLabels`, `formatNumber`, `showTicks`/`tickInterval`, `disabled`, `autoFocus`, `name`/`form`, `aria-label`/`-labelledby`/`-describedby`, `id`, `className`, `style`, `data-testid`. Not carried over: `aria-valuetext` (each thumb's is its formatted number, from `formatNumber`).

## Decisions taken while building

- **Shared internals, not a copy (user's choice of three).** `Slider`'s layout — the six `showValue` / `showMinMaxLabels` / vertical layouts, the tick marks, the thumb-tooltip open state, the size classes — was extracted, DOM unchanged, into `Slider/sliderShared.tsx` (not exported from the package), and both components use it. `Slider`'s files changed only in `Slider.tsx` (now 190 lines shorter, 432 to 242); its 56 unit tests and its browser stories passed unchanged before and after, which is the evidence it is a pure refactor (three-question test: no visible or behavioural output changed, so it stays Finalized). The alternatives were duplicating about 250 lines, or making `Slider` itself accept a range.
- **`data-testid` goes on the root, `id` on the lower thumb.** `Slider` puts `data-testid` on its one thumb; two thumbs have no single answer, so the root is the anchor a test can query the thumbs inside. `id` goes on the lower thumb (the first focusable part, what a `FieldLabel`'s reference should reach) and the upper thumb's is `{id}-maximum`; generated ids when there is none.
- **Each thumb's accessible name is the slider's name plus "Minimum" / "Maximum".** With `aria-label` the two are joined ("Price Minimum"); with `aria-labelledby` the thumb is labelled by the visible label *and itself* (its own `aria-label` is the word), which is what `FormField`'s render-prop spreads produce. There is no `role="group"` wrapper: a name on every thumb is deterministic in every screen reader, where a group's name is announced inconsistently. Dev warning once when there is no name.
- **The default range text isolates each number** (U+2068 … U+2069). See findings.
- **The lower thumb is focused by `autoFocus` through a ref and an effect,** not React's `autoFocus`. See findings.
- **Playground uses two Storybook-only numbers** (`lowerStart`, `upperStart`) in place of `defaultValue`, since a pair has no single control; they are hidden from the Properties table and written as `defaultValue` in the snippet (the `media` control on `Card` is the precedent). The Playground remounts when they, `min` or `max` change, since an uncontrolled slider ignores a changed `defaultValue`.

## Findings from the build

- **Radix moves the first thumb on Home and the last on End, whichever thumb has focus** (confirmed in the installed source and by test: focus the lower thumb, press End, and the *upper* thumb goes to `max`). For two thumbs that is wrong. Each thumb now handles Home and End itself and stops the event before Radix's own handler sees it: the focused thumb goes to its own limit (the track's end, or as far as the other thumb allows, keeping `minStepsBetweenThumbs`), the other never moves, results are rounded to the step's decimals (0.7 − 3 × 0.1 is 0.4, not 0.39999999999999997), and `onValueChange` / `onValueCommit` fire once when something moved. Every other key is Radix's.
- **React's `autoFocus` does nothing on the thumb.** React only focuses a `button`, `input`, `select` or `textarea` on mount, and a Radix thumb is a `span`. `RangeSlider` focuses the lower thumb itself; `Slider`'s `autoFocus` had never worked for the same reason (confirmed: a mounted `<Slider autoFocus>` did not have focus) and was fixed the same day, see [Slider.md](Slider.md).
- **A range of numbers in right-to-left digits was drawn backwards on a left-to-right page.** Arabic-Indic digits pull the neutral dash between two of them into their own right-to-left run, so `formatNumber={new Intl.NumberFormat("ar-EG").format}` showed the range 20–80 with 80 on the left. Found by looking at the Docs page, then measured (the lower number sat 28px to the right of the upper). Wrapping each number in a bidirectional isolate makes them neutral to their surroundings, so the pair follows the page's direction. A `labels.range` of the consumer's own is theirs to isolate.
- **Radix insets a thumb so it never overhangs the track,** so a thumb's centre is a few pixels off the filled range's exact edge (6px at 20% for a 20px thumb). My first layout assertion expected the edge to be on the centre and failed; the real invariant is that each end of the fill lands inside its thumb.
- A `getComputedStyle` read straight after switching `data-theme` still returns the previous value while the 150ms colour transitions run (the same pitfall `Slider`'s review records) — read with transitions off.

## Right to left, 2026-09-25 (was the open item; decided and built at explicit direction)

**Found by testing a right-to-left page rather than reading the code:** the slider itself stayed left-to-right (Radix forces `dir="ltr"` on its root, so thumbs, ticks and arrow keys agreed with each other), but the min/max labels sit *outside* Radix's root, followed the page, and came out backwards — "0" under the maximum end. That was a defect whatever was decided about mirroring.

**Decision (option C of three):** classified under [ADR-0009](../adr/0009-rtl-mirroring-is-a-per-component-judgment-call.md) as reading-flow content, so it mirrors, and it follows the precedent of `Tabs`, `Accordion` and `RadioGroup`: an explicit `dir?: "ltr" | "rtl"` (default `"ltr"`), passed to Radix, **not** inherited from the page. Auto-detecting the page's direction was left out: it needs JavaScript, can flash left-to-right on a server-rendered page, and would be a library-wide `DirectionProvider` decision for every Radix component together, not this one's. No new ADR (it applies ADR-0009).

**Built** (shared, so `Slider` gets it too — additive optional prop plus a defect fix, so `Slider` stays Finalized): `dir` on Radix's `Root` (mirrors the thumbs, fill, ticks and flips the arrow keys) and on **every layout wrapper** (`SliderLayout`), so the value label and min/max labels follow the slider's direction, and stay left-to-right, agreeing with it, when `dir` is left out inside a right-to-left page. Four rules centred themselves with `translate(-50%)` on a logical inset — the ticks (both orientations), the vertical min/max labels and the thumb's 24px hit area — which in a right-to-left context sit half their width off-centre (measured: 4.8px); each has a `:dir(rtl)` override negating the shift, the arrangement `Switch`'s thumb already uses. Home/End (per thumb, in `RangeSlider`) are unaffected: they go to the value's own limits.

**Verified:** 9 unit tests per component pair (`dir` on Radix and on wrappers, left-to-right by default, left-to-right inside a right-to-left page, ArrowLeft raising and ArrowRight lowering in `rtl`, ArrowRight raising otherwise, vertical wrapper, Home/End in `rtl`); a hidden real-browser story per component measuring, in `rtl`, `ltr` and `ltr` left out inside a `dir="rtl"` page, horizontal and vertical: which thumb is right of which, the min/max labels' order, the ticks' order and the middle tick on the track's centre, the value label on the far side, the thumb hit areas at ±11px, and the labels and ticks centred over a vertical track. **Broken on purpose, each seen to fail:** no `dir` on Radix, no `:dir(rtl)` overrides (4.8px off), no `dir` on the wrappers. A visible "Right to left" story and Docs section in each; `dir` in the Playground, snippets and Properties table.

**Not verified:** a right-to-left *language* with real Arabic or Hebrew text in the labels beyond the digits story; real screen reader behaviour.

## Final review before Finalizing, 2026-09-25

A full `06-engineering-standards.md` §9 pass, checked against the code and the running component rather than the build-time notes. **Two findings, both fixed; nothing else needed action.**

1. **A malformed value was silent.** `value` / `defaultValue` as an unsorted pair (`[80, 20]`) or outside the track (`[-50, 500]`) rendered as given — a "Minimum" thumb above the "Maximum" one, and `aria-valuenow` outside `aria-valuemin`/`aria-valuemax` (confirmed with a probe) — with no warning, against §3's "invalid combinations fail loud in development". Now one development-only `console.warn` per instance for each case (stripped in production; Radix doesn't clamp, and a value the parent owns can't be repaired here). Three unit tests, the two warning ones fail without the warning (checked).
2. **Never tested: composing with `FormField`.** The component is documented inside one (`{(fieldProps) => <RangeSlider {...fieldProps} />}`) and `06` §9's cross-part wiring item applies to what consumes `FormField`'s render-prop, but nothing exercised it. Probed, then covered by three unit tests: each thumb is named "Price Minimum" / "Price Maximum" from the field's label, both are described by the helper text or error, `aria-invalid` and `disabled` arrive on both, and jest-axe is clean. They fail with the `aria-labelledby` composition removed (checked). Also added: jest-axe in right-to-left with everything shown.

**Checked, no action needed:**
- **Baseline:** no `any`, suppression or hardcoded value in the source (the component has no CSS of its own); every Radix `Root` prop is exposed or deliberately not (`asChild` is not needed, `name` reaches the hidden inputs as `name[]`); `{...props}` precedes every computed attribute, and `aria-invalid` is last on each thumb; JSDoc on every prop; no console output but the two development warnings and the no-name one, all once and stripped in production; SSR-safe (no `window` or `document`); `StrictMode` tested.
- **Snippets, never typechecked at build time:** all 9 (six static, three generated from the Playground builder across a spread of controls) typecheck against the real component; a planted unknown prop, a three-number `defaultValue` and `dir="sideways"` each fail, so the check bites.
- **Real pointer behaviour:** with both thumbs on the same value at either end the pair can still be separated by dragging (Radix moves the nearer thumb: 100/100 dragged left gave 48/100; 0/0 dragged right gave 0/48), so the overlapping-thumbs trap that two-thumb sliders often have is absent; a mouse drag commits once on release with the final pair, equal to the live value (20–52 in the Controlled story).
- **Responsiveness:** no page overflow at a 320px viewport with everything on at size `xl`, in containers from 100% down to 5rem; the track gives up space first, and the range text wraps below about 130px. The same layout as `Slider`.
- **Theming:** the error state resolves to the danger colours in dark Emerald with `aria-invalid` set; the four theme combinations were read earlier.
- **Docs and Storybook:** Properties table 31 rows, none with an empty description, defaults present; the Docs page has every template section; every visible story has hand-written "Show code"; interaction stories are hidden (`!dev`); the Playground's args match the real defaults except the two Storybook-only start values and `tickInterval`, each explained; nothing in reader-facing text cites an internal document, a date, review history or another library.

**Not verified:** a real screen reader; real Arabic or Hebrew text beyond digits.

**Test totals now:** 66 unit tests for `RangeSlider` (2,927 in the package), 22 real-browser stories.

## Gaps named, not built

- **A `RangeSlider` with more than two thumbs** — Radix supports it; nothing here asks for it.
- **Two typed inputs kept in step with the thumbs** — a common pairing (`NumberInput` ×2); a pattern for a page or a future `FormField` group, not this component.

## Post-Finalization fix (2026-09-26, at explicit direction) — a `labels` entry that is `undefined` keeps its default

Found on `AvatarGroup`'s final review: `labels` was merged as `{ ...defaultLabels, ...labelOverrides }`, so `labels={{ x: t?.x }}` (a missing translation) replaced the default with `undefined`. Probed on this component: `minimum` and `maximum` left both thumbs without an accessible name (`range` was already guarded). Now merged with `mergeDefined` (a new helper in `packages/utils`, which skips an override that is `undefined`), so each label falls back to its own default. **Finalized status unchanged** — it corrects a genuine defect (`06-engineering-standards.md` §9, question 2), and nothing that rendered correctly changes. A new test fails on the old spread (checked).
