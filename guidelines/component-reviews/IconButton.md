(13)/(14) Found moot/redundant once the box-size-matching work (below) landed: `IconButton` gained an `iconSizeForButtonSize` lookup map early in the review to bridge its own size scale to `Icon`'s, but once `size` was matched 1:1 to `ButtonSize` (a literal subset of `Icon`'s own size type), the map became a same-key-to-same-key no-op — removed, `size` now passes straight through to `Icon`.   Additional work beyond the numbered findings, at explicit direction: matched `IconButton`'s box size (all 5 steps, square and rounded) to Button's real rendered height at the equivalent step — new `packages/tokens/src/component/icon-button.json` component-layer tokens, since none of the 5 measured pixel values land on the shared `space.*` scale (same precedent as `Avatar`'s own size tokens); and redesigned the pressed-state treatment per tone family — `primary`/`destructive` invert to that tone's own `-subtle` tint, `secondary`/`tertiary`/`ghost` converge to a solid `bg.brand`/`icon.on-brand` fill, and the icon switches to Phosphor's "fill" weight while pressed, reinforcing the toggle state visually beyond color alone (contrast pairings logged in the final review pass below).

  Writing the Docs page (finding #15) surfaced a real layout bug in the shared `TokenRow` block (`.storybook/blocks/TokenRow.tsx`, consumed by 10 components' own Docs pages) via `IconButton`'s own long `icon-button.size.xs–icon-button.size.xl` token — two rounds of real fixes, not one: a first attempt (wrapping `<code>` in a `<span>` so it could hug short tokens) reverted `<code>` to native `display: inline`, which fragments its background per line — wrapped continuation lines lost their left padding and visually overlapped the row above (caught live via a user-provided screenshot). Reverting to a direct-flex-item `<code>` with `maxWidth` fixed the fragmentation but introduced a second bug — short tokens like `radius.sm` started wrapping unnecessarily, because the default `flex-shrink: 1` lets the flex algorithm squeeze a `break-word`-enabled item's width down toward its (now much smaller) min-content size any time the row is remotely tight. Root-caused via live `getBoundingClientRect` measurements, not guessed. Fixed with `flexShrink: 0` (letting `maxWidth` alone do the capping/wrapping, since max-width clamps the used width regardless of shrink factor). Then, per explicit follow-up feedback that pill sizes read "unbalanced" against each other, changed from a `maxWidth` cap (pills hug their own content, so a page mixing short and long token names doesn't line up) to a fixed `13.5rem` width sized to the longest real semantic token found across every `TokenRow` usage in the codebase (`motion.easing.emphasized`, 24 characters, measured live via canvas `measureText` against the pill's actual computed font/padding/border) — every pill in a component's token section is now the same size and the `usage` description column lines up in a straight edge, while longer component-layer/range tokens (`icon-button.size.xs–icon-button.size.xl`, `badge.size.xs–badge.size.xl`, etc.) still wrap cleanly within the fixed-width pill instead of overflowing or fragmenting. Verified live across all 10 `TokenRow` consumers (IconButton, Button, Checkbox, Skeleton, Spinner, ProgressBar, Avatar, Tag, ProgressCircle, Badge) with zero non-uniform pill widths.

  **Final review pass** (2026-08-24, same day): re-verified the full checklist end to end rather than assuming the 15 findings plus extra work already covered everything, the same discipline as Button's/Checkbox's own final passes — combined live verification (theming across Purple/Emerald × Light/Dark, responsiveness at mobile width, keyboard-focus/native-button-semantics confirmation) with a fresh, skeptical static-code audit, and found three more real gaps, each independently re-verified before being trusted. (1) **Real accessibility violation, confirmed live via a scoped jest-axe check before fixing:** `aria-pressed` was set unconditionally, including in `asChild` mode — `aria-pressed` is only a valid ARIA attribute on a role that supports it (e.g. `button`), not on every element `Slot` might render onto (a native `<a>`'s `link` role disallows it), so `<IconButton asChild defaultPressed><a>...</a></IconButton>` — a real, already-tested combination — rendered an anchor with an `aria-allowed-attr` violation (impact: critical), invisible to the existing test suite since the one test covering this combination checked the attribute's value but never ran it through axe, and the only pressed-state axe test used a native `<button>`, not `asChild`. Same bug class this section's own precedent already named (Avatar's `role="img"` + `as="button"`, `06-engineering-standards.md` §9). Fixed: `aria-pressed` now withheld whenever `asChild` is set (`isToggle && !asChild`), with a new dev-mode warning explaining why and how to work around it (mirroring the existing `asChild`-ignores-`icon` warning pattern), the previously-wrong test corrected, a new test confirming the pressed *visual* class still applies regardless, the missing axe test added (zero violations now), and 3 tests covering the new warning's gating. (2) `AsChild`/`AsChildDisabled` stories had the same dead-Controls-panel bug already fixed once in this same review (finding #6, `AllVariants`/`AllSizes`) and on Button/Checkbox/Tag/ProgressBar before it — both used a bare `render: () => (...)`, hardcoding `icon`/`aria-label` and ignoring every other arg. Confirmed live (setting `size` to `xl` via a URL-args override left the canvas at `md`, unchanged) before fixing; fixed by mirroring Button's own already-fixed `AsChild`/`AsChildDisabled` pattern exactly (`render: (args) => <IconButton {...args} asChild>...`), then re-confirmed live via the same URL-args technique (size/variant/rounded all now drive the canvas correctly). (3) The pressed-state redesign's own new color pairings had no logged contrast ratio, despite `IconButton.mdx`'s own Accessibility section already claiming every state pairing was checked — computed directly from the built primitive values rather than assumed: `icon.brand` on `bg.brand-subtle` (`primary`'s pressed state) turned out to already be covered by an existing log entry under a different name (`icon.brand`/`text.brand` share the exact same primitive value in every theme/mode, confirmed Phase 39, and `text.brand`/`bg.brand-subtle` was already logged in full, Phase 11); `icon.danger` on `bg.danger-subtle` (`destructive`'s pressed state) was genuinely new and unlogged — **4.86:1 light, 10.32:1 dark** — both logged here, with the tight light-mode margin flagged explicitly — this specific pairing (icon.danger *on* bg.danger-subtle, not bg.danger-subtle's own primary pairing) is finer-grained than `03-token-system-spec.md`'s own current-state table tracks, so this entry is its record. Full self-verification, whole package: `tsc` (package + `.storybook`), `eslint`, `tsup` build, both Vitest projects (`unit`: 756/756, `storybook`: 275/275), Playwright (8/8), and the Foundations token-coverage check (in sync) all clean. **Finalized 2026-08-24** — per that section's own note, don't make further changes to IconButton (code, stories, docs, or its tokens) without asking first.

  **Real defect found and fixed, 2026-08-30, at explicit direction (Storybook/docs only — `IconButton.tsx` itself untouched, so per the three-question test in `06-engineering-standards.md` §9 this stays finalized):** every single story in `IconButton.stories.tsx` — not just the Playground — rendered in toggle mode (`aria-pressed` set, pressed styling reachable) by default, because the shared `meta.args` set `defaultPressed: false`. `isToggle`'s own check is `defaultPressed !== undefined`, not a truthiness check — `false` is still a defined value, so this silently forced toggle semantics onto `AllVariants`/`AllSizes`/`Loading`/`Disabled`/`Rounded`/`AsChild`/`AsChildDisabled` too, none of which had anything to do with toggling. No story anywhere demonstrated the component's actual, real default (non-toggle) appearance — found via direct user observation of the Playground, confirmed by reading the code rather than assumed. `IconButton.mdx`'s own Code examples section had the identical bug baked into a real snippet: `<IconButton ... defaultPressed={false} />` was presented as if it were the plain/non-toggle example, when it actually opts into toggle semantics (starting unpressed) — corrected to a genuine non-toggle example (no `pressed`/`defaultPressed`/`onPressedChange` at all) plus a clarifying uncontrolled-toggle example alongside the existing controlled one.

  Fixed by porting Tag's own "Interaction mode" synthetic-select pattern (`06-engineering-standards.md` §9 precedent, `Tag.stories.tsx`'s `Playground`) rather than just deleting the default: `defaultPressed: false` removed from the shared `meta.args` entirely (so every story's real default is now genuinely non-toggle, not just the Playground's), `pressed`/`defaultPressed`/`onPressedChange` all set to `control: false` at the meta level (a bare boolean can't represent "not a toggle at all" — true and false both keep `isToggle` true, the actual root cause), and the Playground story gained a Playground-only `interactionMode: "Non-toggle" | "Toggle"` select (not a real `IconButtonProps` field) that composes `defaultPressed`/`onPressedChange` into the render only when "Toggle" is selected, defaulting to "Non-toggle" — IconButton's real zero-extra-props default. `IconButton.mdx`'s `PlaygroundControls.exclude` updated to add `defaultPressed` alongside the already-excluded `pressed`/`onPressedChange`. The dedicated `Toggle` story (unchanged, sets its own local `defaultPressed`/`onPressedChange` args) still correctly demonstrates toggle mode independent of any of this.

  Live-verified, not just typechecked: `Playground` with "Non-toggle" selected renders zero `aria-pressed` attribute; switching to "Toggle" live-adds `aria-pressed="false"` and clicking the canvas button visibly applies the pressed fill + `onPressedChange` firing (Actions panel count incrementing); `AllVariants`'s 5 buttons all confirmed `aria-pressed: null` post-fix (previously all toggle-mode); the dedicated `Toggle` story unaffected (`aria-pressed="false"` on load, as before). The Playground's own raw `interactionMode` control (undecorated camelCase label, since `PlaygroundControls` doesn't read `argType.name` the way Storybook's native Controls panel does) is expected, matching the exact same already-shipped, already-accepted characteristic on Tag's own finalized Docs page — confirmed by checking Tag's page live, not assumed to match. Full self-verification: `tsc` (package + `.storybook`), `eslint --max-warnings 0`, `tsup` build, both Vitest projects (`unit`: 811/811, `storybook`: 291/291), the component bundle-size check (IconButton: 1.83KB JS / 0.81KB CSS, within budget), and the Foundations token-coverage check (79/79, unaffected) all clean.

## Reads an optional `ButtonGroup` context, 2026-09-26 (additive; stays Finalized)

At explicit direction ([ADR-0025](../adr/0025-buttongroup-shares-settings-through-a-context-read-by-button-and-iconbutton.md)), `IconButton` reads an internal context that `ButtonGroup` provides: inside a group its `variant`, `size` and `rounded` default to the group's (its own props win) and a disabled group disables it; it also emits `data-variant` there, so the group can draw the separator that suits its variant. Outside a group the context is `null` and nothing changes: same output, same classes, no extra attribute. That is purely additive (question 1 of `06-engineering-standards.md` §9's three-question test), so `IconButton` stays Finalized; the new surface got its own scoped pass in `ButtonGroup`'s suite (props reaching it, own props winning, no leak outside a group, `disabled` OR-ed, `data-variant` only inside a group), each test failing when its behaviour is removed, and all of `IconButton`'s own tests, its stories and the visual baselines pass unchanged. **One side effect, fixed:** the three props are no longer destructuring defaults, so docgen stopped supplying the Properties table's Default column for `variant`, `size` and `rounded` (found live: "—"); each now states its default in its stories' argTypes.

**`min-height` / `min-width`, same day:** each size class now repeats its `height` / `width` as a `min-height` / `min-width` (no change on its own), so a `ButtonGroup` can let it stretch to its row or column without a row of only icon buttons collapsing to the icon. Without it a fused row with a `Button` that has a leading icon (about 2.4px taller) showed a step.

## `asChild` guard moved to the capture phase, 2026-09-26 (defect fix; stays Finalized)

At explicit direction. The same defect, found with `Button`'s: a link rendered `asChild` on a disabled or loading `IconButton`, or inside a disabled `ButtonGroup`, set `aria-disabled` but still ran its **own** `onClick` (a router's navigation, say), because the guard was a bubble-phase `onClick` and Radix `Slot` runs the child's own handler first — the bug `05-component-api-conventions.md` §3 documents for `Link`. Confirmed with a probe before the fix, and the existing test hadn't caught it because it only checked `IconButton`'s *own* `onClick`. The guard is now `onClickCapture` (a caller's own `onClickCapture` still runs when the click isn't blocked), and the bubble-phase branch, now unreachable, is gone. Under `06-engineering-standards.md` §9's three-question test it corrects a genuine defect (question 2), so `IconButton` stays Finalized. Four new tests (the same as `Button`'s): the slotted child's handler and `IconButton`'s own are both blocked when disabled, the child's handler is blocked and the link not followed while loading, the child's handler, `onClick` and a caller's `onClickCapture` all run in that order when not blocked, and a caller's `onClickCapture` doesn't run on a blocked click — all fail on the old guard (checked), as does a new `ButtonGroup` test for a disabled group.

## `tooltip` and `tooltipSide` added, 2026-10-03 (additive; stays Finalized)

At explicit direction, for `Toolbar` (every icon item there needed the same three-line `Tooltip` wrapper). `tooltip` takes
`true` (the button's own `aria-label` is the text) or any other content (a string, or a node such as a label with its
shortcut); `false`, `null`, an empty string and `undefined` mean none. `tooltipSide` (default `top`) picks the side. It
renders the button inside the `Tooltip` atom, so the DOM is unchanged unless `tooltip` is set. The button is still named
by `aria-label`; the tooltip is a convenience for sighted users and never the only name.

Three-question test: no existing output changes (a new prop whose default is no tooltip), so it stays Finalized, with a
scoped mini-pass: JSDoc on both props, a Properties-table row each (the Playground's Off / Label / Custom text choices live
on the Playground story, not the meta-level argTypes, so they aren't listed as values), a "With a tooltip" story and
snippet (typechecked), a Docs section and code example, and eight tests (no tooltip unless asked, shown on keyboard focus,
custom text and a node, the four no-tooltip values, ref and click and toggle state kept, axe with the tooltip open).
Known costs, not defects: the tooltip's `aria-describedby` repeats the name when `tooltip` is `true` (as it does for a
hand-wrapped `Tooltip`); a disabled or loading button never shows one (it can't be hovered or focused); and `IconButton`
now imports `Tooltip`, so every consumer's bundle carries it (Radix Tooltip is already a dependency; the per-component
size check stays within budget at 1.59KB JS).

## `tone` added, 2026-10-18 (additive; stays Finalized)

At explicit direction ([ADR-0097](../adr/0097-button-and-iconbutton-take-a-tone-brand-or-neutral-that-destructive-ignores-and-buttongroup-hands-down.md)): `tone` is `brand` (the default) or `neutral`, in the same neutral tokens as `Button` but with `icon.*` colours, never `text.*` ones (`icon.on-neutral` on `bg.neutral`, `icon.default` elsewhere, `border.neutral-strong` for the `secondary` outline). The pressed state of a toggle follows the brand pattern in neutral tokens: `primary` goes quiet (`bg.neutral-subtle`, `icon.default`), the other three go solid (`bg.neutral`, `icon.on-neutral`). `destructive` ignores the tone. Additive, so `IconButton` stays Finalized. Icons need 3:1, and the neutral pairings are 5.1:1 or more in every theme (4.0:1 before `icon.default` moved to `gray.700` / `gray.200`, 2026-10-18); `Button.checks.stories.tsx` measures them in the browser, including a pressed toggle. New unit tests cover each variant, the pressed state, `destructive` and the default.

## `label` and `hideLabelBelow` added, 2026-10-18 (additive; stays Finalized)

At explicit direction ([ADR-0098](../adr/0098-iconbutton-takes-an-optional-label-drawn-inside-the-button-and-hideLabelBelow-over-demo-only-captions-or-a-stacked-button.md)): an optional caption under the icon, inside the button, so hover, press, the focus ring and a click cover both (the `Navbar` demo's own caption had left the word out of all of them). `hideLabelBelow` leaves it out below a breakpoint step, where the plain square applies again. Without `label` nothing changes (no new class or element). The caption is `text.*` coloured by variant, tone and pressed state; pressed draws it bold with the box's width reserved. Contrast was computed from the tokens for every pairing in all four themes (4.5:1 floor): all pass except `text.danger` on `bg.danger-subtle-hover` in light mode (4.44:1), avoided by a captioned destructive toggle keeping its pressed fill under the pointer. `IconButton.checks.stories.tsx` measures the caption's contrast in the browser at rest, pressed and under a real pointer over the caption (which also hovers the whole button), that the box is taller than and never narrower than the square (and exactly the square below `hideLabelBelow`), that pressing doesn't change the width and a real click on the caption presses it, and that the focus ring surrounds the whole box; each fails when its rule is broken (checked for the caption colour and the width reservation). Unit tests cover the markup, each step's class, `asChild`, `rounded`, `tooltip` and label-in-name warnings, the loading and pressed states, and a group's `rounded`. Not looked at: a screen reader's announcement of a captioned toggle, and a real finger on a phone-sized captioned button.

## Icon, spinner and caption drawn inside an `asChild` element, 2026-11-15 (additive; stays Finalized)

At explicit direction ([ADR-0218](../adr/0218-an-aschild-component-draws-its-own-icons-spinner-and-caption-inside-the-slotted-element-with-radix-slottable-over-dropping-them-or-asking-the-consumer-to-put-them-in-the-child.md)): with `asChild`, an empty slotted element (`<a href="…" />`) gets the `icon`, the spinner and the `label` caption drawn inside it, with Radix `Slottable`. The development warning that `icon` has no effect with `asChild` fired on every documented use, since `icon` is required; it is removed, and only a `label` given to an element with content of its own still warns. The asChild stories and snippets now use the empty link. Found while building the docs website.
