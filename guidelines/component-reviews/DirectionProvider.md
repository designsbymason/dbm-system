# DirectionProvider

**Tier:** Atom · **Category:** Utility · **Finalized:** ❌ (built 2026-11-06, review pending)

Built as part of the AppShell work ([ADR-0182](../adr/0182-appshell-grows-a-busy-main-a-whole-page-state-and-a-layer-ladder-and-direction-reaches-the-shell-sidebar-and-navbar-through-a-provider.md), implementing [ADR-0177](../adr/0177-an-optional-direction-provider-sets-the-text-direction-for-a-subtree-over-reading-the-page-direction-automatically.md) in part).

## Built
- `DirectionProvider` (context only, no element) and `useDirection(own?)`; types and JSDoc; 8 unit tests (default, provided, own wins, nesting, fallback).
- `Sidebar`, `Navbar` and `AppShell` read it. Batch 1 of the wiring (2026-11-06) added `Slider`, `RangeSlider`, `ScrollArea`, `ToggleGroup`, `Stepper`, `Combobox`, `MultiSelect`, `Tree` and `CommandPalette`: each swaps its `dir = "ltr"` default for `useDirection(dir)`. One table-driven test (`DirectionProvider.consumers.test.tsx`) checks that each follows a provider, is left to right without one, and that its own `dir` wins; breaking the wiring in all nine made all nine cases fail. Batch 2 (2026-11-06) added `Calendar`, `RatingInput`, `Splitter`, `Carousel`, `ImageViewer`, `Tour`, `Toast`, `EditorTabs`, `Toolbar`, `Menubar`: the same swap, each with a test next to its existing right-to-left test that wraps the same fixture in a provider (a swipe, an arrow key, a drag or the `dir` attribute, whichever that test already measured); breaking the wiring in all ten made all ten fail. Batch 3 (2026-11-06) added `Menu`, `ContextMenu`, `Select`, `Dialog`, `Drawer`, `DatePicker`, `DateRangePicker`, `DataTable`: the overlays and pickers. A portalled panel sits outside the provider's DOM, so what matters is that the component resolves the direction itself and hands it to the panel; 7 real-browser checks (`DirectionProvider.checks.stories.tsx`) set the direction ONLY with a provider and measure the computed `direction` of what opened (Menu, ContextMenu by a real right-click, Select, the Dialog and Drawer bodies, and a DatePicker's calendar, mirrored), and a Menu with no provider stays left to right. `Dialog` and `Drawer` needed no code: their body is a `ScrollArea`, which batch 1 wired, so the body no longer stays left to right inside a right-to-left drawer once a provider is present (without one the old default stands). `DatePicker` and `DateRangePicker` leave the `dir` attribute off when nothing says otherwise, so their buttons inherit the page's direction; they now read a new internal hook, `useProvidedDirection`, to keep exactly that. Breaking the wiring one component at a time made exactly that component's check or test fail. Later batches add to the same pattern.
- Stories (Playground, whole app, own `dir` wins), snippets (checked by `storySnippets.test.ts`), Docs page, description, inventory row.

## The Drawer body defect, followed up (2026-11-06)
The `Drawer` and `Dialog` body is a `ScrollArea`, which batch 1 wired, so a right-to-left provider reaches it. A real-browser check on `AppShell` (`PhonePanelIsRightToLeftFromTheShellAlone`, at phone width, with `dir="rtl"` on the shell and none on the `Sidebar` or `Drawer`) confirms the menu panel and the links in its body read right to left; breaking either `ScrollArea`'s wiring or the shell's provider made it fail. What remains by design ([ADR-0177](../adr/0177-an-optional-direction-provider-sets-the-text-direction-for-a-subtree-over-reading-the-page-direction-automatically.md)): a page that sets only `<html dir="rtl">`, with no provider and no `dir` on the body, still gets a left-to-right body. The Docs for `Dialog`, `Drawer` and this provider say so.

## Batch 4 (2026-11-06)
Added `Accordion`, `Tabs`, `RadioGroup`, `Alert`, `Breadcrumb`, `ColorPicker`. `Accordion`, `Tabs`, `RadioGroup` (and `Select`, moved onto the same hook) used to hand an unset `dir` to Radix, which defers to a Radix `DirectionProvider` if the app has one, so they now read `useProvidedDirection` (our provider, else undefined) rather than `useDirection`, which would have forced `"ltr"` over an app's Radix provider. `Alert`, `Breadcrumb` and `ColorPicker` leave the `dir` attribute off when nothing says otherwise, so they inherit the page's direction as before; with a provider they set it. `Accordion` renders no `dir` attribute, so its test measures the arrow keys instead (three items, so the wrap-around cannot hide a wrong direction). A real-browser check opens the `ColorPicker` panel under a provider. Breaking the wiring made exactly these tests and that check fail. Every component with a `dir` prop now reads the provider.

## Batch 5 (2026-11-06)
The portalled overlays that have no `dir` prop: `Dialog`, `Drawer`, `AlertDialog` (so `ConfirmDialog`), `Popover`, `Tooltip` and `HoverCard`. Measured first, with only a right-to-left provider: a `Dialog`'s body was right to left, but its header and footer were left to right, and `Popover` content was left to right, because a portal puts the panel under `<body>`. Each content part now sets `dir` from `useProvidedDirection` after `{...props}` (so its own `dir` still wins); with no provider the attribute stays off and nothing changes. 6 unit cases (plus a `ConfirmDialog` test) and 5 real-browser checks cover the panel, the header, body and footer, and the `Popover`'s `align="start"`, which lands on the trigger's right edge once the content reads right to left; breaking the wiring in each content part made exactly its test and check fail. Documented, not changed: the `Portal` atom draws no element, so content an app portals itself takes the page's direction (give it a `dir`). `Pagination` needs nothing: it flips with `:dir(rtl)`, which follows the DOM.
