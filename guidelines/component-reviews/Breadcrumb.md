# Breadcrumb

**Tier:** molecule · **Category:** Navigation · **Status:** built 2026-09-23; **Finalized 2026-09-23**, after the final review pass recorded below.

## What was built

A compound component over a `<nav>` and an ordered list: `Breadcrumb` (root), `Breadcrumb.Item` (`<li>`), `Breadcrumb.Link` (the `Link` atom, restyled), `Breadcrumb.Page` (the current page, `aria-current="page"`). No Radix primitive underneath, so no new dependency; no new token. Files: the standard set plus three hidden docs-only stories files for the sub-parts ([ADR-0013](../adr/0013-compound-sub-part-properties-documented-via-hidden-docs-only-stories-file.md)).

Props on the root: `size` (shared 5-step scale), `tone` (`info` default / `brand` / `neutral`), `underline` (boolean, default `false`), `compact` (`never` default / `auto` / `always`), `truncate` (boolean, default `false`), `separator` (`"chevron"` default, `"slash"`, or any string/element), `maxItems` (a number or `"container"`)/`itemsBeforeCollapse`/`itemsAfterCollapse`, `labels` (`navigation`, `expand(hiddenCount)`), `aria-label`/`aria-labelledby`, and the usual `className`/`style`/`id`/`data-testid`. `Breadcrumb.Link` and `Breadcrumb.Page` take a leading `icon`; `Breadcrumb.Link` also takes everything `Link` does (`external`, `disabled`, `asChild`, native anchor props) except `underline`.

## Decisions taken while building (none needed an ADR)

- **Compound, one item per level, rather than an `items` array.** Follows `05` §4 (a compound for anything with sub-parts) and keeps a router link a plain child (`asChild`). The cost is that the root has to look at its children to collapse them: it reads `Children.toArray(children)` and renders only `Breadcrumb.Item` elements, so a fragment wrapping several items is ignored (with a dev warning) — documented on the Docs page.
- **The separator belongs to the item, drawn by the component** — a hidden `<span>` inside each `<li>` but the last, never a CSS pseudo-element (a custom element or string can't be one), and never in the accessibility tree (the list already says how many levels there are and which one you're on). Chevron flips under RTL through `:dir(rtl)`, the same as `Pagination`'s arrows.
- **Collapsing expands in place** (a "…" `IconButton`, `variant="tertiary"`, its name from `labels.expand(n)`), rather than opening a menu of the hidden items. Expanding removes the button, so focus is moved to the first revealed item's link — the "never remove the focused control" rule in `06` §9, tested with real keyboard input in a real browser (`CollapseInteraction`) and under `StrictMode` in the unit tests. It only collapses when at least two items would be hidden; `itemsAfterCollapse` is clamped to at least 1 so the current page is never the one that collapses; a dev warning fires when before + after fill `maxItems`.
- **`labels` without `formatNumber`** ([ADR-0021](../adr/0021-labels-object-and-optional-formatnumber-over-an-implicit-intl-default.md)): the only number in any text is the hidden-item count inside the "…" button's accessible name, which is never shown, so a caller's own `expand` function formats it. Nothing visible needs a formatter.
- **`Breadcrumb.Link` composes `Link`** (atom-reuse audit) with `underline="hover"` by default — a link in a navigation list isn't running through body text, the case the atom's `always` default protects — and overrides the colour with `a.toneInfo` / `a.toneBrand` / `a.toneNeutral` (each with its `:visited`) (element-qualified, so it wins over the atom's own `:visited` rule whichever stylesheet loads last). `icon` is not drawn with `asChild` (the slotted element owns its content); a dev warning says so.
- **Colours (revised, see the follow-up below):** the current page is `text.primary` in `font-weight.semibold`, so it isn't set apart by colour alone; a link's colour is the trail's `tone`.
- **The "…" button is the smallest `IconButton` (30px) up to `lg`**, `sm` at `xl`. An `IconButton` of the trail's own size is as tall as a `Button` of that size, far taller than a line of text; even the smallest makes its own line slightly taller than the others — accepted.
- **Separators are top-aligned to the first line of a wrapped label** (`1lh`-high, `align-items: flex-start`; the "…" item centres instead through `:has()`), found by looking at a phone-width screenshot.

## Findings from the build

- **Contrast — measured, not recalled.** The first draft of the Docs page quoted contrast figures from memory and had light and dark the wrong way round; and the separators were first `icon.secondary`, which is 2.86:1 (light) / 2.12:1 (dark) on `bg.canvas`. Recomputed from the primitive values: `text.secondary` 6.88 / 10.47 on the surface and 6.05 / 5.10 on the canvas; `text.primary` 14.11 / 13.53 on the surface and 12.41 / 6.59 on the canvas. The separators moved to `icon.default` (4.70 / 8.21 on the surface, 4.13 / 2.96 on the canvas). **Still a hair under 3:1 in dark mode on the canvas (2.96)** — accepted for a purely decorative, aria-hidden glyph that only repeats what the list and the spacing show (1.4.11 doesn't bind it); recorded on the Docs page.
- **The `Link` router placeholder** — the snippet guard rejects a component the package doesn't export, so the `asChild` snippet uses a plain `<a>` and a comment saying it stands in for the router's link.
- **Storybook's `userEvent` sends synthetic events, which never match `:hover`** — the colour story asserts the resting colours and decoration, and the hover colour was checked live in a browser instead.
- **`IconButton`'s `ghost` variant is the filled one; `tertiary` is the unfilled** (see `Pagination`'s own variant mapping) — the first draft used `ghost` and drew a boxed "…".

## Follow-up, 2026-09-23 (before Finalize): `tone` and `underline`

Added at explicit direction, after the build was pushed and before any review pass, so the component was not yet Finalized.

- **`tone?: "neutral" | "brand" | "info"`, default `"info"`** on the root, applied to every link (and to a `Breadcrumb.Link` with `asChild`). `info` is `text.link`, `brand` is `text.brand`, `neutral` is `text.secondary`. This **changes the default from the neutral colour first built** — `neutral` is the earlier look. The current page stays `text.primary`; the "…" button stays neutral (`icon.default`) whatever the tone.
- **Hover:** `brand` and `info` links keep their colour and gain an underline in that same colour (the underline is `currentColor`); only `neutral` darkens to `text.primary`. Nothing extra needed for the underline — it is `Link`'s own `underline="hover"`.
- **`underline?: boolean`, default `false`**, on the root: `true` passes `underline="always"` to every `Link`, so the underline is on at rest as well as on hover. The boolean is deliberately not the atom's own three-valued `underline`, which `BreadcrumbLinkProps` still omits.
- **Placement constraint, recorded on the Docs page and in `03`:** `text.link` (and so the `info` tone) must not be placed on `bg.canvas` — 4.15:1 (light) / 4.00:1 (dark) there. Neither should `brand` in dark mode on the canvas (3.63:1 Purple / 3.16:1 Emerald). Use `bg.surface`; use `neutral` when a trail must sit on the canvas. Surface figures: `text.link` 4.71 / 8.20; `text.brand` 7.37 (Purple) / 6.08 (Emerald) light, 7.45 / 6.49 dark.
- **A token description to know about:** `text.brand`'s own `$description` says it is for "emphasis/labels, not links" (written before links were de-branded). The `brand` tone uses it for links at explicit direction; the description was left as it is.
- **`text.link` itself was considered for a change** (`blue.600` → `blue.700` in light mode, for contrast on the canvas) and **not done**: the constraint above is the documented answer instead. See `03-token-system-spec.md`'s `text.link` row.
- **Verified:** unit tests (colour class per tone, underline class, `asChild`, jest-axe for the new tones), two new real-browser stories (`Tones` resolves each tone's computed colour against its own token and checks the current page stays primary; `Underline` checks the resting decoration colour), the snippets re-typechecked (a planted bad `tone` was caught), and computed colours read live in Purple light and Emerald dark. Hover was read from the stylesheet rules (only `neutral` has a hover colour rule) rather than triggered: Storybook's `userEvent` can't match `:hover`, and the browser pane could not composite a screenshot at that moment.

## Follow-up 2, 2026-09-23 (before Finalize): `compact`, `truncate`, and `maxItems="container"`

Three of the four gaps this file first named, built at explicit direction.

- **`compact?: "never" | "auto" | "always"`, default `"never"`.** Swaps the trail for one link — the item above the current page — with a back arrow before it. `auto` is below the `sm` breakpoint (the literal 640px, since a custom property can't be used in an `@media` condition, the same note `Pagination` carries). The request named `auto` and `always`; `"never"` is the explicit default, matching `PaginationCompact`. Implemented in CSS, not by rendering a separate link: the parent `<li>` is marked (`isParent`, from a position context the root builds), every other item is `display: none`, its separator is hidden and a back arrow (`icon.default`, flipped under RTL) is shown. Compact takes precedence over `maxItems`, and keeps the parent from being collapsed away (`itemsAfterCollapse` is at least 2 whenever `compact` isn't `"never"`). A trail of one item has no parent, so it never goes compact.
- **`truncate?: boolean`, default `false`.** One line (`flex-wrap: nowrap`), each label ellipsized as space runs out. Each label sits in its own `<span class=label>` (the ellipsis needs a block container; an inline-flex link holding an icon can't draw one), so a `Breadcrumb.Link`/`Page` now has an inner element — **the current page's text is no longer the `aria-current` element itself** (tests climb out with `closest("span[aria-current]")`). A slotted (`asChild`) link truncates on the element itself. A plain-text label also gets `title` = its full text (a caller's own `title` wins); a rich label gets none. **Known limitation:** items shrink in proportion to their size, so a short label like "Home" still gives up a few characters when the overflow is large — "the longest lose the most", not "only the longest lose". A weight that grows with length isn't expressible in CSS without the label's length in JavaScript; not done.
- **`maxItems?: number | "container"`.** `"container"` measures the trail against its own width before paint (`useLayoutEffect`, `list.scrollWidth` against `nav.clientWidth` while the list can't wrap or shrink — `.measuring`), hides one more item at a time (two the first time — a lone item is never swapped for a button), and starts over from the full trail whenever a `ResizeObserver` reports a new width. It hides from just after the first `itemsBeforeCollapse` items, so the ones nearest the current page stay longest, and stops at `itemsAfterCollapse`; past that it is `settled`, and wrapping — or `truncate`, if set — takes over. With `truncate`, items collapse first and labels are cut short only once settled. A collapse is **held back while keyboard focus is on an item it would hide** (the `Pagination` rule, `06` §9): the trail waits for `focusout` and catches up. Once the "…" button is used, the trail shows in full (and wraps). Measured in the browser only, so a server-rendered page shows the full trail until it hydrates.

### Bugs the tests found in the first version of the measuring

1. On mount, the effect that resets the measurement when the item count changes ran right after the measuring effect and undid its first collapse. It now runs only when the count actually changes.
2. A width change that left every state value as it was (a trail that showed in full and now had to collapse) changed no state, so the effect never re-ran and never measured. A `widthChanges` counter now forces it.
3. The `ResizeObserver`'s first callback was treated as "just record the width", so if it arrived after a resize (as it does in a headless test frame) that resize was swallowed. The width is now recorded when measuring starts. The first version of the keyboard-focus story **passed with the hold-back removed** because of this; after the fix it fails without the hold-back and passes with it (checked by breaking it on purpose).

### Decisions worth knowing

- **The real-browser measuring tests render one trail per fixed width** (each measured at mount) instead of resizing one — a headless test frame doesn't reliably deliver resize observations; the resize path is covered by unit tests with a controllable `ResizeObserver`, the keyboard-focus story, and a live check (6 → 5 → 4 items and back as a box was resized by script).
- **Only the compact form can drop keyboard focus.** It is a media query, like `Pagination`'s `compact="auto"`, so resizing across `sm` with focus on a link that then becomes hidden can't hold anything back. Documented on the Docs page.
- **The Playground's `maxItems` control is a select with an extra `off`** (leaving the prop out), set on the Playground story alone; the meta-level argType the Properties table reads lists only the real values (`3`, `4`, `5`, `container`). The prop has no default, so its Default cell is "—" like every other prop without one in the system — no `undefined` summary and no `@default undefined`. *(Corrected 2026-09-23: the first version put `off` in the meta-level options, so the table listed a value the prop doesn't take; a second attempt then wrote `undefined` into the Default cell, which no other component does, and was reverted.)*
- **Verified:** lint, both typechecks and build clean; unit tests (compact classes, parent marking and back arrow, no-parent trail, truncation classes and titles, the whole container algorithm with stubbed layout and a controllable observer, StrictMode and axe still passing); real-browser stories for compact (wide and at a 375px viewport), truncation (one line, ellipsis on the long labels, titles), fit at five widths, and focus not being dropped; every snippet typechecked (a planted bad `compact` value was caught); the compact form read live at phone width.

## Final review before Finalizing, 2026-09-23

The full `06-engineering-standards.md` §9 checklist, run against the code as pushed in `508ca56`. Findings, all fixed the same day:

1. **A real defect: the expansion outlived the page.** In a layout that keeps `Breadcrumb` mounted across route changes, using the "…" button once left the trail expanded for every later page (`expanded` was never reset). A failing test reproduced it first. The trail now starts over — collapsed again if long, measured afresh — whenever the ordered keys of its items change. Items with no `key` of their own can only be told apart by position, so a page with the same number of unkeyed items isn't detected; the Docs page, the component JSDoc and the code example all say to give each item a `key` (its `href`). (The same effect used to reset the measurement on a changed item *count*; it now uses the keys, which covers that too.)
2. **`dir` was documented but not declared.** RTL is a feature the Docs page shows and a story tests, but `BreadcrumbProps` never redeclared the native `dir` (`06` §9's native-props audit), so its type and JSDoc reached only the story's argTypes, not the manifest. Redeclared with a JSDoc.
3. **The root component's JSDoc predated `tone`, `underline`, `compact`, `truncate` and `maxItems="container"`** — it feeds the manifest, so an agent reading it would not have known any of them existed. Rewritten.
4. **A Docs sentence named a prop that was in the table above it** — the "also accepts any other native `<nav>` attribute" sentence cited `dir` as its example (`06` §9: the example must not already be listed). Changed to `onFocus`, `title`.
5. **An overclaim on the Docs page:** "the first item, the '…' button and the last two items always stay" — they are `itemsBeforeCollapse`'s and `itemsAfterCollapse`'s defaults. Reworded.
6. **A missing test:** nothing asserted that a keyboard reader still gets a focus ring on a link in a `truncate` trail. Added to the truncation story (`outline-style: solid` after a real Tab).

Checked and found sound (no change): every value in the CSS is a token, the one literal being the `640px` media query (documented, as in `Pagination`); `{...props}` is spread before every computed attribute (`ref`, `role`, `aria-current`, `aria-label`, `title`, `className`) on all four parts; roles and names (`nav`, `list`/`listitem` stated for Safari, `aria-current`, hidden separators, a named "…" button); contrast, re-measured for every tone; the compact form's back arrow and item order under `dir="rtl"` (read live: mirrored arrow, first item at the right); every visible story has a hand-written snippet, resolved through Storybook's own store (19 of 19; the seven hidden interaction stories have none, as intended); the Playground's new controls (`compact`, `tone`, `underline`, `maxItems`, `truncate`) each drive the canvas (read live through the story URL args); the Properties tables show every default; the Docs page has the full template in order; tests pass under `StrictMode`; SSR-safe (`window` is only touched in `useIsomorphicLayoutEffect`, an event handler and `keyboardIsOn`); Emerald dark read live earlier.

**Not verified in this pass:** a screenshot of the Docs page and of every story (the browser pane could not composite one during the review, so appearance was read from computed styles and the DOM rather than seen), and the Docs page's "Show code" panels opened one by one on the page itself (lazy rendering needs a visible pane) — their contents were read through the story store instead.

## Post-Finalize story fix, 2026-09-25 (docs-only; stays Finalized)

**Found by the user:** tabbing through the Playground's links showed only two vertical bars instead of the whole focus ring. **Not a component defect** — reproduced with a real Tab press in Chromium: the ring is drawn correctly (2px, 4px offset), and in a story with no wrapper the whole ring shows. The cause was the *demo*: the Playground and three other stories wrap the trail in a `resize: horizontal; overflow: auto` box (so `maxItems="container"` and `truncate` can be watched as the width changes), which was exactly as tall as one line of links, and an `overflow` box clips anything drawn outside it — a ring reaches 6px beyond a control. The four resizable stories (Playground, "Collapsing to fit the width", "Truncated labels", "Long labels wrap") now share one `ResizeBox` with `space-2` (8px) of padding, and a hidden story tabs through every link and asserts the real ring fits inside every ancestor that clips overflow — measured from the ring's own width and offset. It fails, "clips the ring on the left", with the old unpadded wrapper (checked). `ResizeBox` and the test are stories-only; the component is untouched, so under `06` §9's three-question test this is a doc-only change and `Breadcrumb` stays Finalized.

## Post-Finalization fix (2026-09-26, at explicit direction) — a `labels` entry that is `undefined` keeps its default

Found on `AvatarGroup`'s final review: `labels` was merged as `{ ...defaultLabels, ...labelOverrides }`, so `labels={{ x: t?.x }}` (a missing translation) replaced the default with `undefined`. Probed on this component: `expand` crashed the render, and `navigation` left the `<nav>` without a name. Now merged with `mergeDefined` (a new helper in `packages/utils`, which skips an override that is `undefined`), so each label falls back to its own default. **Finalized status unchanged** — it corrects a genuine defect (`06-engineering-standards.md` §9, question 2), and nothing that rendered correctly changes. A new test fails on the old spread (checked).
