# Checkbox — Storybook/component review findings

*(Migrated from `07-storybook-and-documentation-standards.md` §6 during the guidelines retrofit pass, 2026-08-31 — this file's own content is unchanged from what was there, just relocated. See `07`'s own status table for this component's current Docs-page/Finalized status.)*

**Inputs:** Checkbox — ✅ done (2026-08-23 — comprehensive `06-engineering-standards.md` §9 review, worked one finding at a time across 11 findings): (1) no `Playground` story — the old `Default` story had only `size` wired to a real control; replaced with a full `Playground`, including a `radio` control for `defaultChecked`'s tri-state (`false`/`true`/`"indeterminate"`) and `checked` deliberately `control: false` with a documented reason (driving the controlled prop live without a real `onCheckedChange` wired back would freeze the checkbox, since Radix always defers to a controlled value — the Playground demonstrates the uncontrolled path instead, matching `Tag`'s own precedent for this class of component). (2) Confirmed 6th instance of the JSX-attribute-ordering bug (`05-component-api-conventions.md` §3) — `{...props}` now spreads before the computed `id`/`checked`/`defaultChecked`/`onCheckedChange`/`disabled`/`aria-invalid`/`className`. (3) `AllSizes`/`States`/`IconOnly`/`SelectAllPattern` stories' `render` functions fixed to accept and spread `args`. (4) `aria-label`/`aria-labelledby`/`id`/`className`/`style`/`data-testid` all redeclared on `CheckboxProps` with full JSDoc (previously undocumented, working only via native inheritance). (5) Dev-mode warning added for no accessible name (no `children`/`aria-label`/`aria-labelledby`), matching Button/ProgressBar/ProgressCircle/Spinner/Tag. (6) The unchecked box's `:hover` state was reusing `border.focus` (meant for focus rings only) — fixed to `border.neutral-strong` (added in Phase 23, previously unconsumed by any component). (7) Three `play`-function interaction stories added (`ClickInteraction`, `DisabledInteraction`, `SpaceKeyInteraction` — Space only, not Enter, since the WAI-ARIA checkbox pattern's keyboard contract differs from a native `<button>`'s). (8) Two keyboard-interaction unit tests added at the Vitest layer, mirroring #7 (Tab-then-Space toggles; a disabled checkbox is skipped by `Tab` entirely, via native `disabled` — unlike `Tag`'s `aria-disabled`-based pattern, which stays focusable). (9) Feature-completeness gap (a custom-icon-override pattern comparable libraries support) — built at explicit direction rather than deferred: `icon`/`indeterminateIcon` props added (`PhosphorIcon`, defaulting to the system's own `CheckIcon`/`MinusIcon`), wired into a live Controls-panel select (`argTypes.mapping`, same pattern as Button's `leadingIcon`/`trailingIcon`) and a new `CustomIcons` demo story. (10) No micro-interaction on the checkmark/dash appearing — added a `checkboxIndicatorIn` scale+fade-in animation (`motion.duration.fast` / `motion.easing.emphasized`) on `.indicator`, which only mounts into the DOM on check/indeterminate (Radix's own conditional-mount behavior), so it plays once per state change — a one-shot transition, not a continuous/looping animation, so it's outside `06-engineering-standards.md` §4's `prefers-reduced-motion` requirement (same carve-out as Badge's pop and Tooltip's fade-in). (11) `Checkbox.mdx` Docs page added from scratch, full 10-section template — Related Components links to `Switch`/`FieldLabel`/`FieldError`, none of which have their own Docs page yet, so their cards deep-link to `/story/...--default` instead of a `--docs` route (a new, documented exception to the otherwise Docs-only linking precedent, since every previously-written `RelatedCard` happened to link between already-finalized siblings). A real bug caught and fixed while writing this page: the first-drafted Accessibility section cited `03-token-system-spec.md` by filename in reader-facing prose, which `07-storybook-and-documentation-standards.md`'s own §4 rule prohibits ("never reference an internal `guidelines/*.md` path in visible page content") — reworded to state the contrast claim standalone. **The same violation still exists, unfixed, in the already-finalized `Button.mdx`** (`` `03-token-system-spec.md`'s methodology`` in its own Accessibility section) — flagged here rather than fixed, since Button is finalized and changing it needs explicit confirmation first. Full self-verification, whole package: `tsc` (package + `.storybook`), `eslint`, `tsup` build, and both Vitest projects (`unit`: 713/713, `storybook`: 274/274) all clean.

**Final review pass** (2026-08-23, same day): re-verified the full checklist end to end rather than assuming the 11 incremental findings already covered everything, the same discipline as Button's own final pass — and found two more real gaps. (1) Feature-completeness against Radix itself, this component's own direct upstream primitive, not just the broader comparable-library survey: Radix's `Checkbox` accepts `required`/`name`/`value`/`form` and automatically renders a hidden native `<input type="checkbox">` inside a `<form>` so it participates in real HTML5 form submission and validation — but `CheckboxProps` (extending `ComponentPropsWithoutRef<"button">`, which has no `required` of its own) silently blocked `required` at the type level, and `name`/`value`/`form`, while structurally inherited and already working, were undocumented and invisible in the Properties table. Fixed: `required`/`name`/`value`/`form` added to `CheckboxProps` with full JSDoc (no component-code change needed beyond the type — all four already flowed correctly through the existing `{...props}` spread), wired into live Playground controls, and verified two ways: live in Storybook (`required` toggling `aria-required` on the real DOM node) and via a real `<form>`/`FormData` submission test in `Checkbox.test.tsx` proving `name`/`value` actually post through Radix's own hidden input, not just type-checked. (2) The `has no accessibility violations` test only ever exercised default-styled checkboxes (unchecked/checked/indeterminate/labeled) — `hasError`'s red-border/`aria-invalid` pairing and `disabled`'s dimmed-opacity rendering were never actually run through axe, only assumed safe by inference (same gap class Button's own final review closed for its variants). Extended the test to cover both; zero violations, confirming the assumption held but wasn't previously verified. Also re-confirmed live, beyond what individual fixes already checked: full Docs page render (all 10 sections, `required`/`name`/`value`/`form` rows correctly populated in the Properties table and Playground panel, `form` correctly excluded from live controls), the `States`/`Select-all` galleries at 375px mobile width (no overflow/clipping), and Purple/Emerald × Light/Dark (all 4 combinations render correctly — Emerald hadn't been spot-checked for Checkbox before this pass). Full self-verification, whole package: `tsc`, `eslint`, `tsup` build, and both Vitest projects (`unit`: 715/715, `storybook`: 274/274) all clean. **Finalized 2026-08-23** — per that section's own note, don't make further changes to Checkbox (code, stories, docs, or its tokens) without asking first. **Raw Controls-panel order fixed, 2026-08-24 (same fix and same day as Button's — see the shared root-cause note in `07-storybook-and-documentation-standards.md` §4.1):** the raw per-story Controls panel showed `disabled` jumping to the very front, ahead of `size`/`hasError`/`checked`/`defaultChecked`/`onCheckedChange`/`icon`/`indeterminateIcon` — `disabled` was purely inherited from `ComponentPropsWithoutRef<"button">`, never redeclared on `CheckboxProps`. Fixed by explicitly redeclaring `disabled?: boolean` on `CheckboxProps` (Omitting it from the native extends first, matching the existing `checked`/`defaultChecked`/`onChange` pattern), moving `children` to the top of the interface and `icon`/`indeterminateIcon` ahead of `required`/`name`/`value`/`form` to match `propOrder` exactly. Zero behavioral/DOM/token change. Full self-verification: `tsc`, `eslint`, `tsup` build, both Vitest projects (`unit`: 715/715, `storybook`: 274/274) all clean; live-reconfirmed (after a required dev-server restart — see `07-storybook-and-documentation-standards.md` §4.1) the raw Controls panel and Docs page Properties table both now read `children, size, hasError, checked, defaultChecked, onCheckedChange, icon, indeterminateIcon, disabled, required, name, value, form, aria-label, aria-labelledby, id, className, style, data-testid` — an exact match to `propOrder`.

**Authorized post-finalization change (user-directed, 2026-09-14): `CheckboxGroup` composition support.** While building `CheckboxGroup`, an architecture fork came up: unlike `Radio`, Radix ships no group primitive for checkboxes at all — `Checkbox` is already a fully standalone primitive, so `CheckboxGroup` has to implement its own array-based multi-select coordination. Presented as an explicit choice rather than assumed; user chose "Context-based, mirroring `RadioGroup` exactly," which meant editing this already-Finalized file to add the consuming side of that context. Added two new contexts, `CheckboxGroupContext` (carries the real coordination state and callback — `value: string[]`, `onItemCheckedChange`, `disabled`, `name`, `form` — unlike `Radio`'s own plain-boolean `RadioGroupContext`, since there's no Radix `Root` doing this internally to lean on) and `CheckboxGroupSizeContext` (mirrors `RadioGroupSizeContext` exactly, same reasoning for keeping it a separate channel). `Checkbox.tsx` now reads both: `isGrouped = groupContext !== undefined`; `resolvedSize` follows the same `size ?? inheritedSize ?? "md"` chain `Radio` already established; `resolvedDisabled = isGrouped ? groupContext.disabled || disabled : disabled`; grouped `checked`/`onCheckedChange`/`name`/`form` all read from or delegate to the group context instead of the standalone props. Two new dev-mode warnings added (standalone-only props passed while grouped; no `value` while grouped), mirroring `Radio`'s own pair. **Real bug caught and fixed during this same edit, before it ever shipped:** the outer `<label>`'s dimming class checked the raw `disabled` prop instead of the new `resolvedDisabled`, so a `Checkbox` disabled purely via a group's cascade would correctly disable the control but leave its label text at full opacity — fixed by using `resolvedDisabled` consistently in both places, covered by a new regression test (`CheckboxGroup.test.tsx`'s own "dims an individual Checkbox's label when disabled only via the group cascade").

**Three-question finalization test (`06-engineering-standards.md` §9):**

2. Not reached — question 1 already resolved to "No."
3. Not reached.

## Post-Finalization follow-up (2026-11-17, at explicit direction) — the box's edge clears 3:1

The unchecked box is identified by its edge alone, and `border.neutral` was 2.32:1 on `bg.surface` in the two light themes (and 2.22:1 on the subtle fill), under the 3:1
that WCAG 1.4.11 asks of a control's boundary. The resting edge is now `border.neutral-strong` (4.70:1 on the surface in the light themes, 6.08:1 in the dark ones; `Tree`

`Radio` got the same change. A defect fix (question 2 of the three-question test, `06-engineering-standards.md` §9) at explicit direction: the component stays Finalized.

## Post-Finalization follow-up (2026-10-17, at explicit direction) — an invisible hit area of at least 24 × 24px

`DataTable`'s review found that a `Checkbox` at `xs`, `sm` and `md` is drawn 12, 16 and 20px, under the 24 × 24px minimum target that
`06-engineering-standards.md` §9 asks for at every size, and `DataTable` had patched it inside its own stylesheet. The rule asks for the
fix at the atom, so it is made here: `.root` is `position: relative` and carries an `::after` whose insets are
`min(0px, calc((100% − space.6) / 2))`, an invisible square of the minimum size centred on the box (a box already that big, `lg` and
`xl`, gets none).

**Finalized status is unchanged.** Three-question test (`06-engineering-standards.md` §9): question 1, does it change the rendered or
behavioural output of anything that existed? Nothing visible, and the box, its states and its tokens are as they were; what changed is
where a press lands. Question 2, is it correcting a genuine defect? Yes: a target under the minimum at three of five sizes failed a
requirement that already stood, so the original pass would have failed this line had it measured it. It stays Finalized.
Re-verified: a hidden real-browser check (`HitAreaInteraction`) presses points 11px either side of every size's centre and
asserts each answers, that each box still answers at its own centre in a stack (a hit area doesn't cover the next box), and that the xs box is
still 12px; the `Checkbox` and `CheckboxGroup` suites pass. The new token (`space.6`) has its row in the Docs page. Known cost: in a
stack closer than 24px between box centres the two hit areas overlap by a few pixels, and the later box in the document wins there; the
default stacks are further apart than that.
