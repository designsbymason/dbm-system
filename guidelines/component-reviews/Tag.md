# Tag — Storybook/component review findings

*(Migrated from `07-storybook-and-documentation-standards.md` §6 during the guidelines retrofit pass, 2026-08-31 — this file's own content is unchanged from what was there, just relocated. See `07`'s own status table for this component's current Docs-page/Finalized status.)*

Tag — ✅ done (2026-08-22 — comprehensive Docs page added, modeled on Avatar's/Badge's own template: Playground, Properties table, Variants gallery, Usage guidelines, Best practices, Accessibility, Code examples, Design tokens, Related components). A full `06-engineering-standards.md` §9 review pass followed the same day and found two real gaps: (1) Feature-completeness, against this project's own `05-component-api-conventions.md` §8 definition of done ("...including error and disabled states") as well as a comparable production chip/tag component's own `disabled` prop and this repo's own `Avatar` precedent — Tag had no `disabled` state at all. Added `disabled?: boolean`, scoped to "only meaningful once interactive" (mirrors `Avatar`'s own gate, generalized for a component with no `as`/native-button branch at all — see `05-component-api-conventions.md` §3's new bullet on this), blocking `onClick`/keyboard toggle/remove and applying `aria-disabled` while staying focusable (WAI-ARIA APG pattern, not native `disabled`, since Tag's root is always a `<span>`); also redeclared `aria-label`/`aria-labelledby` explicitly on `TagProps` (`05-component-api-conventions.md` §3's "redeclare component-relevant aria-* props" rule — functionally already passed through via native prop inheritance, but wasn't documented/visible in the Properties table or Playground before this). Both shipped with full JSDoc, CSS (`.disabled` class, `:not(.disabled)` added to all 24 hover rules), a new "Disabled (interactive)" story plus an interaction-test story, 8 new unit tests, and Docs-page coverage (Properties/Playground/Variants/Accessibility/Design tokens all updated) — live-verified across both brand themes × both color modes, Storybook's own Accessibility addon (0 violations), and the `storybook` Vitest project (every play function, including the new one, in a real browser). (2) Responsiveness, caught live via the viewport check required by this same review pass: the "All sizes" story's demo container was missing `flexWrap: "wrap"` (present on every sibling multi-instance story — `AllTones`/`Solid`/`Outline`) — at mobile widths its last tag clipped off-screen instead of wrapping. Fixed to match its siblings; confirmed live at 375px. Full self-verification after both fixes: `tsc`, `eslint`, `tsup` build, and both Vitest projects (`unit`: 644/644, `storybook`: 265/265) all clean. **Finalized 2026-08-22** — per that section's own note, don't make further changes to Tag (code, stories, docs, or its tokens) without asking first. **Per-variant CSS/token redesign, same day, at explicit direction (migrated here 2026-08-31 from `03-token-system-spec.md`, where it had landed without a proper home — token-adjacent but really component-CSS work, not a token decision):** a full pass across all three variants (`subtle`, `solid`, `outline`), one at a time, converting every variant to real `border`/`background`/`text`/`icon` properties with **no `box-shadow` anywhere** except where explicitly confirmed correct as-is. `subtle` gained a real decorative `border.{tone}-subtle` (previously none), its selected state moved from a shared `box-shadow` ring to a real `border-color` change (4.51–7.03:1 light / 7.45–10.68:1 dark, all clear the 3:1 floor with margin), and hover was fixed to apply while selected too (the original box-shadow-based exclusion no longer applied once selected used `border-color` instead). `solid` was reviewed and confirmed correct as-is (its offset-halo `box-shadow` stays, by design) — same hover-while-selected fix applied. `outline` got the same border conversion, plus its default-state icon decoupled from `text.{tone}` for the first time (own `icon.{tone}`, matching the `subtle`/solid-fill fixes already applied elsewhere — `guidelines/adr/0005`'s general fill/text-decoupling principle) and a genuinely new selected-hover state (previously nothing happened on hover at all). Across every variant, `icon.{tone}` decoupling from `text.{tone}` closes the same category violation already fixed elsewhere in the system (icons and text are independently-tracked token categories, deliberately not the same value via `currentColor` inheritance).

Two real, separately-found bugs in the removable "×" icon, both confirmed by direct measurement, not visual inspection: (1) the non-interactive path (rendered via `CloseButton` at the time) had its icon size double-remapped — `Tag`'s own correct size was being re-remapped a second time by `CloseButton`'s internal scale, producing a `×` visibly smaller than the leading/trailing icons (12px vs 20px at `xl`); fixed with a `CloseButton` `iconSize` override prop (since superseded — `Tag` no longer calls `CloseButton` at all, see `05-component-api-conventions.md` §10). (2) The *interactive* (selectable/clickable) removable path renders the `×` through a separate, undecorated `<span>`, not `CloseButton` — that span was missing `display: inline-flex; align-items: center`, producing a real, reproducible 1.7px vertical offset against the leading/trailing icons; fixed by adding the missing flex properties. Both paths verified matching pixel-for-pixel across all 5 sizes afterward. Full self-verification throughout this pass: `tsc`, `eslint`, the full unit/Storybook test suites, and live checks (computed styles, not just visual) across both brand themes/both modes for every variant/state combination — no re-opening of Tag's own Finalized status needed per `06-engineering-standards.md` §9's three-question test (design-quality refinement to already-compliant surface, not a defect fix, but scoped to this component's own files only).

## Post-Finalization change (2026-09-21, at explicit direction) — `variant="outline"` renamed `variant="outlined"`

A survey of the system's variant values found `outline` (`Tag`, `Indicators`) and `outlined` (`Card`, `EmptyState`, `Pagination`); `outlined` was chosen as the single spelling and is now a
rule (`05-component-api-conventions.md` §2). `TagVariant` is now `"subtle" | "solid" | "outlined"`. **Earlier entries in this file use the old spelling `outline`; they are history and
were not rewritten.** Everything named after the variant moved with it: the `.outline{Tone}` CSS classes (now `.outlined{Tone}`), the story export and snippet keys, the Docs page prose and
examples, and the tests. **Breaking for a consumer** (`variant="outline"` is no longer valid) — the package is unpublished (`0.0.0`), so no migration is needed yet.

Under the three-question test in `06-engineering-standards.md` §9 this is a preference change to already-compliant surface confined to the component's own files, so a **partial
re-finalization**: re-verified — types and JSDoc, stories and Docs page, tests, and rendering. Rendering is unchanged, and provably so: with the rename reversed, all seven files
are byte-identical to what was committed, so no logic, style, token or behaviour changed. Not re-run, because nothing they cover was touched: the contrast and theming checks and the
feature-completeness pass. A first pass missed nothing here; the two class selectors that pattern skipped were in `Tabs`, not `Tag`.

## Post-Finalization fix (2026-10-03, at explicit direction) — remove button's hit area below 24 × 24px

Found by `TableToolbar`'s review: the real remove `<button>` is 12, 12, 12, 16 and 20px across `xs`–`xl` (the glyph's size), under WCAG 2.5.8's 24 × 24px minimum, and no earlier
review decided that. Fixed by growing the hit area only: `.removeButton` is `position: relative` and gets an invisible, centred `::after` of at least `--dbm-space-6` (24px) square. The

## Post-Finalization changes (2026-10-10, at explicit direction) — the `highlight` tone, and `brand` as the default tone

Two changes asked for by the user, run through the three-question test (`06` §9) separately.

**1. A `highlight` tone (additive).** `TagTone` gains `"highlight"` (after `warning`, as in `BadgeTone`), in every variant and state, from the existing `highlight` family ([ADR-0042](../adr/0042-yellow-is-an-anchored-scale-with-its-own-light-end-chroma-and-the-highlight-semantic-family.md)); no new token.
- **Subtle:** `bg.highlight-subtle` / `border.highlight-subtle` / `text.highlight`; hover `bg.highlight-subtle-hover`; selected border `border.highlight`.
- **Solid:** `bg.highlight` / `text.on-highlight`; hover `bg.highlight-hover`; selected ring `border.highlight`.
- **Outlined:** `border.highlight` / `text.highlight`; hover `bg.highlight-subtle-hover`; selected converges to solid (`bg.highlight` / `text.on-highlight`, hover `bg.highlight-hover`).
- **Icons:** `icon.on-highlight` on a solid fill. On the subtle and outlined fills the icon takes the tag's own `text.highlight` through `currentColor`, because `icon.highlight` is 2.87:1 on `bg.highlight-subtle-hover` in light, under the 3:1 non-text floor (`03` says an icon on that fill takes `text.highlight`'s step). `standaloneToneIcon` therefore holds `undefined` for `highlight`.
- **Contrast, measured live from the resolved tokens (light / dark):** subtle text on fill 6.64 / 9.08, on hover 6.13 / 6.42; solid text on fill 4.67 / 6.42, on hover 6.89 / 7.63; outlined text on the surface 6.89 / 8.97, border on the surface 3.23 / 8.97; selected subtle border on the subtle fill 3.11 / 9.08; selected solid ring on the surface 3.23 / 8.97. All match `03`.
- **Result:** purely additive (a new value of an existing prop, no change to anything that existed), so **stays Finalized**; scoped pass: types and JSDoc, stylesheet, stories (every tone grid), snippets, Docs page (tone options, nine token rows), two unit tests (classes in each variant and state; icon tone).

**2. `tone` defaults to `brand` (was `neutral`).** This changes the rendered output of every `<Tag>` that passes no `tone`, so it is a preference change to existing surface, not a defect fix: step 3 of the test, **partial re-finalization**.

The Docs-page previews that use a bare `<Tag>` (`Badge`, `Icon`, `TableToolbar`, `TagsInput` related-component cards, the `Tag` Docs page) now show a brand tag, which is what the default is.
- **Updated:** the default in the JSDoc, the Playground's `tone` arg and its Default column, the snippet builder (omits `brand`, writes `tone="neutral"`), the Docs page's tone guidance (a tag is `brand` unless told otherwise; `neutral` for a plain label), and the tests that asserted `neutral` as the default.

## Post-Finalization addition (2026-10-10, at explicit direction) — `removeTabStop`

`TagsInput` asked for its chips to be one tab stop with arrow-key movement ([ADR-0050](../adr/0050-tagsinput-chips-are-one-tab-stop-with-arrow-key-movement-and-tag-lets-its-remove-button-leave-the-tab-order.md)), which needs `Tag`'s real remove button out of the tab order.

- **`removeTabStop?: boolean`** (default `true`): with `false` the real remove button has `tabindex="-1"`: still focusable by script and by a press, still named and read, not in the tab order. Only the real button is affected; the decorative glyph shown on a clickable or selectable tag was never a tab stop.
- **Finalized status unchanged** under the three-question test: purely additive, and a default that leaves every existing caller as it was. Scoped pass: JSDoc, a Controls entry and Playground arg, the snippet builder, the Docs page's `propOrder`, and a unit test (the attribute is absent by default, `-1` when off, and the button still takes focus).

**Hover label contrast** (2026-11-25, at the maintainer's direction, found while drawing `Tag` in the Figma library): the `subtle` and `outlined` looks left the label in `text.{tone}` on `bg.{tone}-subtle-hover`, which is under 4.5:1 in the light themes for `info`, `warning` and `danger` (4.15:1, 4.2:1 and 4.44:1). Those six hover rules now set the label to three new semantic tokens, `text.info-hover`, `text.warning-hover` and `text.danger-hover` ([ADR-0245](../adr/0245-a-tags-hover-label-takes-three-semantic-hover-text-tokens-over-darkening-the-status-text-tokens-or-changing-the-hover-treatment.md)), 6.1:1 or more on the fill; the dark themes use the same colour as before. A real-browser check (`Tag.checks.stories.tsx`) hovers each of the six with a real pointer and holds the computed colour to the token and 4.5:1, and fails with the six lines removed. The Docs page lists the tokens. **Finalized status unchanged:** an authorised fix, with no new prop or behaviour.

## Post-Finalization review pass (2026-11-25, at the maintainer's direction) — six findings, all fixed

A full `06` §9 review found six things; every one is fixed and held by a test that fails without the fix.

1. **A same-named prop could replace what the tag computes (a defect).** `{...props}` came after `role`, `tabIndex`, `aria-pressed`, `aria-disabled`, `aria-keyshortcuts` and `onKeyDown`, so a passed `role="link"` won and a caller's `onKeyDown` dropped the tag's own handler (Enter no longer activated it: reproduced in jsdom with a real keydown). The computed attributes are now spread after `{...props}`, in an object that leaves out an attribute the tag has no opinion on (a plain tag still takes a `role`), and the caller's `onKeyDown` runs first and can claim a key with `preventDefault()`.
2. **The remove button's default name was wrong (a defect).** `children.toString()` gave "Remove Status: ,Active" for `Status: {value}` and "Remove [object Object]" for an element, and `??` let `removeLabel=""` give a blank name (flagged, not fixed, in the 2026-09 stories). A `textOf` helper joins the strings and numbers through elements and arrays, the fallback is "Remove" with no text, and `||` makes an empty `removeLabel` mean the default.
3. **The Playground's remove label went stale.** Its `removeLabel` arg was a fixed "Remove Design", so a tag showing "Delete" kept that name. The arg is `""`, which now means the default.
4. **The Docs token table had drifted.** Rows for `space.2`, `space.3`, `space.6` and `icon-size.xs`–`md` were missing; they are added and `Tag.docs.test.ts` holds the table to the stylesheet and the icon tones in both directions (it fails with a row removed).
5. **The Properties Default column had gaps.** `defaultSelected` and `removeLabel` showed "—" and `tone` was unquoted beside `"subtle"` and `"md"`; each argType now carries its summary.
6. **A long label overflowed a narrow container.** A 109-character label drew 696px wide at a phone width. The label is drawn in a `span` of its own (none for an icon-only tag), and the tag has `max-inline-size: 100%` with the label shortened by an ellipsis and the icons kept from shrinking. The glyph ink of `gypqjyQ` was measured inside the label box at the largest size. A real-browser check (`Tag.checks.stories.tsx`) fills a 12rem box with a long label and holds the tag, the ellipsis, the icon and remove sizes and a short label's hug; it fails without `max-inline-size`.

**Finalized status unchanged** under the three-question test (`06` §9): 1 and 2 are defect fixes; 3 to 5 are stories and docs only; 6 changes the DOM (a label `span`) but corrects a broken responsive layout, a defect, and leaves every tag that fits as it was. Re-verified: baseline correctness, accessibility (the new tests), responsiveness, the Docs page and the unit and real-browser runs. A consumer test that reached a tag through `getByText` now gets the label `span` and should use the role or a test id; `Tag`'s own tests did.
