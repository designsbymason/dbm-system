# RatingInput — build and review findings

**Inputs & Forms:** RatingInput — built 2026-10-04, item 32 in the molecule build order (`04-component-inventory.md`). **Finalized 2026-10-04** by the user, after the final review recorded at the end of this file, accepting the half-step target-size limit (finding 8) as documented. Decision: [ADR-0041](../adr/0041-ratinginput-is-a-native-radio-group-with-two-radios-per-icon-at-half-steps-over-a-slider-role.md).

**What it is:** a rating field drawn as a row of icons over native radios. Flat props (not compound); `ref`, `id`, `data-testid` and the `aria-*` props go on the element that carries the role (`radiogroup`, or `img` when read-only), `className`/`style` on the outermost box. A number value (`0` for none): `max` (default 5, 1 to 10), `value`/`defaultValue`/`onValueChange`, `precision` (`1` or `0.5`), `size`, `tone` (`brand` default, `highlight`, `warning`, `success`, `info`, `danger`), `icon` (a Phosphor reference, a star by default), `readOnly`, `clearable`, `hasError`/`disabled`/`required`, `name`, `valueNames` with `showValueName`, `formatNumber`, `labels` (`itemLabel`, `valueText`, `notRated`).

**Decisions put to the user before building:** the structure (a native radio group, chosen over a slider role), precision (whole and half steps), and the first-version extras (read-only display with fractional fill, hover preview with clearable, a custom icon with per-value names, the core props).

**Composition checkpoints (06 §9):** compound sub-parts — not applicable (flat props); atom reuse — the icons are `Icon`; consumed-atom defects — none found; Radix audit — not applicable (native radios); cross-part ARIA wiring — `id`/`aria-labelledby`/`aria-describedby` from a `FormField` land on the group (tested in a `FormField` story and unit tests); composed tab order — one tab stop (the chosen radio, or the first), tested forwards in jsdom and Chromium; no nested provider.

**Defects found by running it in a real browser, all fixed:**
- **An empty `name` ungrouped the radios.** Chromium's Tab went to the first radio, not the chosen one, because the Playground passes `name=""`, which was taken as a real (empty) name; the radios were separate tab stops. An empty name now counts as no name (a unit test and a deliberate break confirm it).
- **A pointer resting over an icon overrode a keyboard change.** The hover preview now stops when any key is pressed.
- **A test aimed at the wrong element:** a half-step press must land on the element under the point, not the group; the story presses what `elementFromPoint` finds.

**Contrast and shape:** the icon colours come from the `icon.*` tokens, which are on the system's non-text 3:1 record: the default `icon.brand` 7.37:1 (Purple, light) and 7.45:1 (dark) on `bg.surface`, `icon.highlight` 3.23:1 and 8.97:1, `icon.warning` 4.78:1 and 8.12:1, the other tones as recorded for `icon.*`, and the outline `icon.secondary` 3.25:1 / 4.34:1. What is chosen is told apart by shape (a filled icon against an outline), not colour alone, which also survives forced colours. The value name is `text.secondary` (AA).

**Tokens:** no new tokens, no component tokens. Icon sizes use the existing `icon-size.*` scale (one step above the shared size scale: `xs` is 16px, `xl` 40px); every choice is at least 24px (`space.6`).

**Behaviour worth stating:** a value between steps is shown as the nearest step, and read-only draws any value exactly; a half step shows the name of the whole value below it; the hover preview is for mouse pointers only; pressing the chosen value again, or Backspace, Delete or Escape, clears when `clearable`; a read-only rating with a `name` submits its value through a hidden input; the value name keeps the space for the longest name, so nothing moves.

**Tests:** 54 unit tests (the group and its named radios, icon layers hidden from assistive technology, `max` and its fallback, choosing by press and arrows from one tab stop, controlled and uncontrolled, clamping and a non-number value, half steps, snapping, clearing by click and three keys, the hover preview for mouse only, read-only as an image with its exact fill and hidden input, states, forms including no name and an empty name and required validity, value names and their widths, labels with `undefined` and `formatNumber`, ref/id/aria placement and computed attributes winning, a custom icon, left to right, a server render, StrictMode, jest-axe in five configurations), a Docs-page token guard (`RatingInput.docs.test.ts`), and 10 hidden real-browser stories (choosing, hover preview, left and right half presses, target size at every size, the clipped fill, the value name never moving anything, the focus ring, forced colours, left to right, a narrow container). **Mutation check:** seven deliberate breaks (empty name as a name, hover surviving keys, touch previews, no snapping, half order swapped, click-to-clear removed, half hit area moved) were all killed.

**Self-verification (real runs):** lint, unit and Chromium suites, build and the bundle-size check recorded in the commit message; the Docs page opened in a running Storybook (all template sections, 12 canvases, every Properties row described, defaults shown), the native Controls order and the Properties table order read live and matching the types file, with no inert "Set …" placeholders; sizes, tones, half steps, the read-only fraction and the value name looked at in light, and a choice with its name in dark.

**Not yet done (for the final review):** all four themes by eye (two looked at); a real touch device (tap-to-choose, no hover preview); a keyboard walk through the Docs page's own Playground; screen-reader announcements of the group and each choice (checked by structure and accessible names, not by listening); a forced-colours look at the clipped fill.

**Known limits:** `max` above 10 falls back to 5 with a warning; the scale follows `dir`, not the page's direction (set it per rating); a value passed in that is off a step is shown as the nearest step; a read-only rating with a `labelledby` includes its own text in the name by referencing itself; the rating doesn't reset with a native form reset.

## Yellow and the `highlight` tone (2026-10-04, at explicit direction)

The new yellow scale and its `highlight` semantic family ([ADR-0042](../adr/0042-yellow-is-an-anchored-scale-with-its-own-light-end-chroma-and-the-highlight-semantic-family.md)) give a rating's stars a colour that reads as yellow, where `warning` (amber) read as brown. `tone` gains `highlight`, **now the default** (`warning` stays an option); the stars use `icon.highlight` (`yellow.600`, 3.23:1 against `bg.surface` in light, 8.97:1 in dark) with the outline in `icon.secondary`. `RatingInput` was not yet Finalized, so changing the default did not reopen anything. The Tones story, the Properties table, the snippets and a new test (the default tone and an explicit one) are updated. Looked at in light and dark next to the other tones: in light the stars are an olive yellow, noticeably different from the brown of `warning`, which is the darker single mustard chosen so the icon passes 3:1 on its own.

## The hover preview's look (2026-10-04, at explicit direction)

A star the pointer would add is now drawn as a pale fill of its tone under an outline in the tone's border colour (`bg.<tone>-subtle` and `border.<tone>`, for each of the six tones), instead of in the solid chosen colour, so a preview is plainly not a choice. Two stacked layers do it, because Phosphor's filled star and its outline are separate shapes: the `fill` weight in the subtle colour under the `bold` weight in the border colour, between the empty outline and the chosen fill, cut off after the previewed fraction like the chosen fill (half steps preview half an icon). The chosen stars stay solid up to the pointer; a pointer below the rating still empties the chosen stars above it and previews nothing new. `data-fill` is now the solid part and `data-preview` (present only while previewing) is the previewed part.

**Tokens and convention:** the layers' colours come from `bg.*-subtle` and `border.*`, not `icon.*` (the "an icon's colour comes from `icon.*`" rule, `05` §6, is about an icon glyph; this is a two-colour shape, a fill and an outline, which is what those two token families are for). No new tokens. **Contrast:** the outline is `border.<tone>`, on the record at 3:1 or better against `bg.surface` for the state-identifying tones (`border.highlight` 3.23:1 light, 8.97:1 dark); the fill is a decorative tint (about 1.04:1 in light for `highlight`, where it is `yellow.50` and the outline carries the preview, and in dark `bg.highlight-subtle` is `yellow.950`, close to the surface, so the outline carries the preview there). **Forced colours:** every colour becomes one system colour, which would make the preview a solid star like the chosen ones, so the preview is drawn as an outline in `CanvasText` with `Canvas` inside.

**Tests:** the hover tests now assert the solid and preview portions separately (a lower hover, half steps, no preview for touch, disabled or after a key press, the preview layers hidden from assistive technology), and two real-browser stories check that the preview's fill and outline resolve to the right token in all six tones and that it is an outline in forced colours. Four deliberate breaks (the solid part ignoring the hover, the preview not exposed, a wrong stroke token, the forced-colours rule removed) were all killed. Looked at in light and dark in the running Storybook.

## The review-summary row: `showValue`, `count` and `suffix` (2026-10-04, at explicit direction)

For the review use case (`4.2 ★★★★☆ (124) Read reviews`) the user asked what should be props and what a developer should build. Decided with them: the number and the count are props, because they belong to the component's own value and its text alternative; the link is a slot, because a link is its own control.
- **`showValue`** writes the rating as a number before the icons on the same row: the chosen value, or the one under the pointer while previewing (a read-only rating draws its exact value). One decimal always (`4.0`, `4.2`) through `formatValue` (default `value.toFixed(1)`, plain numbers in; a locale's numerals go through the consumer's own formatter, since `formatNumber` can't force the decimals). The space for the widest value (`formatValue(max)`) is kept with a `ch` minimum width and tabular figures, so a value that changes on hover never moves the icons. Hidden from assistive technology, since the rating's own text already says it.
- **`count`** (read-only summaries only) writes `(124)` after the icons through `labels.count` (default `(${formatNumber(count)})`) and adds the count in words to the read-only image's text alternative through `labels.countText` (default "124 reviews", "1 review"): "Average rating, Rated 4.2 out of 5, 124 reviews". The visible count is hidden from assistive technology so nothing is read twice. A count that is not a finite number is ignored.
- **`suffix`** (read-only summaries only) is a slot after the count on the same row, for a `Link` or `Button`; it is a real control that keeps its own role, focus and name, and inherits the row's size. On an interactive rating `count` and `suffix` are ignored with a development warning (decided with the user: a count and a link only make sense on a summary).
- **Layout:** the number and the icons stay together (one nowrap unit); the count and the link wrap below it on a narrow container, which a real-browser story measures.

**Tokens:** no new tokens; the number uses `text.primary`, `font-weight.medium` and `space.2`, the count, the value name and the link `text.secondary` at the row's `--name-font-size` step (a text size one step under the icon's box). **The number is one font-size step larger than that** (`--value-font-size`: `sm` at `xs`, `base` at `sm`, `md` at `md`, `lg` at `lg`, `xl` at `xl`; changed 2026-10-04 at the user's request, since it read small next to a large star), so it leads the row and the count and link stay quiet; it stays level with the icons, and the kept width follows the larger figures.

**Tests:** 18 unit tests (the number with one decimal, exact when read-only, `0.0` for none, following the pointer, `formatValue`, the kept width at `max` 5 and 10, no number unless asked; the count's text, name, labels with `undefined`, `formatNumber`, a non-number; the suffix on the same row and as its own tab stop; both ignored with a warning on an interactive rating; jest-axe on a whole summary), and three real-browser stories (one row, in order and level; a changing value never moves the icons at `max` 10 and half steps; the count and link wrap in a narrow container). **Mutation check:** five deliberate breaks (the count missing from the name, the number not hidden, no width reserve, the count shown on an interactive rating, the number ignoring the preview) were all killed. The Docs page, the native Controls order and the Properties table were read live and match; two new variant stories and their Show-code panels, and the Playground's `showValue` and `count` controls (`count` only passed while `readOnly` is on), were looked at.

## Story wiring audit (2026-10-04, after a user report that the Playground's `count` showed nothing)

The report was the visible end of a wider problem, so every visible story's live controls were driven from the page itself (changing each control through Storybook's channel and checking the canvas markup changed). Findings, all fixed:
1. **`count` and `suffix` were offered while `readOnly` was off**, where the component ignores them by design, so the Playground's `count` control looked wired and did nothing. They are now offered only while `readOnly` is on (`if: { arg: "readOnly" }`), and the Playground gained a `suffix` choice ("None" / "Read reviews link"), so the link can be tried there too. `count` had also been in the shared meta args, so every interactive story passed it and logged the "ignored" development warning; it now lives in the Playground's own args.
2. **`defaultValue` was dead in every story**: an uncontrolled rating keeps its first value, so the control changed nothing on screen. The stories are keyed by it with a meta-level decorator, so changing it starts the rating again at the new value.
3. **`precision` was still offered on the read-only stories**, where a read-only rating draws its value exactly; the control is off there.
4. **`In a FormField` listed no `showValue` or `count` control-off entries** (both new), leaving two live-looking controls that did nothing.
Also: the docs-page Playground block honoured no `if`, and once it did, the conditional control appeared several seconds after the switch that revealed it (the block waited for the round trip), so it now uses the value just set. A re-run of the audit finds no dead control in any visible story. `clearable` only changes behaviour (a press clears), so a markup check can't see it; it is covered by its unit and browser tests. **Not the only component with this**: any story with an uncontrolled `defaultValue` control and no remount (several Finalized components' stories) likely has a dead `defaultValue` control; not touched here.

## No-value dash, `roundTo` and `dir` (2026-10-04, from the review's gap list, at explicit direction)

1. **A rating with no value writes a dash, not `0.0`.** `showValue` on an unrated rating read "0.0", which can look like a zero given. The default `formatValue` now writes `–` for `0` (`(value) => (value > 0 ? value.toFixed(1) : "–")`); `formatValue` is handed `0` for no rating, so a custom one decides for itself (`0.0` if wanted). No extra prop.
2. **`roundTo` (`1` or `0.5`) draws a read-only average to the nearest whole or half icon** (3.3 as three and a half) instead of exactly; the number from `showValue`, the text alternative and the submitted value stay exact (`reported` against the drawn `current`). For read-only only: on a rating a person can change it is ignored with a development warning, since `precision` is what governs choosing there; an invalid value warns and draws exactly. The value name follows the drawing.
3. **`dir` (`"ltr"` default, `"rtl"`)** is an explicit prop, not read from the page (`05` §3's Radix-direction convention). In `rtl` the first icon is at the right, the fill and the preview are cut from the left (`:dir(rtl)` clip rules), the half-step radios sit on the logical halves (the lower half at the right), and the number, count and link follow the same order. **Found in a real browser:** Chromium's native radio arrows do not follow the direction a group is drawn in (Left went to the lower value, which is on the right), and browsers disagree on it, so in `rtl` Left and Right are handled by the component (Left chooses the next value, looping like a radio group; modified keys are left alone; Up and Down stay native).

**Tests:** unit tests for the dash, `0` handed to `formatValue`, `roundTo` (whole, half, exact name, number and submitted value, the value name, ignored with a warning, invalid), `dir` (default, rtl, not read from the page, the same choices in the same order, the turned-round arrows, modified keys, left to right untouched), and three real-browser stories (rtl: order, the fill from the right, half presses and the arrow keys; an rtl read-only fill; a rounded average). **Mutation check:** six deliberate breaks (the dash removed, `roundTo` ignored, the name using the rounded value, the number using the rounded value, the rtl arrows not handled, the rtl clip removed) were all killed. The scripted control audit (`07` §5) finds no dead control in any visible story, including the new `dir` and `roundTo` (conditional on `readOnly`) ones. Looked at in the running Storybook: a right-to-left rating (number at the right, stars filled from the right, the half star filled on its right side) and a rounded average (3.3 beside three and a half stars).

## Final review before Finalization (2026-10-04)

A full `06-engineering-standards.md` §9 pass over the finished component (re-read end to end, then probed). Findings, all fixed unless marked:

1. **A read-only rating named by `aria-labelledby` dropped its own text when no `id` was passed.** The name referred to `…-self`, an id the element never carried, so "Average rating Rated 2 out of 5" came out as "Average rating". The element now carries the id it refers to (a probe without an `id` fails without the fix; the earlier test had passed one).
2. **The consumer's `onKeyDown` and `onPointerLeave` were dropped on a read-only rating** (destructured, attached only to the interactive group). Passed through now; the lint rule against listeners on a `role="img"` is disabled on that line with the reason (they are the consumer's own, as with any native prop).
3. **The Docs page and the `id` JSDoc said a `FieldLabel`'s `htmlFor` could name the rating.** A `<label for>` names only a labelable element, and the group is a `div`: only `aria-labelledby` (or `FormField`) works. Reworded in the Properties text, the Do list and the related-component card; a development warning now fires when a rating a person can change has no `aria-label` or `aria-labelledby`.
4. **`formatValue` was trusted**: a non-string return measured the wrong width (`undefinedch`); the text and the reserved width now go through `String`.
5. **A long scale overflowed a phone**: ten icons at `md` were 450px wide and at `lg` 540px in a 375px viewport, so the page scrolled sideways. The icons wrap onto a second row instead (measured: no horizontal scroll, two rows, the count and link below); a real-browser story checks it and fails without the wrap. Five icons fit 375px at every size, `xl` included.
6. **The Playground's `defaultValue` was 3**, not the prop's real default (0); now 0 in the Playground only.
7. **ADR-0041 still said the scale "always reads left to right"**: amended (marked) for `dir`.
8. **Size claim corrected:** "every choice is a target of at least 24px" holds at whole steps; at half steps each half is half an icon (12px at `xs`, 14 at `sm`, 16 at `md`, 20 at `lg`, 24 at `xl`). **Known and accepted, not fixed:** that falls under WCAG 2.5.8's minimum at the smaller sizes, and the two halves are adjacent so the spacing exception doesn't apply. Widening the hit areas would mean wider gaps between icons. The Docs page and the prop descriptions now say so, and recommend whole steps or `xl` on a touch screen; every half is reachable by keyboard at any size. **Accepted by the user when the component was Finalized (2026-10-04):** half steps stay as built, with the limit documented and whole steps or `xl` recommended on a touch screen; revisit if the system ever adopts wider hit areas for adjacent targets.
9. **Known and accepted:** Escape clears a `clearable` rating, but inside a dialog the dialog's own document-level Escape handler runs first and closes it (Backspace and Delete are the reliable keys there); documented. A native form reset doesn't clear the rating (state, like the other controls here); the Playground's `clearable` and the form-reset cases are covered by tests, not by a markup check.

**Also verified, no change needed:** a server render and StrictMode; computed attributes win over a consumer's same-named props (in both branches, tested); `{...props}` before computed attributes; one tab stop and the suffix as its own stop; the hover preview for mouse pointers only and stopped by a key; forced colours (the preview and the focus ring); right to left (order, fill, half presses, arrow keys); all 14 visible stories' controls driven live (no dead control); the Show-code snippets typechecked against the real components; all four themes by eye (the brand tone follows Purple and Emerald in light and dark, and the other tones are consistent); the Docs page, the native Controls order and the Properties table order (types, `propOrder`, argTypes and the rendered tables agree) and the table's width against `SearchInput`'s.

**Still not done:** a real touch device (tap-to-choose, no hover preview, the half-step targets above); a screen-reader listen (checked by structure and accessible names only).
