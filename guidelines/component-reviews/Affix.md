Proved it wasn't theoretical before fixing: rendered `<Affix data-stuck="false">` and confirmed the DOM came out `data-stuck="false"` regardless of real state; fixed by moving `{...props}` first (10th confirmed instance, `05-component-api-conventions.md` §3), with a regression test verified to actually fail against the reverted code before being trusted. (5) Feature-completeness gap, named against a comparable component of the same name and role and built at explicit direction: `scrollContainerRef` — the `IntersectionObserver`'s `root` was always `null` (the viewport), which doesn't correlate correctly with a nested scrollable container's own scroll position (`position: sticky` itself already works against any scrolling ancestor with no configuration; only the *stuck-state detection* needed this). Named `scrollContainerRef` (a `RefObject`) rather than a `target`-style getter function — more idiomatic for this system's own conventions, and unambiguous where "target" alone isn't. Real, severe, previously-shipped structural bug, found via a second, more precise direct user report the same day.** The user pushed back on the "false signal" conclusion with a specific description that didn't match automation flakiness: in `Playground` with `side="top"`, the header's own text correctly flips "Scroll down" → "Stuck!" while scrolling, but the header visually keeps scrolling away with the rest of the content instead of pinning to the viewport top. Re-investigated with a `getBoundingClientRect()` check instead of trusting the attribute, and found the real defect: `Affix.tsx` wrapped the sentinel and the sticky root together in a shared `.wrapper { position: relative }` div, which made that wrapper the sticky element's CSS *containing block* — and since the wrapper's only other child (the sentinel) is `position: absolute` and contributes no flow height, the wrapper was never taller than the sticky content itself, leaving it almost no room to actually stay pinned. Confirmed empirically before fixing: scrolling 1400px down showed `getBoundingClientRect().top` at `-506px` (fully off-screen) instead of `0`. Fixed by removing `.wrapper` entirely and rendering the sentinel and sticky root as plain `Fragment` siblings ordered by `side` (sentinel first for `side="top"`, last for `side="bottom"`) — siblings inherit whatever containing block the *consumer's* own surrounding layout provides, which is normally the whole scrollable region `Affix` is meant to stick through, not an Affix-internal wrapper sized to its own content. Verified the fix rigorously, not just visually: temporarily reverted to the buggy wrapper structure, confirmed the new regression test (asserting `getBoundingClientRect().top` stays `0` across a real `window.scrollTo`) failed against it exactly as expected, then restored the fix and confirmed it passed. `side="bottom"` had zero test coverage before this and turned out to need real geometry care to test correctly (`bottom: 0` sticky requires substantial *leading* content and engages scrolling *down*, the mirror of `top`'s trailing-content/scroll-down-from-zero case) — added as a new `BottomScrollInteraction` story with its own `play`-function regression test, confirming `getBoundingClientRect().bottom` stays pinned at `window.innerHeight` across scroll. `WithinScrollContainer`'s own play function gained the equivalent visual-position assertion (with a `<3px` tolerance — the panel's own border-width creates a real, expected sub-pixel offset between its border-box and the edge Affix pins to, not a bug). **Lesson for future `IntersectionObserver`-based components: a passing `data-stuck`/state-based test is not proof the underlying CSS positioning works — assert on real geometry (`getBoundingClientRect()`) too, since the two are independently implemented and can diverge exactly like this.** Live-reconfirmed in a real Chromium tab post-fix: `side="top"` in `Playground`, scrolled to 1400px, `top` reads `0` (was `-506`).   **Two more real bugs found and fixed, same day, while specifically re-checking the Docs page's Playground and Variants sections at direct user request (a follow-up check after the structural sticky-positioning fix above):**

  (1) **Direction-agnostic stuck detection.** The stuck-state logic (`stuck = !entry.isIntersecting`) couldn't tell "the sentinel scrolled past the edge" (genuinely stuck) from "the sentinel hasn't been scrolled to yet" (mounted below the fold — a long Docs page stacking multiple demos is exactly this case, but so is any real page where `Affix` sits deep in content, or behind a route that lands mid-page) — both report `isIntersecting: false`. Caught by loading the Docs page itself: at `scrollY: 0`, the "Sticky table-style header" Variant (positioned far down the combined page) read `data-stuck="true"` and rendered "Stuck!" despite never having scrolled anywhere. Fixed by comparing the sentinel's own edge against the observed root's edge instead (`entry.boundingClientRect.top < (entry.rootBounds?.top ?? 0)` for `side="top"`, the bottom-edge mirror for `side="bottom"`), which disambiguates "scrolled past" from "not yet reached." `side` added to the effect's dependency array since the callback now reads it. Three new regression tests added (`Affix.test.tsx`, `unit` project: 13→16) — one for the below-the-fold case, one confirming `side="bottom"` uses its own edge rather than reacting to the opposite one — all three verified to actually fail against the reverted `!entry.isIntersecting` logic before being trusted, matching this file's own established discipline. Re-ran the real Chromium-backed `storybook` Vitest project after the fix (still 5/5) to confirm the directional `rootBounds`/`boundingClientRect` logic holds under an actual browser `IntersectionObserver`, not just the jsdom mock.

  (2) **Storybook Docs-mode breaks page-scroll sticky demos, independent of Affix's own correctness.** Even after fix (1), the Playground and Sticky-header demos still never visually stuck when viewed through the Docs page's `<Canvas>` blocks (though they worked correctly on their own standalone sidebar story pages, and in every automated test). Root cause: Storybook's addon-docs wraps every inlined `<Canvas>` story in a `.docs-story` container that unconditionally sets `overflow: auto` — to contain wide/tall demos without blowing out the page layout — and per the CSS spec, any ancestor with `overflow` other than `visible` becomes `position: sticky`'s nearest scrolling-ancestor reference, *even with zero actual overflow* (confirmed: `.docs-story`'s own `scrollHeight === clientHeight`, so it never has a real scrollbar to move). A page-scroll-based `Affix` (no `scrollContainerRef`) trapped behind that boundary has no real scroll delta to react to and can never stick, regardless of how correct its own CSS or JS is. This is a Storybook/MDX architectural constraint, not something fixable inside the component. Fixed per-story via `parameters: { docs: { story: { inline: false, iframeHeight: 500 } } }` on `Playground` and `StickyHeader` (the two page-scroll demos surfaced via `<Canvas>` in `Affix.mdx`) — this makes Storybook render those specific Canvas blocks as real per-story `<iframe>`s (their own document/window) instead of inlining the live React tree into `.docs-story`'s DOM, sidestepping the containing-block issue entirely. `WithinScrollContainer` didn't need this — it already creates its own actually-scrollable local container via `scrollContainerRef`, which sits nearer than `.docs-story` in the ancestor chain and wins first. Live-confirmed post-fix: the Playground demo's `<Canvas>` on the Docs page now renders in a genuine nested iframe, and scrolling within it correctly pins the header ("Stuck!" visible with content scrolling behind it, screenshot-verified). The Sticky-header demo's own live re-check was inconclusive in this session's own browser-automation tooling specifically — `document.visibilityState` kept reading `"hidden"` for that check regardless of clicks/scrolls, a known trigger for Chromium's own `IntersectionObserver` throttling on backgrounded tabs, unrelated to the fix — but it shares 100% identical `Affix` usage with the already-confirmed Playground demo and the same passing automated `storybook` Vitest suite, so treated as equally fixed rather than re-litigated further.

  **Correction, same day, at direct user follow-up ("it doesn't change back to 'Stuck!' when the title row is sticking to the bottom") — the "doesn't flip back" claim above was real after all, and is a severe, previously-undetected bug in `Affix.tsx`'s own stuck-detection logic, not a Storybook/copy issue.** Re-investigated with the exact repro the user gave (scroll to the very end, confirm unstuck, scroll back up partway, check whether the label re-engages) instead of accepting the earlier round-trip test as sufficient — this time watching the transition zone in fine-grained ~100px steps with a real screenshot forced before every single read (not just at the start and end). Found it immediately: at a scroll position where `getBoundingClientRect()` showed the header genuinely pinned at the viewport's exact bottom edge (`rect.bottom` equal to `window.innerHeight`, confirmed visually too — the header held its on-screen position while content scrolled beneath it across three separate screenshots), `data-stuck` stayed `false` and the label stayed "Scroll up." Root cause, found by instrumenting a second, independent `IntersectionObserver` directly on the same sentinel and logging its raw entries: **`entry.rootBounds` was reported in a different coordinate frame than `entry.boundingClientRect` whenever `Affix` renders inside a nested browsing context** — confirmed with a real captured entry: `rootBounds: { top: 0, bottom: 912 }` (the actual outer browser tab's height, i.e. `window.innerHeight` on the *top-level* window) while the sentinel's own document (Storybook's preview iframe) was genuinely only `572px` tall (`iframe.contentWindow.innerHeight`). Per the IntersectionObserver spec, `root: null` resolves to the *implicit root* — the outermost top-level browsing context — and `rootBounds` is reported in that root's own coordinate frame, while `boundingClientRect` stays in the target's local document frame; the two are simply not comparable whenever there's an intervening iframe boundary (any embedding context — Storybook's own preview iframe here, but the identical shape for a real consuming app that renders `Affix` inside any iframe, e.g. an embedded widget or micro-frontend). This exact bug was in the code from fix (1) above (the original directional-stuck-detection fix) — it just never surfaced for `side="top"`, because a viewport's own *top* edge is `0` in literally any coordinate frame (so the mismatched `rootBounds.top` coincidentally still compared correctly), while `bottom` genuinely differs by frame and is the only edge `side="bottom"` ever checks. Fixed by dropping `entry.rootBounds` entirely and computing the reference edge locally instead: `scrollContainerRef.current?.getBoundingClientRect()` when a real container is provided (a same-document element, so inherently frame-consistent), or `{ top: 0, bottom: sentinel.ownerDocument.defaultView.innerHeight }` for the default viewport case — both guaranteed to share `entry.boundingClientRect`'s own coordinate frame, since neither crosses an iframe boundary to get there. Two new regression tests added (`Affix.test.tsx`, `unit` project: 16→18): one reproducing the exact cross-frame mismatch (a fake entry whose `boundingClientRect` is genuinely past jsdom's real `768px` viewport, paired with a deliberately wrong, much larger `rootBounds` a broken implementation would trust instead), one covering the `scrollContainerRef.getBoundingClientRect()` path directly (previously untested on its own) — both verified to actually fail against the reverted `entry.rootBounds`-trusting code before being trusted, matching this file's own established discipline. ## Defect fix: the stuck state could stay on after a soft scroll back to the top (2026-11-07, at explicit direction)
Found by the maintainer on a `Navbar sticky` in the `PageShell` story: after scrolling down and back up softly the bar kept its shadow (drawn from `data-stuck`) at the very top of the page. Reproduced with real scrolling in a real browser, on `Affix` alone and in the demo: an eased (momentum) scroll, or a slow drag in 3px steps, left `data-stuck` on at `scrollY` 0, and steps of 7.3px did not, so it depended on where the scroll came to rest.
- **Cause:** the sentinel is one pixel tall and the observer's threshold was `0`. Near the top the sentinel is only partly visible, or just touching the edge, and `isIntersecting` is true for both; moving wholly into view then crosses nothing, so no callback came and the last answer ("stuck") stayed.
- **Fix:** `threshold: [0, 1]`, so reaching a ratio of 1 is a crossing that reports it. With it all three scroll patterns end not stuck, on `Affix` alone and in the `PageShell` demo.
- **Regression check** (`Affix.checks.stories.tsx`, hidden, real browser): scroll down until stuck, then back to the top by an eased scroll, 3px steps and 7.3px steps, and assert `data-stuck` is gone each time. Broken once (the threshold put back to `0`): it failed.
- **Is it a defect?** Yes (`06` §9, the three-question test): a shadow left on at the top is a bug the original pass would have failed, so `Affix` stays Finalized. Every component built on it (`Navbar`'s sticky bar, `Toolbar`, `Alert`, a table's sticky parts) had the same fault and has the fix.
