# Alert

**Tier:** molecule · **Category:** Feedback · **Status:** built 2026-09-23; **Finalized 2026-09-25**, after the final review pass recorded below.

## What was built

A compound component: `Alert` (root), `Alert.Title`, `Alert.Description`, `Alert.Actions`, plus a companion hook, `usePersistentDismiss`, in `packages/utils`. One component covers an inline message and a page-level banner — the decision and its alternatives are [ADR-0023](../adr/0023-one-alert-with-banner-and-sticky-options-and-a-separate-persistence-hook.md). No new dependency (`Presence` was already a direct one) and no new token. Files: the standard set plus three hidden docs-only stories files for the sub-parts ([ADR-0013](../adr/0013-compound-sub-part-properties-documented-via-hidden-docs-only-stories-file.md)).

Props on the root: `tone` (`info` default / `success` / `warning` / `danger` / `neutral`), `variant` (`subtle` default / `outlined` / `solid`), `size` (shared 5-step scale), `icon` (a component, or `false`; each tone has its own default), `banner`, `sticky` + `stickyOffset` + `scrollContainerRef`, `dismissible`, `open` / `defaultOpen` / `onOpenChange`, `role` (`alert` / `status` / `none`), `labels` (`dismiss`), `aria-label` / `aria-labelledby` / `aria-describedby`, and the usual `className` / `style` / `id` / `data-testid`.

## Decisions taken while building

- **The controlled/uncontrolled trio, not ADR-0010's plain `open`:** the alert has its own internal trigger (the dismiss button), which is the case ADR-0010 leaves to the trio. It only ever calls `onOpenChange(false)`, since nothing inside can reopen it.
- **The dismiss button is built locally** (ADR-0008): it takes the tone's own colour. It is a plain `<button>` around an `Icon`, its name `labels.dismiss` ("Dismiss"). There is no `formatNumber`: nothing the component writes contains a number.
- **Role follows the tone** — `alert` (interrupts) for `danger` and `warning`, `status` (waits) for the rest — and `role` overrides either, including `"none"` for a message already on the page at load. The role is computed after `{...props}`, so a stray attribute can't replace it.
- **Exit always, entrance only for an alert that appears (see the follow-up below):** an alert already in the page when it loads shouldn't animate in. Closing fades it while its row collapses (`grid-template-rows: 1fr → 0fr`), so what is below moves up smoothly instead of jumping; clipping (`overflow: hidden`) applies only to the closing state, so a focus ring on an action is never cut off while it is showing. `Presence` keeps it mounted until the animation ends and unmounts at once under reduced motion.
- **Sticky is `Affix` with `asChild` on the alert's own outermost element,** and `Presence` wraps that. A wrapper anywhere around a `position: sticky` element becomes the box it sticks within, and it would never stick; a unit test asserts the sticky element is a direct child of the container. `Affix`'s `data-stuck` (set on that same element) drives a shadow while stuck, swapped per theme as `Card` does. The `Affix` sentinel is a 1px sibling; accepted.
- **Focus moves on when the alert leaves with focus inside it** (the dismiss button, or an action that closes it — `06` §9's never-remove-the-focused-control item): the nearest focusable element outside it, the next in the page or else the previous, is worked out on `focus`, while the alert still exists to measure from, and used when `open` becomes false. Focus somewhere else is left alone.
- **`usePersistentDismiss`** is `useSyncExternalStore` over `localStorage` (or `sessionStorage`): the server snapshot is `"unknown"`, so `ready` is `false` on the server and while hydrating, and a consumer renders nothing until it is `true` (`open={ready && !dismissed}`) instead of flashing a message already dismissed. It syncs across tabs through the `storage` event and across uses in the same tab through its own listener set, falls back to a module-level in-memory map when storage is blocked or full (only then — a copy kept next to a working storage would outlive another tab's `reset`), and stores only a timestamp (`0` for "never expires") under `dbm-dismissed:<key>`. The Docs page says that whether storing even that needs consent is the consumer's call.
- **`banner` is a boolean on `Alert`,** not a `fullWidth`: an alert is already as wide as its container, so "full width" would mislead; what changes is the edge-to-edge treatment.

## Follow-up, 2026-09-23 (before Finalize): `usePersistentDismiss` re-exported from the components package

The hook is implemented in `packages/utils` ([ADR-0023](../adr/0023-one-alert-with-banner-and-sticky-options-and-a-separate-persistence-hook.md)), but `components` re-exported nothing from it, so a consumer installing only `@dbm-system/components` couldn't import it cleanly (with a strict package manager, `primitives` isn't importable from an app that doesn't list it itself). At explicit direction, `components/src/index.ts` now re-exports the hook and its types (`PersistentDismiss`, `PersistentDismissStorage`, `UsePersistentDismissOptions`) from `primitives`; it stays implemented there, so the dependency direction is unchanged, and `primitives` stays an external dependency of the built package (checked in the build output). A test asserts the entry's export is the same function `primitives` defines. Only what a consumer is meant to call is re-exported — not `cx`, `mergeRefs` or `useAnnouncement`. ADR-0023 records the re-export as part of the decision (it was corrected before it was pushed — once an ADR is published it is never rewritten in place), and the Docs page shows the single-package import.

## Follow-up, 2026-09-24 (before Finalize): `Alert.Action`

A screenshot of a brand `Button` in a solid amber alert showed the problem this component had shipped with: measured for every tone, variant and brand in light and dark, a brand `Button` on a **solid** alert is 1.0–1.6:1 against it (against 4.5:1 for a label and 3:1 for an edge), and on subtle and outlined alerts the contrast passes but the brand colour clashes with the tone. The docs' "choose a variant that reads against it" had been written without measuring any of it. Decision and alternatives: [ADR-0024](../adr/0024-alert-action-reads-the-alerts-colours-over-tone-props-on-button-or-unrestricted-children.md). At explicit direction:

- **`Alert.Action`** wraps `Button` (unchanged, still Finalized), takes its size from the alert (`xs`–`xl`) and its colours from the alert's tone and variant, and takes everything else `Button` takes except `variant` (`primary` default / `secondary` / `tertiary`) and `size`. An unknown `variant` is treated as `primary` with a development warning, and a stray `size` or variant at runtime can't win over the alert's. The alert passes its variant and size down through a small context; the tone reaches the action as CSS variables the alert already sets.
- **The treatments** (all three, on each alert variant) were approved as a table before anything was built. On `solid`: primary is an inverted fill (`bg.on-<tone>`) with `text.<tone>` as its label (neutral: `text.secondary`); secondary is outlined in `border.on-<tone>` with `text.on-<tone>` as its label; tertiary is plain `text.on-<tone>`; hovers use `bg.<tone>-subtle` (primary) and `bg.<tone>-hover` (the others); the focus ring is `icon.on-<tone>`. On `subtle` and `outlined`: primary is `bg.<tone>` with `text.on-<tone>`; secondary is outlined in `border.<tone>` (neutral: `border.neutral-strong`) with a `text.primary` label; tertiary is `text.primary`. Neutral keeps a gray primary on subtle and outlined. The colours are applied in `Alert.module.css`, one selector deeper than `Button`'s own rules, and icons inside an action are set to inherit the label's colour (`Button` locks each icon to a tone of its own variant).
- **Ten new semantic tokens** — `bg.on-*` and `border.on-*` — added in their own commit first (see `03-token-system-spec.md`); `text.neutral` was not added.
- **Verified, from the colours the browser actually draws:** a real-browser story measures every tone × alert variant × action variant — the label against its fill (or the alert), and a filled or outlined edge against the alert, at 4.5:1 and 3:1 — in light, in dark and in Emerald (each story asserts the theme it claims). It fails, as it should, when a label is made invisible (checked by doing exactly that). A second story checks an action's height follows the alert's size. Hover colours were computed from the token values (label at least 4.51:1 in light and 6.59:1 in dark) rather than triggered, since Storybook's `userEvent` can't match `:hover`; the `info` solid-primary hover label is 4.5068:1, accepted as the same razor-thin figure `text.info` already has.
- **Also fixed on the way:** the Docs page's Properties table for `Alert.Action`; its stories and snippets; every place the old `Button`-in-`Actions` example appeared.

## Follow-up, 2026-09-24 (before Finalize): inline actions, centred content, and an entrance

Three ideas from the review's gap list, built at explicit direction.

- **`actionsPlacement?: "below" | "inline"`, default `"below"`.** `inline` puts `Alert.Actions` beside the message at the end of the row. It adapts to the *alert's own width*, not the page's: the body is a wrapping flex row, the message has a minimum basis (the new component token `alert.inline-text-min-width`, `20rem`), and the actions drop below on their own when the two don't fit. A media query would have stacked an alert in a narrow sidebar of a wide page badly, and a container query puts size containment on the alert, which collapses it to nothing inside a shrink-to-fit parent. To do this the alert now **splits its children**: `Alert.Actions` (recognised by type) becomes the message group's sibling, and everything else goes in a `text` group — so `Alert.Actions` has to be a direct child; one wrapped in another element is treated as part of the message (a unit test states that; the Docs page and the types say so). It is not limited to banners.
- **`align?: "start" | "center"`, default `"start"`.** Centres the icon, the message and inline actions as one group, with the text centred too. The dismiss button leaves the row (absolutely positioned at the end) and the row takes symmetrical padding for it, so the group stays centred with or without one, and a long message stops short of the button instead of running under it (tested at a narrow width: the check failed when the padding was removed, which the centring assertion alone had not caught).
- **Bug found by the user, fixed the same day: with `align="center"` and the default actions-below placement, the icon stayed at the far left.** The body was a full-width wrapping row (its wrapping items each take a whole row, so its max-content is their sum), so it filled the alert and only the *text* was centred inside it. Centred mode with actions below is now a column exactly as wide as its widest part, so the icon, text and actions are one group in the middle. **A second round on the same feature, reported with a screenshot: the group was centred but the icon was still far from the title.** In centred mode the icon was a separate flex item beside the message, so it sat against the *widest* line (the description or the buttons) while the shorter title was centred well away from it. The icon is now drawn **inline at the start of the first line of the message** — the title, or the description when there is no title — through a context that the alert gives only to its first text child, so it centres and wraps together with those words. It falls back to the old position (before the whole message) when the first thing is plain text or a title drawn onto the consumer's own element (`asChild`, which can take only one child). Every alert resets that context, so an alert nested inside another's first line doesn't inherit the outer icon (a unit test found the leak). The story now uses the reported case (title, description and actions), measures the words themselves, and asserts the icon is within 12px of the title, the first line centred, and the description and actions centred; turning the change off fails it with the reporter's own ~112px gap.

**Why the tests missed it:** the centring story only covered *inline* actions with short text, which happen to form a tight group, and — worse — measured the description's *box*, which stretches across its row wherever the words are. The story now also covers actions-below and measures the words themselves (a range over the text), and fails with a 35px offset on the old CSS (checked before the fix). The lesson: measure the content, not the element that wraps it.
- **An entrance for an alert that appears after the page loads.** `pageSettled.ts` records the load event (or, if it has already happened, now) plus two animation frames; an alert that mounts before that (a server-rendered one hydrating, an app's first render) just is, and one that mounts afterwards — or is reopened through `open` — gets `data-enter` for the length of a fade-and-slide-in whose row opens from `0fr` to `1fr`, the reverse of the exit. The flag is set in a layout effect (before the first paint, so there is no flash of the finished alert first; and after the first render, so a server-rendered alert hydrates unchanged), cleared by the wrapper's own `animationend` (so it never clips a focus ring once the alert is in) and by the reduced-motion rule, which disables the animation and must not leave `overflow: hidden` behind. A real transition is `previousOpen === false`, so React's `StrictMode` remount doesn't animate a page-load alert. No prop: an alert that appears should animate; one that was there should not. **Known limits:** it is a heuristic — a client-side route change or a lazily loaded chunk mounts after the page settled and so animates, which is right for content that appeared and arguably wrong for a whole new page; and jsdom can't run animations, so the unit tests mock the helper and dispatch the prefixed `webkitAnimationEnd` that React listens for there, while a real-browser story checks the flag clears on a real `animationend`.
- **Verified:** unit tests for the child split (actions apart from the message, wrapped actions, actions-only and message-only alerts), the placement and alignment classes, and the whole entrance logic (page not settled / settled, reopened, cleared on animation end, ignores an inner animation ending, StrictMode both ways, cleared when closed); real-browser stories that measure the geometry — inline actions beside the message at 60rem and below it at 16rem, the centred group centred in its frame with and without a dismiss button, text stopping short of the button — and the entrance really animating in and clearing. Each was broken on purpose to confirm it fails (inline layout, centring padding, the entrance flag never clearing).

## Final review before Finalizing, 2026-09-25

The full `06-engineering-standards.md` §9 checklist, run against the code as pushed in `f94fb3b`. Findings, all fixed the same day — each with a real-browser test written first and shown to fail (and shown to fail again with the fix removed):

1. **The dismiss button was 20 × 20px at `xs` and `sm`** (its glyph is `xs` at both, plus 4px of padding a side) — under the 24 × 24px minimum of WCAG 2.5.8 (Target Size, Minimum). It now has a 24px minimum at every size (`md` and up were already 24 / 24 / 28).
2. **A sticky alert had a 1px hairline of page above it.** `Affix` puts a 1px marker before the sticky element to tell when it is stuck, and that marker takes up room in the flow; measured, the alert sat 1px below the top of its container. The sticky wrapper is pulled up by the marker's height, so the alert is flush (the story now asserts under 0.5px, where it had allowed 2). Resolves the "sticky `Affix` sentinel's 1px in a real page" item this file listed as unchecked.
3. **Inline actions overflowed a narrow alert.** The actions row had `flex: 0 0 auto`, so it never shrank below its buttons side by side and its own wrapping never applied — at 375px with an `xl` alert, and even a `md` one at 18rem (349px of content in a 286px box). It now shrinks to the room there is (`flex: 0 1 auto`, `max-inline-size: 100%`), so the buttons wrap inside the alert. **Known limit:** a button doesn't wrap its own label, so an alert too narrow for a single button (an `xl` alert at 20rem, with its icon and dismiss button) still overflows by a few pixels; the test uses 24rem for `xl`.
4. **`dir` was documented but not declared on `AlertProps`** — the same gap `Breadcrumb` had (`06` §9's native-props audit): RTL is a feature with a story and a test, but its type and JSDoc never reached the manifest. Declared, with a JSDoc.
5. **The alert's context value was a new object every render**, re-rendering every `Alert.Action` each time; it is memoised.
6. **Theming was only measured for the actions in dark and Emerald.** The alert's own fills, borders and text (every tone × variant) are now asserted against the tokens they should resolve to in light, dark and Emerald, each story asserting the theme it claims.

Checked and found sound (no change): no hardcoded value in the CSS (90 tokens, no literals); `{...props}` before every computed attribute on all five parts, and `role` cannot be replaced; RTL with centred content, measured on the words (icon right of the title, first line and description centred, dismiss at the far side); all 22 visible stories have a hand-written "Show code" (checked through Storybook's own store); the five Properties tables are complete (25 / 6 / 5 / 5 / 18 rows) with real value options and defaults; the Docs template, roles and names, focus handoff, the controlled/uncontrolled trio, `StrictMode`, SSR safety (`window` only in the module's guarded block, an effect and handlers), and contrast for every pairing this component introduces (re-measured for the label change).

**Not verified in this pass:** a screenshot of the Docs page and of every story (the browser pane could not composite one, so appearance was read from computed styles and geometry), and the Docs page's "Show code" panels opened one by one on the page itself.

## Action labels in the tone's colour, 2026-09-25 (before Finalize)

At explicit direction, a secondary or tertiary `Alert.Action` on a **subtle** or **outlined** alert takes the tone's own text colour for its label (`text.info` on an info alert, and so on; neutral uses `text.secondary`, since there is no `text.neutral`) instead of `text.primary`. (Border and primary are unchanged; the solid variant was already tone-aware.) Measured before building: the label on the alert is 4.51–6.59:1 in light / 7.47–10.68:1 in dark on subtle, and 4.71–6.88:1 / 7.94–10.47:1 on outlined; the `info` label on its tint is 4.5068:1, the tightest margin in the system (it passes 4.5).

**One companion change was necessary, not requested:** the subtle variant's hover fill for those two actions was `bg.<tone>-subtle-hover`, and a tone label on that tint measures **4.15:1 for info** (4.20 warning, 4.44 danger) in light mode — under the 4.5:1 text floor. On a subtle alert the hover fill is now `bg.surface` (4.71:1 or more in light, 7.94:1 or more in dark). An outlined alert's hover fill (`bg.<tone>-subtle`) was already fine (4.51:1 or more). A real-browser story asserts each label is the tone's token on every subtle and outlined alert, and that it still reads (4.5:1) on its hover fill, worked out from the tokens since a synthetic pointer can't trigger `:hover`; it fails when the label is put back to `text.primary` (checked). **ADR-0024** described these labels as neutral; at explicit direction it was amended in place (a dated marker in its Status line and in the Decision) rather than superseded by a new ADR, since the decision itself is unchanged.

## Spacing, 2026-09-25 (before Finalize)

At explicit direction, the space between the message and its actions when they are stacked (actions below) was increased: it was a fixed `space-2` (8px) at every size, and is now `--alert-actions-space`, set per size — `space-2` (8px) at `xs`, `space-3` (12px) at `sm`, `space-4` (16px) at `md` and `lg`, `space-5` (20px) at `xl` — so it grows with the alert. It applies wherever the actions sit below the message (start-aligned, centred, or inline actions that have wrapped). A real-browser story measures the gap at every size (8 / 12 / 16 / 16 / 20px) and fails on the old fixed 8px (checked). The space between a title and its description is unchanged.
