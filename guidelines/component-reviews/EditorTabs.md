# EditorTabs — review

**Status:** Built, with its Docs page, stories, tests and real-browser checks. The §9 review pass has not been declared done and the component is not Finalized.

## What exists
`EditorTabs`: a strip of tabs given as data (`tabs`, an array of `{ id, label, icon, title, dirty, pinned, closable, disabled }`) for tabs a person opens, closes and arranges, built on `Tabs` ([ADR-0145](../adr/0145-editortabs-is-a-data-driven-strip-built-on-tabs-with-a-tabs-item-part-that-asks-the-owner-for-closes-adds-and-moves-over-a-compound-strip-a-list-it-owns-or-a-touch-drag.md)). It owns no list: `onClose`, `onAdd` and `onReorder` ask, and the strip shows the array it is given next.

Props worth knowing: `value`/`defaultValue`/`onValueChange` (a tab id or `null`), `closeSelects` (`neighbor` or `none`), `tabContextMenu` (a render prop of `ContextMenu` items told the tab, its place and `close()`, `move(to)`, `select()`), `overflow` (`scroll` or `menu`), `variant`/`size`/`rounded`, `dir`, `labels`/`formatNumber`, `controllerRef` (`select`, `close`, `add`, `move`, `focus`), and `EditorTabs.Panel` (`Tabs.Content` with `forceMount`). Also built: `Tabs.Item` (see [Tabs.md](Tabs.md)), `useSortable`'s `autoScroll` option, and the `editor-tabs` component tokens.

## Decisions made while building
- **The close button is `aria-hidden`.** A button inside a `tablist` fails `aria-required-children`. It is a pointer shortcut; the Delete key, a middle click and `tabContextMenu` are the other ways, and a tab that can be closed says `aria-keyshortcuts="Delete"`.
- **Touch does not drag.** A touch press on a scrolling strip is a scroll, and `useSortable` cannot tell the two apart. `tapToMove` would make every tap pick a tab up. A touch screen moves a tab through `tabContextMenu`, which a long press opens. Changed from the plan, which had tap-to-move with a long press.
- **Pinned tabs sit outside the sortable.** The hook is given the unpinned tabs only (indexes offset by the pinned count), so a move can never put a tab among the pinned ones, and the keyboard's "where is it now" never drifts from where it is. The cost: pinned tabs cannot be reordered by drag or keyboard.
- **A neighbour is chosen when the tab has gone**, in the commit that removes it from `tabs`, not when the close is asked. A close the owner refuses (a dialog about unsaved changes) selects nothing and moves no focus.
- **A tab names a panel only if one is drawn** (`aria-controls`), since the strip works without panels and an invalid reference is an axe failure.
- **`onMove` keeps keyboard focus**: reordering moves DOM nodes, which can drop focus, so the moved tab is refocused after the commit.
- **The close button keeps focus where it is** (`mousedown` is cancelled): the button is out of the tab order and hidden, so focus landing on it would strand a keyboard user.
- **The per-tab menu is a copy of `DataTable`'s row menu wrapper**, small and second of its kind; extract at the third (`05` §1).
- **Priority stays ⚪** in the inventory (the maintainer asked for the recommendations, and the count in `04` is unchanged).

## Second round: nine gaps closed (2026-10-30)
Decision: [ADR-0146](../adr/0146-editortabs-gets-its-own-tab-menu-a-close-many-request-a-previous-tab-selection-opt-in-shortcuts-a-status-a-tooltip-through-the-tooltip-atom-a-vertical-strip-and-a-css-eased-reflow-over-leaving-each-to-the-app.md). Still not Finalized.

- **A tab menu of its own (`tabMenu`).** Close, Close others, Close tabs after this one and Close all (with `onCloseMany`), and Move to the start, earlier, later and to the end (with `onReorder`), each disabled where there is nothing to do; the app's `tabContextMenu` items follow after a separator. It is the accessible and touch route that the first round left to each app.
- **Closing many (`onCloseMany`, `controller.closeMany`).** Handed the closable tabs together; a selection and a focus decision once, not per tab; one announcement ("3 tabs closed").
- **`closeSelects="previous"`.** A most-recently-used list, and a pure `chooseAfterClose` that closing one and closing many share (11 unit tests).
- **Opt-in `hotkeys`** (`next`, `previous`, `close`, `add`), on `CommandPalette`'s parser; none bound by default; focus follows only when it was on a tab; an unknown modifier warns once.
- **`status`** (`busy`, `error`, `warning`, `statusText`): a spinner or an icon after the name, spoken after it, on the same line as the name (the first draft wrapped it beneath: a check now measures the mark against the name's own line).
- **A tooltip through the `Tooltip` atom** (`tooltip`, then `title`; else the whole name when it is cut). **A bug found while building it:** the atom sets its own `data-state` on the element it wraps, which replaced the tab's `active` or `inactive`, so the selected tab lost its styling and the scroll-into-view stopped. The tab now states `data-state` itself, and a unit test holds it (the real-browser reveal check failed first).
- **A vertical strip** (`orientation`; `useSortable`'s `orientation` option decides the drop side by height). The list scrolls inside the height the root is given (its wrapper is a flex column, which `Tabs` documents as the way to bound it).
- **Motion.** A `translate` transition (a motion token, none under reduced motion) eases tabs to their new places after a reorder, an add or a label change, measured in the list's scrolling coordinates; a new tab fades in; a pointer-dragged tab is not eased again. A closing tab leaves at once.

**Verified:** 137 unit tests for the component (the new ones: the tab menu and its disabled states, `onCloseMany` with a pinned tab, close-all selecting what is left, the owner's items after a separator, a move from the menu, the controller's `closeMany`, `previous` with and without history, every shortcut including a repeat and a refused combination, status names and translated words, the tooltip on hover and on focus and none for a short name, the tooltip text kept out of the name, vertical keys, the entering mark, and `data-state`); 11 for the pure close model; 1 for `useSortable`'s vertical orientation. 31 real-browser checks, with 10 new: a cut name's tooltip on a real hover (and none for a short one), a tab's own tooltip on hover and focus and Escape, the status mark's layout at three sizes, a vertical strip scrolling and filling its width with each tab revealed by the arrow keys, a real drag in a vertical strip, a reorder easing and leaving no offset behind, shortcuts by real key presses with the previous-tab selection, and the tab menu's Close others from a real right-click. The new stories and the Docs page were opened in a running Storybook (the status and vertical stories, in light purple).

**Not verified:** a screen reader (the status words and the tooltip's description), a real touch device and a long press, forced colours for the status marks, a very long strip with the easing running, and a vertical strip in the Docs page's own width. The shortcuts were tried with explicit Ctrl and Alt, not with `mod` on an Apple platform.

**Decisions:** the hotkey helper is imported from `CommandPalette`'s folder (second consumer; extract at the third); the tooltip is not hoverable, so it closes the moment the pointer leaves; the tab menu is drawn only while open, as `DataTable`'s row menu.

## Third round (2026-10-30)
- **Icon sizes.** The status marks (spinner, error and warning icons) follow `Tabs`' new five-step icon size; the close cross stays `xs`. A real-browser check measures all of them at the five sizes. See [Tabs.md](Tabs.md).
- **The overflow fade** is more solid (a `Tabs` change, see [Tabs.md](Tabs.md)); a real-browser check holds its width and solid share and that a scroll button sits inside it.
- **Shortcuts on a Mac.** The example combinations in the story, snippets and Docs were `mod+alt+…`, which on a Mac is ⌘⌥ with the arrow keys or W: the browser uses those to change and close its own tabs and never passes them to the page, so nothing happened. The matching itself is right on an Apple platform (a unit test sends the events a Mac sends: ⌘ and Option with W typing "∑", matched by the physical key, and Control told apart from Command); it is the choice of example that was wrong. The examples are now `ctrl+alt+…` (Control and Option on a Mac, Ctrl and Alt elsewhere), and the Docs and the `hotkeys` JSDoc say which combinations a browser keeps. Not tried on a real Mac keyboard in a browser: the real key presses there were not available here.
- **A vertical strip's add button and tab-list button take the column's width**, the width of the tabs (a real-browser check measures them against a tab).
