# DBM System — Engineering Standards & Agent Process Rules

This doc covers the engineering discipline that sits underneath `05-component-api-conventions.md` — not what a component's API looks like, but how the code inside it is written, and how Claude Code should operate across sessions. Read alongside `CLAUDE.md`.

---

## 1. Clean code

- **Self-explanatory names over comments.** A well-named variable/function beats a comment explaining a poorly-named one. Comments explain *why*, not *what* — if a comment is restating what the code obviously does, delete the comment.
- **No dead code.** No commented-out code blocks, no unused imports/variables/props, no `console.log` left in committed code (a `console.warn` for an intentional dev-mode prop-misuse warning is fine — see §3).
- **Single responsibility.** A component or function does one thing. If a component's implementation file is getting hard to scan, that's a signal to extract a hook or sub-component, not a reason to add more inline complexity.
- **DRY, but not prematurely.** Shared logic (a hook, a utility) belongs in `packages/utils/src/hooks/` once it's used in 2+ places — don't abstract on the first use "just in case."
- **Formatting is automatic, not debated.** Prettier + ESLint (per `02-tech-stack-and-structure.md`) are the formatting authority — don't hand-format against them, don't argue with the linter, fix the lint error or fix the rule (and flag the rule change to me).

## 2. Scalability & architecture

- **Composition over configuration.** Prefer a component that composes well (compound components, `asChild`, slots) over one with 20 boolean flags trying to cover every case. If a component needs a growing list of mutually-exclusive props, that's a sign it should be a compound component instead.
- **No circular dependencies between packages.** `tokens` → `utils` → `icons`/`components` is the dependency direction; nothing downstream gets imported by something upstream.
- **Avoid prop drilling past 2-3 levels.** Use React Context for genuinely cross-cutting state (theme, form context), not as a default for anything inconvenient to pass down.
- **New tokens/components go through the guidelines, not around them.** Adding a component not in `04-component-inventory.md`, or a color/spacing value with no token backing it, means the inventory or token spec is out of date — update the doc as part of the change, don't just quietly add the thing.

## 3. Stability & error handling

- **Fail loud in development, fail safe in production.** Invalid prop combinations should produce a clear `console.warn` in development (stripped in production builds) rather than silently doing the wrong thing — this is standard practice in Radix/React itself and helps both human and agent consumers debug faster.
- **No silent catch blocks.** A `try/catch` that swallows an error without logging or re-throwing is a bug waiting to be invisible. If an error is genuinely expected and safe to ignore, comment why.
- **Semver discipline.** A prop rename, removal, or behavior change to a shipped component is a breaking change — a major version bump and a Changesets entry describing the migration, never a silent patch. Nothing is published yet, so this takes effect when the release pipeline lands (`01-vision-and-goals.md` §13, Phase 8).
- **TypeScript strict mode, no `any`.** Already stated in `05-component-api-conventions.md` — worth restating here as a stability concern, not just a style one: `any` is where runtime bugs hide that the type system would otherwise have caught.

## 4. Performance

- **Memoize deliberately, not reflexively.** `React.memo`/`useMemo`/`useCallback` where profiling or obvious cost justifies it (expensive computation, large lists, components that re-render frequently with stable props) — not wrapped around every component by default, which adds overhead without benefit.
- **Virtualize long lists.** `DataTable` and any component that can realistically render hundreds+ of rows needs virtualization (windowing) as part of its definition of done, not an afterthought bolted on when someone complains.
- **Tree-shaking stays intact.** No barrel-file re-exports that force bundlers to pull in the whole library for one component (the same principle as the icon-prop convention in `05-component-api-conventions.md`).
- **CSS performance:** avoid deeply nested selectors and expensive properties (`box-shadow` animations, layout-triggering properties) in transitions — animate `transform`/`opacity` where possible, consistent with the motion tokens in `03-token-system-spec.md`.
- **Respect `prefers-reduced-motion` on any continuously-repeating animation** (loading spinners, skeleton pulses, anything with `animation-iteration-count: infinite`). For a spinner-type animation that communicates "in progress," slow it down substantially (about 4x the duration) rather than stopping it outright — a fully static spinner reads as frozen or broken, not as "respecting the preference." For a placeholder-type animation (skeleton pulse or wave) with no semantic meaning in the motion itself, `animation: none` is fine. One-shot transitions (hover, focus, state changes) aren't in scope — only continuous/looping animation.
- **Bundle size is tracked, not assumed**, by two separate CI tripwires:
  - `packages/components/scripts/check-component-bundle-size.mjs` budgets the gzipped JS and CSS of **each component of the published package** (the success metric in `01-vision-and-goals.md` §11). It uses `tsup`, the bundler the real build uses, to build each exported component as an isolated, minified, single-entry ESM bundle (external `react`/`react-dom`, no code-splitting between entries). The default JS budget is 10KB.
  - `packages/components/scripts/check-storybook-bundle-size.mjs` covers the **Storybook static build** (`storybook-static/`'s total size and its largest Vite-bundled chunk — `07-storybook-and-documentation-standards.md` §10).
  - A component whose bundle legitimately holds other components can have its own JS budget in `JS_BUDGET_OVERRIDES_KB`, with the reason beside it: `TimeRangePicker` and `Calendar` have 12KB ([ADR-0047](adr/0047-calendar-gets-year-and-month-grids-behind-its-heading-and-a-whole-week-mode-over-more-select-fields-or-a-separate-week-picker.md)). `DateRangePicker` has 22KB, since its bundle holds two `DatePicker`s and so the whole `Calendar` ([ADR-0129](adr/0129-daterangepicker-is-two-datepicker-ends-with-one-range-panel-of-its-own-anchored-to-the-whole-pair-and-a-start-end-value-submitted-as-name-array-over-one-combined-field-a-range-mode-on-datepicker-or-a-panel-extracted-from-it.md)). `MultiSelect` has 18KB, since its bundle holds the option list it shares with `Combobox`, the chip and the popover layer ([ADR-0123](adr/0123-the-floating-option-list-is-shared-by-combobox-and-multiselect-through-internal-and-multiselect-draws-tagsinputs-box-and-chip-over-copying-them-or-adding-a-multiple-prop-to-combobox.md)). `CommandPalette` has 16KB of JS and 7KB of CSS, since its bundle holds a `Dialog`, the option list rows it shares with `Combobox` and the atoms it draws with ([ADR-0132](adr/0132-commandpalette-is-a-prop-driven-dialog-over-a-commands-array-that-owns-its-hotkey-and-a-controller-over-a-compound-of-parts-a-registry-provider-or-a-combobox-in-a-popover.md)). `DataTable` has 32KB of JS and 10KB of CSS (`CSS_BUDGET_OVERRIDES_KB`), since it draws with `Table`, `TableToolbar`, `Pagination`, `Select` and `Checkbox` ([ADR-0085](adr/0085-datatable-takes-columns-and-data-and-holds-the-interaction-state-with-toolbar-selection-and-pagination-parts-over-composed-table-rows-or-a-headless-hook.md)).
  - **Sizes are for a production build:** the script defines `process.env.NODE_ENV` as `"production"`, since development-only code (warnings, the language names behind them) is dropped from an app's build and counting it overstates the cost.
  - An opt-in extra exported beside a component (`export * from "./molecules/CodeBlock/languages"`) is measured as its own entry, and the script fails if a component's bundle contains a marker word of something meant to be opt-in (`CodeBlock` and its Python, Go and Java grammars, [ADR-0027](adr/0027-codeblock-languages-are-registered-by-the-app-over-loading-every-grammar-or-loading-them-asynchronously.md)), because a regression there can stay inside the byte budget.
  - The budgets are set with headroom over the measured sizes, not tuned tight to today's numbers. The approach is a cheap custom script over a new dependency.

## 5. Responsiveness is not optional

Mirroring the accessibility principle in `CLAUDE.md`: **there is no "responsive mode."** Every component must work correctly across the breakpoint scale in `03-token-system-spec.md`, using the fluid typography and spacing tokens as designed — not a fixed-desktop layout with mobile bolted on later. Test each component's Storybook story at multiple viewport widths as part of its definition of done.

## 6. Browser & rendering environment targets

- **Target: last 2 versions of evergreen browsers** (Chrome, Firefox, Safari, Edge). No IE11, no legacy Safari polyfills. This is what makes `clamp()`, CSS custom properties, and CSS Grid usable without fallbacks.
- **SSR/RSC safety:** no unguarded access to `window`/`document`/`localStorage` at module scope or during initial render — guard with `typeof window !== 'undefined'` or an effect, since components should degrade gracefully in a server-rendered environment even though full RSC support is a "later" goal per the roadmap.

## 7. Internationalization & RTL

**Use CSS logical properties for every directional CSS value** — standard web-platform practice for RTL-ready styling (the W3C CSS Logical Properties spec, MDN and web.dev all recommend it as the default), not a DBM-specific convention. Concretely:
- **Spacing/border always logical:** `margin-inline-*`/`padding-inline-*`/`border-inline-*` instead of `-left`/`-right`.
- **Positioning (`position: absolute`/`fixed`) always logical too** — `inset-inline-start`/`inset-inline-end` (or the `inset` shorthand when a value applies to all four sides) instead of `left`/`right`. Two documented exceptions use physical `left`/`right` on purpose: `Badge`'s anchor positions, because whether a component's rendered result should visually mirror under RTL at all is a per-component judgment call ([ADR-0009](adr/0009-rtl-mirroring-is-a-per-component-judgment-call.md)); and `HoverCard`'s hover bridge, which is keyed to Radix's `data-side="left"`/`"right"`, and those values are physical.
- **A part a Radix primitive doesn't own gets the same `dir` as the primitive.** Radix sets `dir` on its own root only, so a label, value or icon drawn *outside* it follows the page instead (`Slider`'s min/max labels came out backwards on a right-to-left page because the slider was left-to-right and they were not). Pass the primitive's `dir` to every wrapper around it, default it (`"ltr"`) rather than inheriting, and measure a right-to-left page in a real browser (jsdom lays out nothing). A `translate(-50%)` centring on a logical inset needs a `:dir(rtl)` override (`translate` has no logical form); a real-browser story measures the centring in both directions.
- **Don't build a translation/string-externalization system for v1** — components shouldn't hardcode user-facing English strings where avoidable (prefer children/props over baked-in text), but a full i18n library integration is out of scope until there's a concrete need, consistent with how mobile/RN was deferred. What a component that must supply text of its own does instead is one optional `labels` object, plus an optional `formatNumber` for any number it shows — [ADR-0021](adr/0021-labels-object-and-optional-formatnumber-over-an-implicit-intl-default.md), `05-component-api-conventions.md` §3.

## 8. Agent process rules (how Claude Code should operate across sessions)

- **Never push without confirmation.** Already a standing rule in `CLAUDE.md` — restated here because it's a process rule, not a code-quality one.
- **Edit `guidelines/*.md` directly when a decision or a fact needs recording; surface what changed and why in the same response.** Mentioning a decision in a chat response isn't the same as recording it — chat scrolls away, `guidelines/*.md` persists — so gating a routine edit on a separate ask-first round trip just means real decisions quietly don't get recorded. This covers a stale count, a wrong name, a dead link and a fix to something a doc describes as pending. **Flag first** instead for a larger rewrite (several sections, or a restructure) with a plan the maintainer approves, one document at a time; and for any change to a standing process rule (this section, `CLAUDE.md`'s principles), which is flagged prominently enough that it gets read even when no pre-approval is needed.
- **Route what you're recording to the right destination, not just the nearest doc, and keep the numbered docs current-state, not a changelog.**
  - A current-state fact goes in the relevant numbered doc (`01`–`07`), **by editing the sentence that is now wrong**. Don't add a dated "Updated/Corrected/Added/Found …" note, and don't narrate how or when something was found or changed.
  - A genuine architecture/API decision goes in `guidelines/adr/`.
  - A component's own review findings (§9 below) go in `guidelines/component-reviews/ComponentName.md`, with `07-storybook-and-documentation-standards.md` §6 holding only the status-table pointer to it.
  - Routine iteration — a debugging dead end, a verification log, an intermediate wrong turn, a "was X, now Y" — goes in the commit message and nowhere else.
  - **`pnpm check-guidelines` (warn-only, also a CI step) flags the usual drift:** a dated update note, an overlong line, a count stated outside `04-component-inventory.md`, an inventory or status-table row that no longer matches the component folders, and a link, section citation or ADR-index entry that no longer resolves. It never fails a build; read its findings and fix them.
  - **A count or list that already has a home is not restated in prose elsewhere.** The component counts live in `04-component-inventory.md`'s summary table and per-component status in `07-storybook-and-documentation-standards.md` §6; other docs say "see the table" rather than quoting a number that will go stale.
- **Keep `guidelines/*.md` current as the project evolves — don't wait to be asked.** When a phase settles something that should be on record (a tool-version decision, a convention established in practice, a fix applied to something a doc still describes as pending), update the relevant doc before reporting that phase done.
- **Periodically audit `guidelines/*.md` and `CLAUDE.md` against the actual current repo state**, not only when logging a new decision — docs drift silently even when every individual change is logged correctly (a doc can describe where something *should* live while the code ended up elsewhere, or a status note can go stale once the thing it describes ships). Fix what the audit finds by the first rule above: routine corrections directly, a larger rewrite flagged first.
- **Stay inside the current phase's scope.** If you notice something that belongs in a later phase, note it for me rather than building ahead — each phase's prompt defines what "done" means for that session.
- **Self-verify before reporting done.** Actually run lint/build/test (and where applicable, the accessibility test suite) and report real results — don't report a task complete based on the code "looking right." This is the single most important process rule: a claimed-done task that doesn't actually pass its own checks is worse than an honestly-incomplete one.
- **Fix blockers properly, not around them.** When you hit a bug, a type error, a failing test, or an environment quirk, find and fix the actual root cause using best practices, industry-standard patterns, and this system's own conventions — not a suppression (`@ts-ignore`, `eslint-disable`, `any`), a hardcoded value in place of a missing token, or a temporary stand-in meant to be revisited later. If the properly-scoped fix genuinely belongs in a later phase (not just "harder than the shortcut"), say so explicitly and flag it — don't paper over it silently.
- **Flag gaps instead of improvising.** If a task requires a decision not covered by any guideline doc, stop and ask rather than guessing — consistent with the closing line of `CLAUDE.md`.
- **Never name, mention, or link to another design system or component library anywhere in this repo or its published output** — not in a Docs page's user-facing prose (`ComponentName.mdx`), not in a code comment (`.tsx`/`.ts`), not in `guidelines/*.md`, `component-reviews/*.md`, or an ADR. This applies to the *written artifact*, not the *reasoning process*: §9's feature-completeness pass (comparing against comparable production component libraries to find real, concrete gaps) stays exactly as valuable and is still expected. Describe the resulting gap and rationale in this system's own terms ("an overlay/notification-dot badge is a common, expected use case this component didn't originally cover") rather than citing which library has the feature, and never link to another library's docs site. Naming one in conversation with the user, to explain where a review finding came from, is fine — chat isn't a committed artifact. If you find an existing reference while doing unrelated work, fix it the same way (drop the name, keep the substance) rather than leaving it for a dedicated pass.

## 9. Component review & enhancement passes

Beyond the initial "definition of done" (`05-component-api-conventions.md` §8, checked once when a component first ships), every component — at any tier: atom, molecule, organism, or template — gets a full review pass. The checklist below applies identically at every tier, using this same list and not a scaled-down one. **Items marked *(molecules/organisms only)* apply from the molecule tier up**: a single atom has no internal composition (of other DBM components, or of a wrapped Radix compound primitive) to audit. Sections marked *(judgment)* are where the scope-creep guardrail below applies; everything else is checklist-driven re-verification, not exploratory redesign. Examples named in an item are components where the issue was found; each item says what to check and how.

**Baseline correctness**
- [ ] Full "definition of done" (`05-component-api-conventions.md` §8) re-verified top to bottom — don't assume it still holds.
- [ ] TypeScript strict mode, no `any` anywhere.
- [ ] JSDoc complete on the component and every prop — this is what feeds the future manifest generator; an undocumented prop is incomplete work, not polish (`CLAUDE.md`).
- [ ] Standard prop patterns still followed (`05-component-api-conventions.md` §3): `forwardRef` (or a justified, JSDoc'd exception), `className`/`style`/`id`/`data-testid` accepted, a controlled/uncontrolled pair for any component holding internal state, `asChild` support where composability matters, component-relevant `aria-*` props explicitly redeclared for documentation visibility.
- [ ] Commonly-relevant native props for the component's own underlying element are audited and redeclared with their own JSDoc, not just the escape-hatch/`aria-*` set. For an `<input>`-based component that means checking `type`/`value`/`defaultValue`/`readOnly`/`autoComplete`/`maxLength`/`minLength`/`pattern`/`autoFocus`/`inputMode`/`name`/`form`, not stopping at `disabled`/`required`; for other elements, whichever native attributes are genuinely relevant. Curate to what's relevant rather than enumerating every attribute; the long tail is covered by the Properties-table disclaimer sentence (Storybook documentation, below).
- [ ] For any component that computes and sets its own `role`/`aria-*`/similar attribute: `{...props}` is spread *before* those explicit attributes in the JSX, not after — read the source directly, don't infer from the type signature (`05-component-api-conventions.md` §3). **Check every part of a compound component, not only the root**, with a probe that passes the attribute and reads the rendered element (`ToggleGroup`'s root was guarded but its item let a same-named `role` and `aria-checked` replace Radix's own). Includes the variant where the ordering exists but is backwards (`FieldError`).
- [ ] Zero hardcoded values — every color, spacing, font-size, radius, shadow, and duration traces to a design-system token; if a needed value has no token yet, add the token first, don't inline it. **A native element's browser default is a value too:** reset the padding, border, font and line height of the native `<input>`, `<textarea>` or `<button>` you draw, so a size is its tokens' sum and nothing the engine adds (`Textarea`'s inner `<textarea>` kept 2px of padding, making a one-row box 4px taller than its tokens say).
- [ ] **An optional override object spread over defaults keeps a default whose override is `undefined`** *(any prop like `labels: Partial<…>`)*. `{ ...defaults, ...overrides }` lets `{ label: undefined }` replace the default, and a consumer's `labels={{ x: t?.x }}` does exactly that, giving a blank name or a crash. Use `mergeDefined(defaults, overrides)` from `utils` and test `{ x: undefined }`.
- [ ] **Text the component parses or highlights costs time in proportion to its length, and a required data prop that isn't there doesn't crash** *(anything that runs a regular expression over consumer text, or takes `code`, `content` or `items` that is often data on its way)*:
  - A lookahead written into a pattern for a word (`[a-z-]+(?=\()`) retries from every letter and is quadratic on one long unbroken word (a `data:` URI, a hash). Time a 29,000-character single word in every grammar, **and test that the cost scales rather than that it stays under a budget at one size**: four times the text must cost about four times, not sixteen. A quadratic input that took 80ms locally passed a 250ms budget and failed it on a slower CI machine. Take the whole word first and decide afterwards by what follows.
  - Let a string or comment that is never closed run to the end of the text as one match, so it isn't retried from every opener.
  - Two whitespace runs with an optional group between them (`\s*(…)?\s*$`) are quadratic on a number followed by many blanks: trim first, then match.
  - A loop that counts from a parsed number with a comparison (`for (i = from; i <= to; i++)`) never ends when the number reads as `Infinity` (a 309-digit string) or is past 2^53. Refuse numbers that are not safe integers, and count steps up to a cap instead of comparing.
  - Render `undefined`, `null` and a wrong type for a required data prop as empty, with a development warning, not a thrown error (`CodeBlock` with `code={undefined}` took the page down).
  - **A function the consumer supplies to process that text** (a `highlighter`, a registered language) is untrusted the same way: check what it returns before drawing it (the shape, and that it still contains the input), catch what it throws, and fall back to the plain text with a development warning ([ADR-0027](adr/0027-codeblock-languages-are-registered-by-the-app-over-loading-every-grammar-or-loading-them-asynchronously.md)).
  - A once-per-message warning needs a test that uses a message nothing else in the file has produced, or the assertion can pass for the wrong reason.
- [ ] Stability: no console noise in production, no silent `catch` blocks, invalid prop combinations fail loud with a dev-mode `console.warn`.
- [ ] SSR/RSC safety — no unguarded `window`/`document`/`localStorage` access at module scope or during initial render. **Server-render it, then hydrate it** *(any component that creates a DOM node or a portal of its own)*: `renderToString` with `window` and `document` removed proves nothing throws, and only `hydrateRoot` over that HTML, with `onRecoverableError` collected (React 19 reports a mismatch there, not through `console.error`), proves the first client render matches it. `Dialog`'s `keepMounted` portaled into an element made in the first client render and passed a server render but not a hydration (`Dialog.ssr.test.tsx`). Whatever the server couldn't have drawn waits for the first commit after hydration.
- [ ] **An editable draft is not a control of the surrounding form** *(a native field shown only while editing: `EditableText`)* — inside a `<form>` it joins the form's validation, so an open, emptied `required` field blocks a submit whose committed value is fine. Give the draft no form owner (a `form` id that matches nothing), submit the committed value through a hidden input, and apply the rules as the edit ends. Test with `form.requestSubmit()` while the field is open and invalid, in a real browser.
- [ ] **Survives React's `StrictMode`** — any component that schedules a timer, subscribes, or otherwise does work from a mount-time effect is tested inside `<StrictMode>`, which in development mounts, unmounts, and remounts it *keeping its refs*. A ref that remembers "already did this" must be reset in the effect's cleanup, or the remount skips the work and the feature silently does nothing in every consumer's dev environment (`EmptyState`'s `announce`; confirm with a failing test before the fix).
- [ ] The component is DBM's own original implementation, not copied or imported wholesale from another design system's source — Radix as the behavior/accessibility foundation is the approved pattern (`02-tech-stack-and-structure.md`); the styling, API shape, and visual identity are ours.
- [ ] **Compound-component sub-part completeness** *(molecules/organisms only — any component using the compound pattern in `05-component-api-conventions.md` §4)* — every sub-export (`.Root`, `.Trigger`, `.Content`, `.Item`, etc.), not just the umbrella component, gets the same baseline-correctness treatment as a standalone component: `forwardRef` (or a justified, JSDoc'd exception), full JSDoc, `className`/`style`/`id`/`data-testid` accepted, and its own commonly-relevant native/Radix props audited and redeclared.
- [ ] **Atom-reuse audit** *(molecules/organisms only)* — confirm the component composes DBM's own existing atoms (`Icon`, `FieldLabel`, `Input`, `IconButton`, etc.) wherever a suitable one already exists, rather than re-implementing equivalent markup, styling or behavior. A molecule duplicating what an existing atom provides is both a DRY violation (§1) and undermines the reason a reviewed atom tier exists to build on.
- [ ] **A wrapped Radix primitive's keyboard behaviour matches the ARIA pattern of the role it announces** *(molecules/organisms wrapping a Radix compound primitive only)* — Radix picks a role for a state, not always the keys that go with it: `ToggleGroup` (single) announces `radiogroup`, where the arrow keys also choose, but Radix moves focus only. Read what the role promises (the ARIA practices pattern), press every key it names, and either add the missing behaviour or choose a role that fits.
- [ ] **A component that provides context to its children is tested nested inside itself** *(molecules/organisms only — `ButtonGroup`, `EmptyState`'s size context, `Toolbar`)* — a provider's value replaces the outer provider's for everything below it, so an inner one that leaves a field unset silently drops what the outer one set, and a disabled outer group leaves inner buttons enabled. Merge with the parent (`own ?? parent`, with `disabled` OR-ed) or document that it doesn't, and test both.
- [ ] **Consumed-atom defect handling** *(molecules/organisms only)* — if this review surfaces a genuine defect in an already-Finalized atom the component consumes, apply the three-question finalization test (below) to that atom, not just to the component under review, rather than working around the defect inside the molecule's/organism's own code. This extends the atom-to-atom precedent (`Badge`'s review finding `Avatar`'s status-dot contrast bug without reopening `Avatar`) to a molecule consuming an atom.
- [ ] **Radix-primitive prop audit** *(molecules/organisms wrapping a Radix compound primitive only)* — extends the native-props audit: for a component wrapping a Radix compound primitive (`Select`, `Popover`, `Accordion`, etc.), the "commonly-relevant" surface to audit and redeclare is the wrapped primitive's own props (e.g. `Select.Root`'s `open`/`defaultOpen`/`onOpenChange`), not raw HTML attributes. **Trace the entire inheritance chain** the wrapped component's exported prop type extends, not just the layer that holds the first gap found: `Popover`'s first round found six gaps from `DismissableLayer`/`FocusScope` and stopped one layer short of two more (`collisionBoundary`/`hideWhenDetached`, from `PopperContentProps`) that only a fresh read of the primitive's complete type definition caught.

**Feature completeness** *(judgment)*
- [ ] Feature-completeness pass against the same role's component in comparable production component libraries — name any concrete gap before adding anything ("X is missing feature Y that comparable components typically have"), not a vague "make it more complete." The comparison is internal reasoning (discussed with the user in chat as needed); the *written* finding — in a commit, a Docs page, a code comment, or any guideline doc — states the gap and rationale in this system's own terms, without naming or linking the library the comparison came from (§8).
- [ ] Required and recommended props all present and sensibly defaulted — a missing commonly-expected prop (a loading state, an `asChild` escape hatch, a controlled/uncontrolled pair) is a gap, not a nice-to-have.
- [ ] Sizes, variants, states, and types covered where they genuinely make sense for the component's role, using the shared `size`/`variant`/`tone` scales (`05-component-api-conventions.md` §2) — never a one-off component-specific scale, and never forced onto a component where they don't apply. **A variant is named from the shared vocabulary in `05` §2** (a bordered one is `outlined`), checked against the existing variant unions rather than coined.
- [ ] Overall feature-rich, complete, and comprehensive relative to what a developer or agent would reasonably expect from a production design system's version of this component — not a minimal/bare-bones implementation.

**Accessibility — verified, not assumed**
- [ ] All necessary ARIA attributes present and correct for the component's actual role (`aria-label`/`aria-labelledby`, `aria-pressed`, `aria-expanded`/`aria-controls`, `aria-haspopup`, `aria-describedby`, etc., as applicable).
- [ ] Keyboard navigation verified by hand: tab order, visible focus indicator, Escape/Enter/Arrow-key behavior where applicable.
- [ ] Automated accessibility test (jest-axe) passes with zero violations — **for a polymorphic (`as`-driven) component, run this against a non-default `as` value too, not just the default element.** `Avatar`'s `role="img"` was correct on the default `span` and became an "aria-allowed-role" violation once `as="button"` existed, since ARIA doesn't permit overriding a native interactive element's own role.
- [ ] **A control's accessible name holds its visible text as whole words, in order** *(any button, link or cell that shows text and has an `aria-label`)* — WCAG 2.5.3 (Label in Name, Level A; [ADR-0112](adr/0112-an-interactive-controls-accessible-name-holds-its-visible-text-as-whole-words-in-order-over-a-name-that-only-means-the-same.md)). A part of a word does not count ("Jan" is not in "January"), and neither does text that is `aria-hidden` or comes from a prop you did not write (a marker's content beside a day's number). Read each such control's visible text and its name side by side. The real-browser run applies axe's `label-content-name-mismatch` to every story, which is how a Storybook bump that brought a newer axe failed 23 stories at once, so a failure there is a finding to fix, not a version to hold back.
- [ ] Any new or changed color pairing introduced by the review is contrast-checked against the methodology in `03-token-system-spec.md` — not assumed from "looks fine."
- [ ] **Cross-part ARIA/id wiring** *(molecules/organisms composing multiple labeling/control pieces only)* — for a component composing a label, control and helper/error text as separate pieces (`FormField`'s shape), verify the `aria-describedby`/`aria-labelledby`/`id` wiring between the pieces is automatic and correct, not just that each piece's own ARIA is correct. A mismatched or missing id between sub-parts is a failure composition introduces that a single atom's ARIA check can't catch.
- [ ] **Nothing drawn inside a labelled cell adds to its name** *(a column heading holding a resize handle, a hint, a count)* — a header cell's accessible name is its content, so a handle named "Resize Name column" and a hidden hint about its keys became part of the heading ("Name Resize Name column Arrow keys resize…"). Draw a hint once outside the cells and point at it with `aria-describedby`, and name a cell that holds a named control with `aria-label`. Read the cell's accessible name in a test (`getByRole("columnheader", { name })`), since an axe pass doesn't see it.
- [ ] **Composed tab order** *(molecules/organisms only — extends the keyboard-navigation item)* — "tab order" for a composed component means the full tab order across *all* its interactive sub-parts together (a stepper's increment/decrement buttons relative to its own text input), verified as a whole, not each internal atom's tab behavior in isolation.
- [ ] **A responsive or measured collapse never removes the control that has keyboard focus** *(any component that hides or removes controls as its space changes)* — hiding a focused control (`display: none`, unmounting) drops focus to the top of the document and the keyboard user loses their place. If a change the user's own action causes (choosing a page) would hide the control they are on, hold it back while keyboard focus (`:focus-visible`) is on it and apply it when focus moves on; a mouse click isn't keyboard focus, so it needn't wait. The same applies when the control disappears from the reader's own scrolling (`Tabs`' scroll buttons, once there is nothing left to scroll to) and when a component removes itself on dismissal (`Alert` works out where focus goes next while it is still there). Prove it with real keyboard input in a real browser, not jsdom. **Do not read where focus is when the change is reported:** the browser drops focus from a hidden element as soon as anything reads the page's layout, which can be before the width change is reported (`Sidebar`'s first fix read `document.activeElement` at the change and failed under a test run that queried the page first). Keep "focus is inside" from the focus events, and do not clear it on a blur that comes from the column being hidden.
- [ ] **Focus is handed back after a late finish only if it is still there** *(any component that restores focus when it closes, saves or removes itself: `EditableText`, `Alert`)* — a close the person's key started can complete much later (a request answered, an owner holding the field open), by which time they may have moved on. Return focus only if it is still inside the component or on `body`; otherwise leave it. Prove both ways in a real browser: move focus away before the finish and assert it stays; leave it and assert it returns.
- [ ] **Live regions announce a change, never a first appearance** *(any component with a status/live region — `useAnnouncement` in `utils` is the shared timing)* — the region is in the page before its text changes, and the text is announced only when the value changes between two states that were *both on screen*. Data arriving after mount (`Pagination`'s `pageCount` going from 0 to 20 with a page already chosen in the URL) is a first appearance, not a change; announcing it is noise. Forget the remembered value while there is nothing to show.
- [ ] **In a control with more than one focusable part, each key acts on the part that has focus** *(any component wrapping a Radix primitive with several thumbs, tabs, items or handles)* — focus each part in turn and press every key the primitive handles (arrows, Page Up/Down, Home, End), asserting *which* part moved, not only that something did. Radix's `Slider` moves its first thumb on Home and its last on End whichever thumb is focused, which is right for one thumb and wrong for two (`RangeSlider`); a test that only looked at the total or at the first thumb passed.
- [ ] **Every interactive target is at least 24 × 24 CSS pixels** (WCAG 2.5.8, Target Size Minimum) — measure it at *every* size step, not only the default: a glyph plus padding can fall short at the smallest steps (`Alert`'s dismiss button was 20 × 20px at `xs` and `sm`). Give a small control a `min-inline-size`/`min-block-size` of `space.6` rather than relying on padding. Where the control's *look* must stay small (`Tag`'s remove button), extend only the hit area: an invisible, centred `::after` of at least `space.6` on a `position: relative` control. `getBoundingClientRect` doesn't see a pseudo-element, so the test presses points 11px either side of the centre with `elementFromPoint`.
- [ ] **A control made of several parts, or one that takes typed text, is fed the text a phone, an autofill and a paste send, in a real browser** — several characters in one `input` event, with no key events (`05` §3). `TimePicker` worked for every key a test typed and turned "041" into "01" when the text arrived as one string.
- [ ] **A real-browser check that needs a modifier key holds it through one `userEvent.setup()`** — Storybook's `userEvent.click` and `userEvent.keyboard` each make their own keyboard, so a Shift pressed by one isn't held by the other (a shift-click sort lost its first column). `const user = userEvent.setup(); await user.keyboard("{Shift>}"); await user.click(…)`.
- [ ] **A listener on a node that other components portal into is a native one** *(a list, region or container whose children are drawn into it by portals)* — the children's events never pass through the node's own React props, so `onPointerEnter`, `onFocus` and the like on it fire for nothing but the node itself (`Toast`'s list: a fan never spread out under the pointer, and the focus bookkeeping worked only because the region's own focus is on the list). Attach native listeners from an effect, and prove it with a real pointer and real focus on a child, not by dispatching an event on the node.
- [ ] **A press inside a portaled child reaches the parent's React handlers** *(any component with a handler on its root and a portaled part, such as a popover's content)* — React bubbles a portal's events to its React parent, not its DOM parent, so a root-level `onMouseDown` or `onClick` also sees presses on the portaled panel. Act only when the target is inside the root's own DOM (`event.currentTarget.contains(event.target)`); on `TimePicker` a press on a picker option was sent to a segment instead of choosing.
- [ ] **A scrolling box that holds focusable items scrolls the focused one fully into view, kept clear of any edge fade** *(`Tabs`' list, `Toolbar`'s `overflow="scroll"`, any strip of controls)* — a browser scrolls a focused element into view only when it is *completely* hidden, so an item that is only partly visible stays cut off behind a fade. Reveal it yourself from bounding rectangles and `scrollBy` (right-to-left safe; `scrollIntoView` would scroll the page), run after the browser's own scroll, keeping the box's `scroll-padding` clear. Test it by arrowing through *every* item in a real browser and asserting each ends up fully inside, not by checking the last one.
- [ ] **"One tab stop" is tested from the item next to the group, not only into it** *(a roving-focus container holding a nested group)* — a nested roving group makes its own container a second tab stop, and a test that only tabs *into* the bar passes either way. Press `Tab` from the item before the group and expect to leave the container (and `Shift+Tab` back), in jsdom and in a real browser (`Toolbar.ToggleGroup`).
- [ ] **A list with its markers removed states `role="list"` / `role="listitem"`** — Safari with VoiceOver drops list semantics under `list-style: none` (`05-component-api-conventions.md` §6). Check any `<ul>`/`<ol>` the component renders and styles, including a `<nav>`'s.

**Responsiveness**
- [ ] Correct behavior across the full breakpoint scale (`03-token-system-spec.md`) — verified live in Storybook at multiple viewport widths via the viewport toolbar addon, not just reasoned about abstractly. No fixed-desktop layout with mobile bolted on.

**Design quality** *(judgment)*
- [ ] Visual execution is modern, clean, premium, and identifiably DBM's own rather than a generic Radix-default or copied look — entirely within the existing token set (color, typography, spacing, radius, shadow, motion). If a new treatment needs a token that doesn't exist yet, add the token first.
- [ ] **Text that changes as the user interacts never resizes or moves what is around it** *(a live value, a counter, a status)* — reserve the width of the widest text it can show (a hidden sizer, or a fixed `ch` width for tabular figures), then measure the neighbouring element's position and size across the values in a real browser, including one, two and three digits and, for a centred stack, the other axis. `Slider`'s value label made its track 8px narrower at 100 than at 99, and shifted a vertical one sideways. To reserve the width without a second copy of the text, draw it from a `data-` attribute in an invisible `::after` (`content: attr(…)`), with tabular figures (`TableToolbar`'s bulk-row count).
- [ ] **Look at it with realistic content at every size, in a real browser — a layout can be exactly as designed and still cut its content off** *(anything that overlaps, crops or truncates)*. A measurement passes when the geometry matches the design, so it can't tell that the design hides something: `AvatarGroup`'s overlap was measured correctly while drawing two-letter initials as "\K" and "/G" from `md` up. Screenshot the widest real content (two-letter initials, long labels, three-digit counts) at the smallest and largest size before signing off geometry, and once in each theme: `CodeBlock`'s highlighted lines were correctly AA and correctly measured, and read backwards in dark mode (a darker band makes the *other* lines look emphasised).
- [ ] Micro-interactions and animation, where they clarify a state change (hover/focus/active transitions, loading/success feedback) — consistent with the existing motion tokens and "motion with restraint" (`01-vision-and-goals.md` §8, principle 5). Not every component needs one — a `Divider` doesn't. Any continuously-repeating animation (spinners, pulses) added or changed must respect `prefers-reduced-motion` per §4.
- [ ] Performance: memoize only where profiling or obvious cost justifies it, not reflexively; tree-shaking stays intact; CSS animates `transform`/`opacity` rather than layout-triggering properties where possible.
- [ ] Scalability: composition over configuration — a component accumulating a growing list of mutually-exclusive boolean flags is a sign it should be a compound component instead (§2).

**Guardrail against scope creep (this is where it happens):** every Feature-completeness/Design-quality enhancement gets proposed with a specific, named rationale before it's built — "X is missing feature Y that [comparable component] has" or "the hover state is instant while every other interactive atom eases" — not a blanket "make it fancier" pass. `01-vision-and-goals.md` §4 goal 7 makes comprehensiveness and premium execution an explicit project requirement, so proposing against that goal is in scope, but every individual addition should still trace to a concrete, stated gap, not be improvised in the moment.

**Theming**
- [ ] Confirmed working in both light and dark mode, and across every shipped brand theme (currently Purple and Emerald) — verified live in a running Storybook instance via the Brand/Mode toolbar toggles, not inferred from the code. A clean typecheck/build is not sufficient evidence: real theming bugs are invisible to `tsc`/`eslint`/`vitest` and only a live browser check catches them (`07-storybook-and-documentation-standards.md` §7.1).

**Storybook documentation**
- [ ] Docs page (`ComponentName.mdx`) exists, first in the component's sidebar group, following the full section template in `07-storybook-and-documentation-standards.md` §4 (Intro, Playground, Properties, Variants/states gallery, Usage guidelines, Best practices, Accessibility, Code examples, Design tokens used, Related components) — not an abbreviated version.
- [ ] Properties section includes one sentence, directly above `<PropertiesTable>`, stating the component also accepts any other native `<element>` attribute beyond what's listed — worded for its actual underlying element (`<button>`, `<div>`, `<span>`, `<p>`, `<label>`, etc.), or phrased around `as` for a polymorphic component (`07-storybook-and-documentation-standards.md` §3 has the requirement and example phrasing). **Double-check the sentence's own example prop names aren't already redeclared and shown in the table above it** — `Avatar` and `Tag` once cited their own `onClick` as a generic passthrough example when each had an explicit `onClick` prop with custom behavior.
- [ ] Code examples section includes at least one snippet demonstrating a genuine *native* prop in use — ideally the same one(s) named in the Properties-section disclaimer sentence, not just the component's own custom props.
- [ ] **The Docs page's "Design tokens used" table matches the stylesheet, checked by a test, not by eye** — it is written by hand and drifts (`CodeBlock`'s lacked seven tokens after three passes). A unit test that reads the component's `.module.css` and `.mdx` and asserts every `--dbm-*` token the stylesheet uses has a `<TokenRow>` (and no row is for a token it doesn't) is a few lines; `CodeBlock.docs.test.ts` is the pattern.
- [ ] Properties table's prop order reads sensibly (content prop → core visual props → behavioral/state props → advanced/escape-hatch props last), via `PropertiesTable`'s `order` prop — don't assume docgen's default order already does (`07-storybook-and-documentation-standards.md` §4 item 3).
- [ ] Properties table's Default column shows the real value for every prop carrying a JSDoc `@default` — don't assume docgen picked it up. It is unreliable in three real shapes: a root Playground meta with no `component:` field; a compound sub-part's `component: Parent.Sub` (a property access docgen can't trace); and a prop whose default is applied by runtime logic or native-HTML implicit behavior rather than a destructuring-parameter default. Check every row against the type file's own `@default` tags directly, since components sharing the same shape turned out differently (`Grid` had some props populate correctly and others not, on the same table). `07-storybook-and-documentation-standards.md` §4.1 has the fix pattern (`table: { defaultValue: { summary: "..." } }`).
- [ ] Playground story exists, positioned directly after the Docs page, with every prop live and interactive — nothing hardcoded via a bare `render`.
- [ ] Every visible story's "Show code" shows hand-written, pasteable code — `parameters.docs.source.code` from the component's `*.snippets.ts`, with the Playground and any args-only story building theirs from the live controls — typechecked against the real components, and checked live on the Docs page once the source has settled (about 3 seconds after opening it). See `07-storybook-and-documentation-standards.md` §4.2 and [ADR-0020](adr/0020-show-code-uses-hand-written-snippets-over-storybook-generated-source.md).
- [ ] Every prop's Storybook control is genuinely interactive wherever it makes sense — a real `select`/`boolean`/`text`/etc. control, not an inert "Set string"/"Set boolean"/"Set object" placeholder — both in the Playground and in every individual variant story's own Controls panel. Use `control: false` (renders as "–") only for props that genuinely can't or shouldn't be live-edited in Storybook.
- [ ] Every story's Controls panel actually drives its canvas, for every story and not only the Playground — checked live by toggling a control and watching the canvas, not by reading the code. Two failure modes:
  - A story with a custom `render` that ignores its own `args` (`render: () => <Component prop="fixed value" />` instead of `render: (args) => <Component {...args} />`) renders correctly once but makes every control a silent no-op, which is worse than an inert placeholder since nothing signals it's broken (`Avatar`'s `as="button"` story showed "span" in the `as` control while the canvas rendered a `<button>`; `07-storybook-and-documentation-standards.md` §5).
  - Where a story intentionally renders multiple instances varying along one fixed axis with no single value a control could represent (an "all sizes" row, a responsive breakpoint map no `select` can express), suppress *only that axis prop's* control (`argTypes: { size: { control: false } }`); every other prop is shared across the grid and stays wired through `args`. Disabling the whole panel (`parameters: { controls: { disable: true } }`) is too blunt: it hides working controls along with the one that doesn't apply. Reserve it for stories with no controllable args at all (a demo driven by its own internal state, such as `ThemeProvider`'s `LiveThemeToggle`).
- [ ] The Playground's own `args` match the component's real prop defaults (its destructuring defaults, e.g. `size = "md"`, `disabled = false`) for every prop that has one — not an arbitrary demo value standing in for a default. Props with no true default (most string/enum props) get a sensible non-blank demo value instead, which is expected.
- [ ] Any prop given a Storybook `args` default of `""` (kept non-nullish so its own control stays interactive) is checked against the component's *own* internal fallback logic, not just its Storybook control. `??` only skips `null`/`undefined`, so an explicit `""` sails straight through a `??` chain and stops it early, backwards from what an *omitted* prop would do (`Avatar`'s `identity = name ?? alt ?? initials` broke `colorful` whenever a story spread an `args.name` of `""`). Use `||` for such a chain when "empty" and "not provided" should mean the same thing; check what an intentionally-empty value should do before swapping the operator.
- [ ] Every other story's effective `args` (Playground defaults plus that story's own overrides, or its `render`'s hardcoded values if intentionally non-interactive) accurately reflect what the canvas shows — a control claiming one value while the canvas shows another is the same bug as the render-ignoring-args issue above.
- [ ] Prop order in every Controls panel (the Playground's and every individual variant story's) reads sensibly — the same sequence principle as the Properties table.
- [ ] Sidebar `title` matches the taxonomy in `07-storybook-and-documentation-standards.md` §3.
- [ ] **A component that contains a `code`, `pre`, `table` or other element Storybook's own Docs stylesheet (`.storybook/docs.css`, under `.sbdocs-content`) styles must be looked at on the Docs page, not only in its stories** — a story renders without that ancestor, so a canvas can be right in every story test and wrong on the page (`CodeBlock`: an inner border, collapsed indentation and grey text, from an `!important` inline-code rule). Test it by rendering the component inside a `.sbdocs-content` wrapper in a hidden story.
- [ ] Docs page visually verified in a running Storybook instance, **again after any change to a stories file's imports** — a module that throws outside the test runner (`vitest/browser`) passes every test and takes the Docs page and every story down, and `tsc --noEmit` passing only proves the MDX compiles, not that the page renders (`07-storybook-and-documentation-standards.md` §4.1).

**Functional verification**
- [ ] Component functions correctly end to end — exercised live, not just read.
- [ ] **What jsdom can't evaluate is tested in a real browser** — `:dir(rtl)` (arrow flips, mirrored alignment), `:focus-visible`, real layout and measurement (`scrollWidth`, whether a row fits, corner radius against height), and computed style from a stylesheet's cascade. A unit test can assert that a class is applied; it can't assert what the class does. Put these in the `storybook` (Chromium) project, as a hidden `!dev` story if there is no visible counterpart to attach the assertions to. jsdom's own `:focus-visible` depends on which tests ran before it, so a unit test that needs it stubs it explicitly.
- [ ] **Measure the content, not the box around it, and don't trust a check that has never failed.** A block element's rectangle stretches across its row wherever its words sit, so a centring or spacing test that measures the box passes whatever the text does (`Alert`'s centred layout shipped with the icon far from the title because the test measured the description's box). Measure the text itself (a `Range` over the text node, not the element that also holds an icon). And break the thing on purpose once, to see the test fail: several tests on `Breadcrumb` and `Alert` passed on first run and did not bite (a keyboard-focus test that passed with the hold-back removed; a centring test that ignored the padding it guarded). Storybook's `userEvent` sends synthetic events, which never match `:hover`, so assert a hover pairing from the tokens' own resolved colours, or prove the rule exists from the stylesheet rule itself (`document.styleSheets`, as `Toolbar`'s scroll-button hover does), rather than triggering it.
- [ ] **A list that opens from inside another overlay is chosen from with a real mouse, in a real browser** *(any portaled list, menu or picker a `Dialog` or `Popover` can host: `Select`, `Menu`, `Combobox`, `DatePicker`, `DateRangePicker`)* — a synthetic pointer event and the keyboard both passed while `Select`'s list was drawn under a dialog's scrim, dimmed and unclickable. Drive a real pointer through the Chrome DevTools Protocol (`Input.dispatchMouseEvent`, as `Dialog.checks.stories.tsx` does, mapping the test iframe's scale), assert the option is the top element at its own point, choose it, and assert the host stayed open ([ADR-0054](adr/0054-portaled-floating-panels-sit-on-the-popover-z-index-step-not-dropdown.md)).
- [ ] **The real pointer outlives a story** *(any real-browser check that asserts something a hover changes)* — a pointer left over an earlier check's position spreads a fan or opens a card under the next one. Put it somewhere neutral (the page's own button) before the check starts, and drive hover with `Input.dispatchMouseEvent`.
- [ ] **A measurement of an element that animates in waits for the animation to finish** *(any check that reads a rectangle of a panel, popover or toast)* — read while the entrance was easing, a 512px panel measured 502px and every layout assertion on it failed by the easing's distance. Wait for `getAnimations()` on the element and its scrim to finish, then a frame, before measuring (`settled` in `Dialog.checks.stories.tsx`).
- [ ] **A control dragged with the pointer ends its drag however the pointer ends, and is measured once it has settled** *(`Splitter`)* — listen on `window` for move and up *and* cancel, remove the listeners on unmount, and wrap pointer capture in a commented `try/catch` (a synthetic or already-ended pointer can't be captured). A measurement taken while the panes still ease to their new size is wrong by the easing's distance: wait for the value to stop changing before comparing. And **a `waitFor` callback must not change the document**: one that appends and removes a probe element on every call re-triggers itself through `waitFor`'s own mutation observer and hangs the run; resolve such values once, outside the polling.
- [ ] Unit test (React Testing Library) covers rendering and interaction, and passes.
- [ ] Self-verify before reporting the review done: actually run lint, typecheck, build, and the full test suite, and report real results — don't report a review complete based on the code "looking right" (`CLAUDE.md`).

**Reporting a review's findings:** present results as a single prioritized, ordered list of exactly what needs to change — added, updated, or removed — not a section-by-section narrative that also explains what already passed. Skip commentary on checklist items that already pass; only what needs action belongs in the list. Two fixed positions within that ordering: if a Playground story is missing, it's always the first item on the list; if a Docs page is missing, it's always the last. Once the findings are actioned and the pass is complete, write them up in `guidelines/component-reviews/ComponentName.md` (create the file if this is the component's first pass) and add/update its row in `07-storybook-and-documentation-standards.md` §6's status table — see `component-reviews/README.md` for that file's conventions.

**Finalized components need explicit confirmation before further changes.** Once the user declares a component's review pass done and the component "finalized," don't make further changes to it — code, stories, docs, or tokens it alone drives — without asking first, even for something that would otherwise be an obvious, in-scope fix (a typo, a stale comment, a missed checklist item noticed in passing). This is a stronger bar than "flag gaps instead of improvising" (§8): post-finalization, a *found* gap gets surfaced and confirmed before touching the file, not fixed proactively the way it would be mid-review. Two things don't count as "changes to the component" and stay unrestricted: reading/discussing it, and separate work that happens to reference it (another component's Docs page linking to it via `RelatedCard`). If later work reveals the finalized component actually needs to change, say so and ask — don't silently reopen it.

**Whether an authorized fix reopens finalized status.** The rule above governs whether a change is *allowed to happen at all* (always: flag, get explicit authorization). This rule governs a separate question that comes after: once authorized and landed, does "finalized" still hold as-is, does only part of the checklist need re-verifying, or does the whole pass need to run again? Getting authorization for the edit is not the same as re-affirming finalized status — a blanket "any authorized fix keeps finalized status" is too blunt, since a narrow diff can still represent a real design decision, and a visually loud diff can still be a pure defect fix. Work through three questions, in order:

1. **Does it change the rendered/behavioral output of anything that already existed at finalization time** — an existing prop's default or visual result under an unchanged value, existing DOM/semantics, or a token value existing usage already renders with?
   - **No** — purely additive (a new prop, a new story, a doc-only edit, or an internal fix with zero visible/API surface): **stays finalized**. If it added new surface (a new prop), that surface still needs its own scoped mini-pass — JSDoc, a11y/contrast if relevant, Storybook coverage, tests — matching the rigor of one of the original review's own findings, just not a full re-run of the whole checklist.
   - **Yes** — go to 2.
2. **Is it correcting a genuine defect** — something that already violated an existing guideline requirement (a contrast failure, an a11y violation, a broken responsive layout, a factual doc error, an actual bug) — such that the *original* finalization pass would have failed this checklist line item had it caught it?
   - **Yes**: **stays finalized**. Fixing a defect is what compliance looks like, not a new design decision — nothing about the rest of the checklist is in question. (`Avatar`'s status dot reusing `bg.success`/`bg.danger`/`bg.warning` directly measured under WCAG 1.4.11's 3:1 non-text floor; it was found and fixed during `Badge`'s own review without reopening `Avatar`'s.)
   - **No**, it's a deliberate preference/design change to something that was already compliant — go to 3.
3. **What's the blast radius?**
   - Scoped to this component's own files only: **partial re-finalization** — re-verify just the checklist sections the change actually touches (a size/padding change touches Design quality, Theming, Responsiveness and Functional verification, but not Accessibility or the feature-completeness pass), then update the component's "Finalized" note with the new date and which sections were re-checked (e.g. "Finalized 2026-08-16, sizing revised 2026-08-20 (re-verified: design quality, responsiveness)").
   - Touches shared tokens/infrastructure other finalized components also consume: full re-run for *this* component, and the same three-question test gets applied to every other finalized component consuming that shared surface — don't assume they're still fine just because their own files weren't touched.

Map to semver instinct only loosely: a defect fix (step 2) reads like a patch regardless of how visible the change is; a purely additive change (step 1, "no") reads like a minor; a preference change to existing surface (step 3) reads like a major. Don't use semver size as the actual test, though — it gets step 2 wrong. A defect fix can be visually loud (looks "major") while still requiring no re-review, and the classification that matters is defect-vs-preference, not diff size.
